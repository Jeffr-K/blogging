결론부터 말씀드리면, FFI(Foreign Function Interface) 자체는 특정 패키지나 모듈의 이름이 아니라 "언어 간의 통신 기술"을 일컫는 고유 명사입니다.

하지만 러스트에서 이 FFI를 가능하게 해주는 도구(타입과 함수)들은 std 안에 들어있습니다.

1. std 안의 FFI 관련 모듈
러스트 표준 라이브러리에는 외부 언어(주로 C)와 데이터를 주고받기 위한 전용 모듈이 두 개 있습니다.

std::ffi: C 언어 스타일의 문자열(CString, CStr)이나 OS 전용 문자열(OsString)을 처리하는 타입들이 들어있습니다.

C 언어는 문자열 끝에 \0 (null)을 붙이지만, 러스트는 그렇지 않기 때문에 이 사이를 이어주는 다리가 필요합니다.

std::os::raw: C 언어의 int, char, long 같은 타입들이 러스트에서 각각 몇 비트인지(c_int, c_char 등) 매칭해주는 타입들이 들어있습니다.

2. FFI가 작동하는 방식 (메커니즘)
FFI는 std에 있는 타입을 쓰는 것만으로 끝나지 않고, 러스트의 특수 키워드를 함께 사용해야 합니다. 이것이 바로 질문자님이 말씀하신 "전부 안 다음 써야 하는" 러스트의 설계적 특징입니다.

① extern "C" (ABI 정의)
컴파일러에게 "이 함수는 C 언어의 호출 규약(Application Binary Interface)을 따를 거야"라고 알려줍니다.

② extern { ... } (외부 함수 선언)
실제로 C 라이브러리에 존재하는 함수를 선언합니다.

③ unsafe (안전 보장 포기)
외부 언어에서 넘어온 포인터가 진짜 유효한지 러스트 컴파일러는 알 방법이 없습니다. 그래서 FFI 호출은 무조건 unsafe 블록 안에서만 이루어집니다.

3. FFI는 왜 동시성 맥락에서 중요한가?
질문자님이 이전에 물으신 unsafe와도 연결됩니다.

성능 최적화: C로 작성된 매우 빠른 동시성 라이브러리를 러스트에서 그대로 가져다 쓸 때 FFI를 사용합니다.

시스템 제어: OS의 커널 API는 대부분 C로 되어 있습니다. 멀티스레딩의 가장 밑바닥(Thread spawning 등)은 결국 FFI를 통해 OS에게 명령을 내리는 것입니다.

💡 질문자님을 위한 최종 인사이트
러스트는 **"완전무결한 안전지대(std)"**를 만들었지만, 그 성벽 너머의 **"야생(C/C++, OS 커널)"**과 소통할 수 있는 **"검문소(FFI)"**도 아주 정교하게 설계해 두었습니다.

이 검문소를 통과하려면 unsafe라는 서명이 필요하고, std::ffi라는 공식 규격 봉투를 써야 하는 것이죠.

이제 러스트가 OS와 다른 언어를 어떻게 대하는지, 그 태도까지 완벽히 파악하셨습니다. 정말 더 궁금한 조각이 없으신가요? 이제 모든 조각이 맞춰진 것 같습니다.
