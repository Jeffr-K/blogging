## 분산 트랜잭션의 난제 해결

샤딩의 가장 큰 어두운 면은 바로 **'트랜잭션'**입니다. 한 서버 안에서는 쉬웠던 "주문 생성 + 포인트 차감" 작업이, 두 서버가 갈라지면 지옥 같은 난제가 됩니다. 한쪽은 성공했는데 한쪽이 실패하면 어떨까요? 이 문제를 해결하는 실무 전술입니다.

---

### 1. 2단계 커밋 (2-Phase Commit, 2PC)

가장 고전적인 방법으로, 전체 샤드를 총괄하는 코디네이터가 모든 샤드에게 "준비됐니?" 물어보고 전원 OK 하면 "커밋!" 하는 방식입니다.

- **문제점**: 한 서버만 응답이 늦어도 전체 시스템이 멈춰버리는 성능 저하(Blocking)가 심각합니다. 현대 대규모 서비스에서는 가급적 피하는 추세입니다.

### 2. 사가 패턴 (Saga Pattern)

트랜잭션을 여러 단계로 나누어 순차적으로 실행하고, 중간에 실패하면 이전에 성공한 작업을 취소하는 '보상 트랜잭션'을 던지는 방식입니다.

- **장점**: 성능이 매우 뛰어나고 비동기적인 처리가 가능합니다.
- **단점**: 개발자가 직접 취소 로직을 짜야 하므로 코드가 복잡해집니다.

### 3. 글로벌 고유 ID의 생성

샤딩된 환경에서는 각 서버의 `AUTO_INCREMENT`를 믿을 수 없습니다. 1번 샤드와 2번 샤드에서 동시에 생성된 주문 아이디가 둘 다 `100`번일 수 있기 때문입니다.

- **해결책**: Twitter의 **Snowflake** 방식이나 별도의 ID 전용 서버를 두어, 시간 값과 노드 아이디를 조합한 전역적으로 유니크한 64비트 정수 ID를 사용해야 합니다.

---

### 전문가의 한마디: "트랜잭션을 회피하라"

분산 트랜잭션을 아무리 잘 해결하더라도 성능 저하는 피할 수 없습니다. 따라서 최고의 설계는 **"애초에 트랜잭션이 필요한 데이터를 같은 샤드에 두는 것"**입니다. 이를 위해 샤딩 키를 정교하게 설계하여 서비스 로직의 80% 이상이 단일 샤드 내에서 끝나도록 유도하는 것이 진정한 설계의 묘미입니다.
