## MVCC: 비차단(Non-blocking) 조회의 핵심 메커니즘

전통적인 데이터베이스는 데이터 정합성을 위해 쓰기 잠금(Write Lock)이 걸린 데이터를 읽기 잠금(Read Lock)으로 차단해야 했습니다. 현대의 고성능 RDBMS는 이러한 제약을 극복하기 위해 **MVCC(Multi-Version Concurrency Control)** 기술을 사용합니다. 

MVCC는 데이터의 여러 버전을 공존시켜 "읽는 세션은 쓰는 세션을 막지 않고, 쓰는 세션 또한 읽는 세션을 막지 않는" 비차단 조회를 물리적으로 구현합니다.

---

## 1. 스냅샷 읽기(Snapshot Read)의 연산 논리

MVCC의 핵심은 개별 트랜잭션이 시작된 시점의 정적인 데이터 **'스냅샷'**을 구성하여 제공하는 것입니다.

- **조회(SELECT)**: 현재의 실시간 데이터를 직접 읽는 대신, 자신의 트랜잭션 ID(XID)보다 과거에 커밋된 최신 버전의 데이터를 찾아 반환합니다.
- **수정(UPDATE/DELETE)**: 기존 데이터를 물리적으로 즉시 삭제하는 대신, 새로운 버전의 데이터를 생성(PostgreSQL)하거나 과거 데이터를 별도 공간에 보존(MySQL/InnoDB)하여 이전 시점의 가시성을 유지합니다.

---

## 2. MySQL(InnoDB)의 구현: 언두 로그 (Undo Log)

MySQL InnoDB 엔진은 원본 데이터 페이지에는 항상 최신 값을 유지하고, 변경 전 데이터는 **언두 로그(Undo Log)** 영역에 링크드 리스트(Chain) 형태로 저장합니다.

1. 특정 레코드의 값을 10에서 20으로 수정합니다.
2. 원본 데이터 페이지는 20으로 갱신되지만, 이전 값 10은 언두 로그에 기록됩니다.
3. 다른 트랜잭션이 해당 데이터를 요청하면, 엔진은 트랜잭션 시작 시점을 확인하여 "20은 미래의 데이터"라고 판단하고 언두 로그에서 10을 역추적하여 제공합니다.

---

## 3. PostgreSQL의 구현: 다중 튜플 (Multi-tuple)

PostgreSQL은 테이블 파일 내부에 동일 데이터의 여러 버전을 직접 공존시키는 방식을 취합니다.

- **xmin / xmax**: 모든 행(Row/Tuple)에는 해당 데이터를 생성한 트랜잭션 ID와 삭제(또는 수정)한 트랜잭션 ID가 메타데이터로 포함됩니다.
- **가시성 체크(Visibility)**: 쿼리 실행 시 이 번호들을 비교하여 현재 트랜잭션이 읽어도 되는 행인지 즉석에서 판별합니다. 이 방식은 테이블 크기를 팽창시키며, 추후 **VACUUM**을 통한 물리적 정리가 수반되어야 합니다.

---

## 4. MVCC의 물리적 제약: 쓰기 충돌 방지

MVCC가 읽기와 쓰기 간의 차단을 해소하더라도, **동등한 쓰기 작업 간의 충돌(Write-Write Collision)**은 반드시 제어되어야 합니다.

- **배타적 잠금(Exclusive Lock)**: 동일 레코드에 대한 배타적 수정 권한을 획득하기 위해 락 대기가 발생하며, 이 과정에서 성능 지연이나 교착 상태(Deadlock)가 발생할 수 있습니다.

---

## 5. 결론

MVCC는 **데이터의 과거 상태를 유지하여 현재의 성능 저하를 방지하는 고도의 가용성 기술**입니다.

1. 락 대기 시간 없이 대규모 동시 조회를 수행할 수 있는 기반을 제공합니다.
2. 언두 로그(MySQL)와 가시성 메타데이터(Postgres)를 통해 일관된 스냅샷을 보장합니다.
3. 트랜잭션 격리 수준 설정에 따라 상이한 데이터 보존 주기를 결정합니다.

다음 아티클에서는 이러한 동시성 제어 중에서도 MySQL 특유의 보호 장치인 **Gap Lock과 Next-Key Lock이 팬텀 리드(Phantom Read)를 물리적으로 어떻게 차단하는지** 분석합니다.
