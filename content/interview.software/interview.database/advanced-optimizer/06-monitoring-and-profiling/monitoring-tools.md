## 모니터링 시스템 뷰: 엔진 내부 연산의 가시성 확보

슬로우 쿼리 로그가 개별 쿼리의 실행 시간을 기록한다면, **Performance Schema(MySQL)**와 **pg_stat_statements(PostgreSQL)**는 엔진 내부에서 소비되는 물리적 자원과 대기 현상의 원인을 정밀하게 분석할 수 있는 시스템 뷰를 제공합니다. 

현대적인 성능 모니터링은 단순히 CPU 및 메모리 점유율을 확인하는 단계를 넘어, 특정 연산에서 발생하는 **대기 이벤트(Wait Events)**와 자원 점유 히스토리를 데이터 기반으로 진단하는 능력을 요구합니다.

---

## 1. MySQL Performance Schema와 sys 스키마

MySQL 5.6+ 버전부터 도입된 `performance_schema`는 엔진 내부에서 발생하는 모든 이벤트를 저레벨에서 수집하는 물리적 데이터 저장소입니다.

- **이벤트 수집 범위**: 함수 호출, 락 경합, 디스크 I/O 발생 빈도 등 미시적인 엔진 동작 데이터를 실시간으로 수집합니다.
- **sys 스키마 활용**: `performance_schema`의 로우 데이터를 사용자 친화적으로 가공하여 제공합니다. 특히 `sys.statement_analysis` 뷰를 통해 인덱스 없이 전체 스캔을 유도하는 고비용 쿼리군을 즉각 식별할 수 있습니다.

---

## 2. PostgreSQL pg_stat_statements 확장 모듈

PostgreSQL의 성능 관리에서 가장 핵심적인 도구는 `pg_stat_statements` 익스텐션입니다.

- **누적 통계 데이터**: 실행 빈도, 총 소요 시간, 평균 처리 시간뿐만 아니라 **공유 버퍼 캐시 히트(Shared Buffer Hit)** 횟수와 I/O 시간까지 정밀하게 계측합니다.
- **분석 활용**: 특정 기간 동안 누적된 데이터를 분석하여 시스템 전체 리소스를 가장 많이 점유하는 쿼리를 식별하고 최우선 튜닝 대상으로 선정하는 근거를 제공합니다.

---

## 3. 대기 이벤트(Wait Events)의 물리적 진단

쿼리 지연의 실질적인 원인은 연산 성능보다 외부 요인에 의한 대기(Wait)인 경우가 많습니다.

- **I/O Wait**: 물리적 디스크 읽기가 병목인 상태입니다. 메모리(`Buffer Pool`) 가용량을 증설하거나 인덱스 필터링 효율을 개선하여 I/O 발생 빈도를 낮추어야 합니다.
- **Lock Wait**: 트랜잭션 간의 자원 경합으로 정체가 발생하는 상태입니다. 트랜잭션의 생명주기를 단축하거나 어플리케이션의 데이터 접근 순서를 단일화하는 설계적 개선이 필요합니다.
- **대기 이벤트의 가치**: "어떤 물리적 자원이 부족한가" 혹은 "어떤 로직 설계가 충돌을 유발하는가"에 대한 객관적인 지표를 제시합니다.

---

## 4. 실전 도구: pg_stat_activity와 실시간 모니터링

`pg_stat_activity` 뷰는 현재 데이터베이스 서버에서 실행 중인 모든 세션의 실시간 상태를 노출합니다.

- **실시간 추적**: 특정 세션이 얼마나 오랫동안 실행(Active) 상태를 유지하고 있는지, 어떤 락을 대기 중인지 식별합니다. 운영 장애 상황에서 비정상적인 쿼리 프로세스를 탐지하고 강제 종료(`kill`)할 수 있는 물리적 근거가 됩니다.

---

## 5. 결론

Performance Schema와 pg_stat_statements는 **"엔진 내부의 연산 과정을 데이터로 가시화하는 정밀 진단 도구"**입니다.

1. 단순 실행 시간 외에 캐시 히트율과 대기 이벤트 종류를 정밀 분석하여 병목의 실체를 파악하십시오.
2. 주기적으로 시스템 뷰의 누적 데이터를 초기화하고 분석하여 성능 변화 추이를 관리하십시오.
3. 데이터 기반의 병목 진단을 통해 불필요한 인력 소모와 하드웨어 증설 비용을 절감하십시오.

이러한 엔진 내부 지표 분석 능력을 갖추었다면, 이제 어플리케이션과 데이터베이스 사이의 물리적 통로를 제어하는 **커넥션 풀(Connection Pool) 최적화 전략**을 분석할 수 있습니다.
