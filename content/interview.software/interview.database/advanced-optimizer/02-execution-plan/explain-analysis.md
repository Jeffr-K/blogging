## EXPLAIN: 쿼리의 실행 경로 분석

작성된 SQL 문이 데이터베이스 엔진에 도달하면 **옵티마이저(Optimizer)**에 의해 여러 경로 중 비용이 가장 적을 것으로 예상되는 하나의 **실행 계획(Execution Plan)**이 결정됩니다. `EXPLAIN` 명령어는 이 의사 결정 과정을 가시화하여 쿼리 성능 저하의 기술적 근거를 제시합니다.

---

## 1. 액세스 타입 (type) 필드 분석

`type` 필드는 데이터베이스가 테이블에서 레코드를 읽어오는 물리적 방식을 나타냅니다. 성능 효율이 높은 순서대로 나열하면 다음과 같습니다.

- **const / eq_ref**: PK나 Unique 인덱스를 사용하여 단 한 건의 레코드만 조회하는 방식. (최고 성능)
- **ref**: 복합 인덱스의 일부 또는 일반 인덱스를 사용하여 여러 건의 레코드를 조회하는 방식.
- **range**: 인덱스를 사용하여 특정 범위(`>`, `<`, `IN`, `BETWEEN`)를 스캔하는 방식.
- **index**: 인덱스 리프 노드 전체를 탐색하는 방식 (커버링 인덱스가 적용되지 않은 경우 비효율적).
- **ALL**: 인덱스 없이 데이터 페이지 전체를 훑는 풀 테이블 스캔 방식 (최적화 필수 대상).

---

## 2. 주요 탐색 지표: key, key_len, rows

- **key**: 옵티마이저가 실제로 선택하여 사용한 인덱스입니다. 이 필드가 `NULL`이면 인덱스를 사용하지 않은 것입니다.
- **key_len**: 선택된 인덱스에서 실제 사용된 바이트 수입니다. 이를 통해 복합 인덱스(A, B, C) 중 어디까지 필터링 조건으로 사용되었는지 분석할 수 있습니다.
- **rows**: 쿼리 처리를 위해 옵티마이저가 읽어야 할 것으로 예상한 레코드 수입니다. 이 수치가 낮을수록 효율적인 실행 계획입니다.

---

## 3. Extra 필드: 내부 연산 오버헤드 탐지

`Extra` 필드는 옵티마이저가 수행하는 부가적인 최적화 작업이나 물리적 비용이 큰 내부 연산을 보여줍니다.

- **Using index**: 커버링 인덱스가 적용되어 테이블 페이지 접근 없이 인덱스 스캔만으로 종료됨.
- **Using where**: 스토리지 엔진으로부터 전달받은 데이터를 MySQL 엔진 차원에서 추가 필터링함.
- **Using filesort**: 인덱스를 활용한 정렬이 불가능하여 메모리나 디스크에서 별도의 정렬 연산을 수행함 (CPU 비용 높음).
- **Using temporary**: 쿼리 결과를 가공하기 위해 내부적으로 임시 테이블을 생성함 (메모리 및 디스크 비용 높음).

---

## 4. PostgreSQL의 EXPLAIN: 비용(Cost) 중심 분석

PostgreSQL의 `EXPLAIN`은 각 단계의 추정 비용(Cost)을 수치화하여 보여줍니다. 특히 **`EXPLAIN ANALYZE`**를 사용하면 예상 비용과 실제 실행 시간의 오차를 정밀하게 대조할 수 있습니다.

- **Seq Scan**: 순차 스캔 (MySQL의 ALL 스캔과 대응).
- **Index Scan vs Index Only Scan**: 인덱스 스캔 후 실제 데이터 페이지 접근 여부 판별.
- **Bitmap Index Scan**: 다중 인덱스를 조작하여 결과를 병합하는 최적화 기법.

---

## 5. 결론

`EXPLAIN`은 쿼리 실행 과정의 비효율을 물리적 지표로 보여주는 진단서입니다.

1. `type` 필드를 `range` 단계 이상으로 개선하는 것을 일차적 목표로 삼으십시오.
2. `Extra` 필드에서 `filesort`나 `temporary`가 발견되면 쿼리 구조와 인덱스 설계를 즉시 재검토하십시오.
3. 쿼리 튜닝은 반드시 실행 계획의 수치를 근거로 수행해야 합니다.
