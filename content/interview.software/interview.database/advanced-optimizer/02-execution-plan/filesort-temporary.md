## Filesort와 Temporary: 내부 연산 오버헤드 분석

`EXPLAIN` 결과의 `Extra` 필드에 나타나는 **`Using filesort`**와 **`Using temporary`**는 옵티마이저가 인덱스를 활용한 정렬이나 그룹화를 수행하지 못해 별도의 연산 부하(CPU, Memory)를 발생시키고 있다는 신호입니다. 대용량 트래픽 환경에서 이러한 내부 연산은 데이터베이스 서버의 로드(Load)를 급격히 상승시키는 주요 원인이 됩니다.

---

## 1. Using Filesort: 인덱스 없는 정렬 프로세스

인덱스는 이미 정렬된 상태의 자료구조입니다. 만약 `ORDER BY` 절에 인덱스 컬럼을 사용하면 엔진은 추가 연산 없이 인덱스 스캔만으로 결과를 반환하지만, 인덱스가 없는 경우에는 별도의 정렬 단계가 필요합니다.

### 1.1 내부 동작과 물리적 비용

- **정렬 버퍼(Sort Buffer)**: 엔진은 개별 세션에 할당된 정렬 버퍼 메모리 내에서 데이터를 정렬합니다. (Filesort라는 명칭과 달리 메모리 내에서도 빈번하게 발생합니다.)
- **디스크 멀지 소트(Disk Merge Sort)**: 정렬해야 할 데이터셋의 크기가 `sort_buffer_size` 설정을 초과하면, 데이터를 디스크에 임시로 쓰고 다시 읽어 들이는 과정에서 I/O 비용이 기하급수적으로 증가합니다.

### 1.2 최적화 전략

- **인덱스 스캔 정렬 활용**: `ORDER BY` 절에 인덱스 컬럼을 포함시켜 추가 정렬 연산 자체를 제거합니다.
- **복합 인덱스 설계**: `WHERE A = 1 ORDER BY B`와 같이 특정 조건 필터링 후 정렬이 필요한 경우, (A, B) 복합 인덱스를 구성하여 정렬 오버헤드를 차단합니다.

---

## 2. Using Temporary: 메모리 및 디스크 임시 테이블

쿼리 가공을 위해 중간 단계에서 **임시 테이블(Temporary Table)**을 생성하는 고비용 작업입니다.

### 2.1 임시 테이블 발생 주요 사례

1.  **DISTINCT**나 **GROUP BY** 연산 시 인덱스를 활용하지 못하는 경우.
2.  **ORDER BY**와 **GROUP BY**에 지정된 컬럼이 서로 다른 경우.
3.  **JOIN** 연산 시 드라이빙 테이블이 아닌 테이블의 컬럼으로 정렬을 시도하는 경우.
4.  대용량 데이터 타입(`TEXT`, `BLOB`)이 포함되어 메모리 임시 테이블(`Memory` 엔진) 공간을 초과하거나, 즉시 디스크 임시 테이블을 생성해야 하는 경우.

### 2.2 최적화 전략

- **그룹화 인덱스 부여**: `GROUP BY` 컬럼에 인덱스를 부여하여 정렬된 상태에서 그룹화가 이루어지도록 유도합니다.
- **조회 컬럼 최소화**: `SELECT *` 사용을 지양하고 필요한 컬럼만 명시하여 임시 테이블의 물리적 행 크기를 최소화합니다.

---

## 3. 정렬 버퍼와 임시 테이블 관련 설정 튜닝

- **sort_buffer_size**: 개별 세션에서 사용하는 정렬 전용 메모리 크기입니다. 과도하게 크게 설정할 경우 동시 접속자가 많을 때 전체 메모리 부족(OOM) 현상을 초래할 수 있습니다.
- **tmp_table_size / max_heap_table_size**: 메모리 기반 임시 테이블의 최대 크기를 결정합니다. 이 임계치를 초과하는 즉시 디스크 기반 임시 테이블(`MyISAM` 또는 `InnoDB`)로 전환되어 성능이 하락합니다.

---

## 4. 결론

`filesort`와 `temporary`의 발생은 인덱스 설계가 최적화되지 않았음을 나타내는 물리적 지표입니다.

1. 정렬(`ORDER BY`)과 그룹화(`GROUP BY`)는 인덱스 설계를 통한 해결을 최우선으로 고려하십시오.
2. 대용량 환경에서는 성능 모니터링을 통해 디스크 정렬(Disk Sorting) 발생 빈도를 철저히 추적하십시오.
