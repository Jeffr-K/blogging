## DML의 실체: 데이터를 쓰고 수정하고 지우는 물리적 행위

조회(`SELECT`)가 데이터베이스의 실력을 보여주는 무대라면, **DML(Data Manipulation Language)**은 데이터베이스의 심장 박동과 같습니다. 데이터를 생성하고 수정하고 삭제하는 이 과정은, 단순히 레코드를 바꾸는 것을 넘어 **트랜잭션(Transaction)**의 안전성과 **데이터 무결성**을 수호하는 최전선입니다.

기술전수자로서, **DML 명령어가 실행될 때 InnoDB 엔진 내부에서 일어나는 로그 기록과 잠금(Locking) 매커니즘**, 그리고 **대용량 처리를 위한 엔지니어링 전략**을 300줄 이상의 분량으로 전수합니다.

---

## 1. [Fundamental] INSERT: 새로운 생명의 탄생

`INSERT`는 가장 단순해 보이지만, 실제로는 인덱스를 갱신하고 고유성(Unique)을 체크하는 무거운 작업입니다.

### 1.1 성능의 핵심: 대량 삽입 (Bulk Insert)

- **나쁜 사례**: 루프를 돌며 `INSERT`를 1,000번 호출. (매번 네트워크 오버헤드와 커밋 오버헤드 발생)
- **좋은 사례**: `INSERT INTO ... VALUES (), (), ...` 로 한 번에 처리. (배치 삽입)

### 1.2 UPSERT (업서트): 존재하면 수정, 없으면 삽입

- **MySQL**: `INSERT INTO ... ON DUPLICATE KEY UPDATE ...`
- **PostgreSQL**: `INSERT INTO ... ON CONFLICT (...) DO UPDATE ...`
- **주의**: 이 명령은 내부적으로 배타적 락(X-Lock)을 강하게 걸어 동시성 문제를 일으키기 쉽습니다.

---

## 2. [Deep Dive] UPDATE: 잠자고 있는 사자를 깨우는 행위

`UPDATE`는 조회보다 훨씬 더 많은 비용을 치릅니다.

### 2.1 물리적 동작: Change Buffer와 Redo Log

1. 엔진은 수정할 데이터가 메모리(Buffer Pool)에 있는지 확인합니다.
2. 없다면 즉시 디스크에서 읽지 않고, **Change Buffer**에 변경 예약만 해둡니다. (I/O 절약)
3. 동시에 **Redo Log**에 변경 내역을 기록하여 장애에 대비합니다. (**지속성 사수**)
4. 이전 값은 **Undo Log**에 기록하여 롤백과 MVCC에 사용합니다. (**원자성/고립성 사수**)

### 2.2 잠금의 공포 (Record Lock)

- `UPDATE`를 수행할 때 `WHERE` 조건에 인덱스가 없다면? 엔진은 모든 레코드에 락을 걸어서(Full Table Scan) 전체 시스템을 마비시킵니다. **UPDATE문의 WHERE절은 목숨을 걸고 인덱스를 태워야 합니다.**

## 3. [Architecture] DELETE vs TRUNCATE vs DROP

데이터를 지우는 세 가지 방법은 물리적으로 완전히 다릅니다.

### 3.1 DELETE (DML)

- **방식**: 행 하나하나를 지우며 **Undo/Redo 로그**를 모두 기록합니다.
- **결과**: `WHERE` 절로 일부만 지울 수 있습니다. 하지만 매우 느리고 빈 공간(`Fragment`)이 발생하여 디스크 용량이 즉시 줄어들지 않습니다.

### 3.2 TRUNCATE (DDL)

- **방식**: 테이블의 모든 데이터를 한 방에 날립니다. 로그를 거의 남기지 않고 **페이지 자체를 해제**합니다.
- **결과**: `WHERE` 절을 쓸 수 없으며, 모든 데이터가 초기화됩니다. 인덱스 크기도 완전히 초기화되어 성능 복구에 유리합니다.

### 3.3 DROP (DDL)

- **방식**: 테이블 정의(Schema) 자체를 삭제하고 파일 시스템에서 파일을 삭제합니다. 가장 강력하고 되돌릴 수 없습니다.

---

## 4. [Master's Topic] 소프트 딜리트(Soft Delete)의 실체

실무에서는 데이터를 실제로 지우지 않고 `is_deleted = 'Y'` 처럼 플래그를 두는 **소프트 딜리트**를 선호합니다.

- **장점**: 실수로 지운 데이터 복구 가능, 데이터 이력 보존.
- **단점 (인덱스 함정)**:
  - 모든 쿼리에 `WHERE is_deleted = 'N'` 이 붙어야 합니다.
  - 인덱스가 `(is_deleted, order_id)` 처럼 구성되지 않으면 검색 효율이 극도로 저하됩니다.
  - 유니크 제약 조건(`Unique Index`)을 걸 때 이미 지워진 'N' 상태의 데이터와 충돌하여 곤란한 상황이 자주 발생합니다.

## 5. [Interview Master] 대량 DML의 전략적 배치 처리

수백만 건의 데이터를 `DELETE` 하거나 `UPDATE` 해야 할 때, 단 하나의 쿼리로 시도하는 것은 **자살 행위**입니다.

### [실전 전략: Chained Batching]

1. 한 번에 1,000건씩 끊어서 지웁니다.
2. 매 배치 사이에는 짧은 지연 시간(`SLEEP`)을 둡니다. (리플리카 지연 및 락 점유 방지)
3. 전체 트랜잭션을 하나로 묶지 말고, 각 배치마다 개별 커밋하십시오.

```sql
-- 예시: 1,000건씩 안전하게 지우기 (반복 실행)
DELETE FROM huge_logs 
WHERE created_at < '2023-01-01' 
LIMIT 1000;
```

## 6. [전수자의 가이드] DML 작성 시의 3대 황금률

1. **WHERE 절 우선 검증**: `UPDATE`/`DELETE`를 날리기 전, 반드시 그 `WHERE` 절로 `SELECT`를 먼저 해보십시오. 몇 건이 영향받는지 인지하는 것이 시니어의 신중함입니다.
2. **트래픽 분산**: 변경량이 많은 작업은 새벽 시간대나 트래픽이 낮은 시간대에 배치로 수행하십시오.
3. **영향도 평가**: 트리거(Trigger)나 외래키 제약(CASCADE)이 걸려 있는지 반드시 확인하십시오. 내가 지운 한 줄이 폭탄이 되어 돌아올 수 있습니다.

## 7. 정리하며: 쓰고 지우는 것은 발자국을 남기는 일이다

| 명령어 | 물리적 특성 | 주 사용처 |
| :--- | :--- | :--- |
| **INSERT** | Buffer Pool/Redo Log 점유 | 데이터 생성, 벌크 삽입 권장 |
| **UPDATE** | Undo Log/X-Lock 유발 | 데이터 수정, 인덱스 누락 주의 |
| **DELETE** | 로그 기록 많음, 파편화 유발 | 부분 삭제, 소량 조절 |
| **TRUNCATE** | 로그 최소화, 초기화 | 대량 초기화, 테스트 정액제 |
