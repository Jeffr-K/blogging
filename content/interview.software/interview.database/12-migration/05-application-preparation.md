## 애플리케이션 계층에서의 마이그레이션 준비

데이터베이스 마이그레이션을 데이터베이스 팀만의 작업으로 생각하는 것은 큰 오산입니다. 애플리케이션 개발 팀에서도 제로 다운타임(Zero-downtime)을 위해 철저한 설계 준비를 갖춰야 합니다.

---

### 1. 연결 정보의 추상화: 하드코딩 탈피

데이터베이스 주소를 하드코팅(IP 등)해두었다면, 전환 시 모든 애플리케이션 서버를 재배포해야 하는 끔찍한 사태가 벌어집니다.

- **해결책**: DNS(Route53 CNAME 등), 프록시(ProxySQL, HAProxy), 혹은 Spring Cloud Config/AWS AppConfig와 같은 동적 설정 변경 서비스를 활용하십시오.
- **효과**: 설정 한 줄 혹은 DNS 값 하나만 바꾸면 수십 대의 서버가 일제히 새 DB를 바라보게 됩니다.

### 2. Dual Write 전략 (이중 쓰기)

DMS 같은 CDC 도구를 쓸 수 없는 폐쇄적인 환경이나 극도의 안정성을 요하는 서비스에서 주로 사용합니다.

- **원리**: 애플리케이션이 `INSERT/UPDATE/DELETE` 작업을 수행할 때, 기존 구 DB(Old)와 시험 동작 중인 새 DB(New) 양쪽에 동시에 쿼리를 날리는 방식입니다.
- **장점**: 두 DB의 데이터를 애플리케이션 레벨에서 완벽하게 동기화된 상태로 유지할 수 있어, 전환 시 데이터 시차가 0이 됩니다.
- **단점**: 쓰기 성능 오버헤드가 발생하며, 두 개 중 하나가 실패했을 때의 예외 처리 로직이 복잡해집니다.

### 3. 기능 토글 (Feature Toggle) 기반 전환

전환 시점에 모든 기능이 한 번에 새 DB로 넘어가게 하지 않고, 일부 유저나 일부 기능(예: 결제 제외한 조회 기능 등)부터 차근차근 새 DB를 쓰게 만드는 방식입니다.

- **장점**: 문제 발생 시 즉시 해당 기능만 롤백할 수 있어 리스크가 분산됩니다.
- **주의점**: 토글이 켜진 유저는 새 DB, 꺼진 유저는 구 DB를 쓰는 동안 **데이터 정합성이 깨지지 않도록** 사전에 정교한 복제 설정(Bidirectional Replication 등)이 필요합니다.

---

### 실전 리포트: 쿼리 타임아웃과 커넥션 풀

마이그레이션할 때 가장 많이 놓치는 성능 지표는 **커넥션 풀(Connection Pool)**입니다. 새 DB 서버의 사양에 맞춰 애플리케이션의 최대 커넥션 수를 재산정하고, 네트워크 구간 변경에 따른 **쿼리 타임아웃(Timeout)** 설정을 리허설 기간 동안 촘촘히 튜닝해야만 원활한 전환이 가능합니다.

---

#### 요약: 개발팀이 체크해야 할 3가지

1. **DB 접속 정보 관리 방식**을 동적 설정 기반으로 바꿨는가?
2. **이중 쓰기(Dual Write)** 로직이 필요한 시스템인가?
3. **새 DB에서의 쿼리 실행 속도**가 이전과 동일하거나 더 나은가?

이러한 준비들이 선행되어야만 데이터베이스 마이그레이션은 비로소 "성공적인 프로젝트"로 기록될 수 있습니다.
