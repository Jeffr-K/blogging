## MVCC (Multi-Version Concurrency Control) 내부 동작 분석

현대 데이터베이스 엔진(InnoDB, PostgreSQL 등)에서 **MVCC(다중 버전 동시성 제어)**는 동시 처리 성능(Throughput)을 결정짓는 핵심 아키텍처입니다. 과거의 데이터베이스가 읽기(Read)와 쓰기(Write)의 충돌을 방지하기 위해 잠금(Lock)을 사용하여 서로를 기다리게 했다면, MVCC는 **"데이터의 버전을 여러 개 관리함으로써 읽는 쪽은 잠그지 않고도 일관된 데이터를 본다"**는 전략을 취합니다.

이 글에서는 InnoDB 스토리지 엔진을 중심으로 MVCC의 물리적 구현 방식과 고립 레벨에 따른 동작 차이를 기술적으로 분석합니다.

---

## 1. MVCC의 물리적 구성 요소

데이터의 여러 버전을 유지하기 위해 엔진은 내부적으로 세 가지 핵심 요소를 관리합니다.

### 1.1 시스템 칼럼 (System Columns)

모든 데이터 레코드에는 보이지 않는 숨겨진 칼럼이 추가됩니다.

- **DB_TRX_ID (6 Bytes)**: 해당 행을 마지막으로 삽입하거나 수정한 트랜잭션의 고유 아이디.
- **DB_ROLL_PTR (7 Bytes)**: 변경 전의 데이터를 담고 있는 **Undo Log**를 가리키는 롤백 포인터.

### 1.2 Undo Log (언두 로그)

- 데이터가 수정될 때마다 이전 버전의 값을 저장하는 별도의 공간입니다.
- 레코드의 `DB_ROLL_PTR`을 따라가면 과거 버전들이 **연결 리스트(Linked List)** 형태로 줄지어 있습니다.

### 1.3 ReadView (리드뷰)

- 특정 트랜잭션이 읽기 시작할 때, **어떤 트랜잭션들의 결과를 볼 수 있고 어떤 것을 볼 수 없는지**를 결정하는 스냅샷 정보입니다.
- 내 트랜잭션 시작 시점 이전에 완료(Commit)된 데이터만 볼 수 있도록 필터링하는 기준이 됩니다.

---

## 2. [Deep Dive] 고립 레벨별 MVCC 동작 차이

MVCC는 사용자가 설정한 **고립 레벨(Isolation Level)**에 따라 ReadView를 생성하는 타이밍을 다르게 가져가며 데이터 노출 범위를 조절합니다.

### 2.1 READ COMMITTED 레벨

- **동작**: 매번 `SELECT` 쿼리를 실행할 때마다 최신의 **ReadView를 새로 생성**합니다.
- **결과**: 다른 트랜잭션이 커밋하여 `DB_TRX_ID`가 바뀌면, 다음 조회 시 즉시 반영되어 보입니다. 이로 인해 **Non-repeatable Read** 현상이 발생합니다.

### 2.2 REPEATABLE READ 레벨

- **동작**: 트랜잭션 시작 후 첫 번째 `SELECT`가 일어날 때 **딱 한 번만 ReadView를 생성**하고, 트랜잭션이 끝날 때까지 이를 계속 재사용합니다.
- **결과**: 트랜잭션 도중에 다른 사용자가 데이터를 수만 번 커밋해도, 내 트랜잭션 안에서는 최초 조회 시점의 데이터만 보입니다. 일관된 읽기를 보장하지만, 너무 오랜 시간 트랜잭션을 열어두면 문제가 발생합니다.

---

## 3. [Architecture] 가비지 컬렉션: Purge Thread

과거 버전의 데이터는 무한정 남을 수 없습니다. 더 이상 아무도 보지 않는(가장 오래된 ReadView보다 더 오래된) Undo Log는 삭제되어야 합니다.

- **Purge Thread**: 백그라운드에서 주기적으로 Undo Log를 스캔하여 필요 없는 데이터를 물리적으로 삭제하고 공간을 반환합니다.
- **History List Length**: 삭제 대기 중인 Undo Log의 길이를 나타내는 지표입니다. 이 값이 급격히 늘어난다면, 시스템 전체 성능이 하락하고 있다는 신호입니다.

---

## 4. [Analysis] MVCC가 성능에 미치는 영향 (Bloating)

MVCC는 읽기 성능을 비약적으로 올리지만, 관리가 소홀해지면 독이 됩니다.

### 4.1 장기 트랜잭션(Long-running Transaction)의 위험

특정 사용자가 트랜잭션을 시작하고 24시간 동안 커밋하지 않는다면?

1. 그 시점 이후에 발생한 모든 변경 내역의 **Undo Log를 지울 수 없습니다.** (Purge Thread가 멈춤)
2. Undo Log 파일이 비정상적으로 비대해져 디스크 공간을 점유합니다 (**Undo Bloating**).
3. 조회를 할 때마다 수천 개의 과거 버전 연결 리스트를 타고 내려가야 하므로 **CPU 사용량이 폭주**합니다.

---

## 5. [Technical Summary] MVCC의 이득과 비용

| 항목 | 상세 내용 | 비고 |
| :--- | :--- | :--- |
| **읽기 성능** | 읽기 잠금이 없어 최고의 동시성 제공 | Selectivity 극대화 |
| **쓰기 오버헤드** | Undo Log 생성 및 System Column 갱신 비용 발생 | I/O 증가 요소 |
| **고립성 구현** | ReadView 타이밍 조절을 통해 일관성 제공 | 엔진 수준의 무결성 |
| **관리 리스크** | 장기 트랜잭션에 의한 Undo Bloating 위험 | 모니터링 필수 항목 |

---

## 6. 결론: "공짜 점심은 없다"

MVCC는 조인과 검색 위주의 복잡한 쿼리들이 쓰기 작업과 한데 어우러져 돌아갈 수 있게 하는 구세주와 같습니다. 하지만 지연된 커밋 하나가 시스템 전체의 Undo Log를 비대하게 만들어 전체 성능을 파괴할 수도 있습니다.

엔지니어는 **`innodb_undo_directory`** 나 **`History List Length`** 메트릭을 모니터링하며, 애플리케이션 레벨에서 트랜잭션의 수명을 최대한 짧게 가져가는 습관을 들여야 합니다. 무결성과 성능은 항상 등가의 교환이 일어나는 영역임을 잊지 말아야 합니다.
