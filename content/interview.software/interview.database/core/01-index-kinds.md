## 데이터베이스 인덱스: B+Tree 구조와 데이터 탐색 최적화

데이터베이스 인덱스(Index)는 검색 성능 향상을 위해 데이터의 물리적 위치를 구조화한 논리적 장치입니다. 인덱스의 본질은 랜덤 I/O를 순차 I/O로 전환하고, 디스크 페이지(Page) 탐색 횟수를 최소화하여 쿼리 응답 시간을 단축하는 데 있습니다.

## 1. [Physical Depth] 왜 B+Tree인가? (B-Tree와의 차이)

대부분의 관계형 데이터베이스(`InnoDB`, `PostgreSQL`, `Oracle`)는 인덱스 구조로 **B+Tree**를 선택합니다. 왜 이 트리가 이토록 사랑받는 걸까요?

### 1.1 B-Tree vs B+Tree 물리적 구조의 차이

- **B-Tree**: 모든 노드(Root, Branch, Leaf)에 실제 데이터(또는 데이터 주소)를 담을 수 있습니다.
- **B+Tree**:
  1. **Leaf Node에만 데이터를 저장**하고, 상위 노드(Non-leaf)는 탐색을 위한 길잡이(Key) 정보만 담습니다.
  2. **페이지(Page)**를 최대한 가볍게 유지하여, 한 번의 I/O로 수천 개의 자식 노드 주소를 메모리에 올릴 수 있게 합니다. (Fan-out 극대화)
  3. **Leaf Node 간의 Double Linked List**: 범위 스캔(Range Scan) 시, 다시 루트로 돌아갈 필요 없이 양옆의 페이지로 즉시 이동할 수 있습니다.

> **분석**: B+Tree의 핵심은 **"Fan-out(분기 수)의 극대화"**입니다. 노드가 가지는 메타데이터를 최소화하여 한 페이지에 더 많은 자식 노드 주소를 담을수록 트리의 깊이(Height)가 낮아지며, 이는 디스크 I/O 비용의 획기적인 절감으로 이어집니다.

## 2. [Deep Dive] 클러스터드 인덱스(Clustered Index)의 실체

테이블당 단 하나만 존재할 수 있는 **물리적 정순서(Physical Ordering)**입니다.

### 2.1 InnoDB의 클러스터드 인덱스 특징

- **리프 노드의 정체**: 클러스터드 인덱스의 리프 노드는 인덱스 정보뿐만 아니라 **"실제 행 데이터 전체"**를 품고 있습니다.
- **PK의 운명**: PK(기본키)가 곧 클러스터드 인덱스가 됩니다. PK 순서대로 데이터 파일(.ibd) 내의 페이지들이 물리적으로 정렬됩니다.

### 2.2 클러스터드 인덱스의 명과 암

- **장점**: PK 기반 조회는 인덱스 탐색이 곧 데이터 탐색이므로 추가 조회가 필요 없습니다 (**Index Scan = Data Scan**).
- **단점**: PK가 무작위(UUID 등)라면, 삽입 시 기존 데이터 사이에 공간을 만드는 **페이지 분할(Page Split)**이 발생하여 디스크 파편화와 성능 저하를 유발합니다. **PK는 반드시 순차적이어야 합니다.**

## 3. 보조 인덱스(Secondary Index)와 더블 룩업

PK 이외의 모든 인덱스는 보조 인덱스입니다.

### 3.1 물리적 링크 구조

보조 인덱스의 리프 노드는 데이터의 물리적 주소(`RID`)를 갖지 않습니다. 대신 **클러스터드 인덱스의 PK 값**을 가집니다.

- **검색 과정**: 보조 인덱스 탐색 -> PK 값 획득 -> PK 인덱스 탐색 -> 실제 데이터 획득 (**Double Lookup 발생**)

### 3.2 커버링 인덱스 (Covering Index)

이 더블 룩업의 비용(Random I/O)을 0으로 만드는 기술입니다.

- 쿼리에 필요한 모든 칼럼이 인덱스 자체에 포함되어 있다면, 엔진은 본 테이블을 아예 열어보지도 않고 인덱스만 보고 응답합니다. `EXPLAIN` 결과에서 `Using index`가 바로 이것입니다.

## 4. 복합 인덱스(Composite Index)와 가장 왼쪽 매칭 법칙

두 개 이상의 칼럼을 묶어 하나의 인덱스로 만드는 것입니다.

### 4.1 가장 왼쪽 매칭 법칙 (Leftmost Prefix Rule)

- 인덱스가 `(A, B, C)` 순서로 생성되었다면, 반드시 **A**가 조회 조건에 포함되어야 인덱스를 탈 수 있습니다.
- `A=1`, `A=1 AND B=1` 은 가능하지만, `B=1` 이나 `B=1 AND C=1` 은 인덱스를 전혀 쓰지 못합니다 (**Full Table Scan**).

### 4.2 칼럼 선정의 '한 끗' 차이: 카디널리티(Cardinality)

복합 인덱스 구성 시, **중복도가 낮고 유일성(Selectivity)이 높은 칼럼**을 무조건 앞으로 배치하십시오.

- 예: `(성별, 아이디)` 보다 `(아이디, 성별)`이 훨씬 강력합니다. 아이디 한 번으로 99%의 데이터를 걸러내는 것이 엔진에게 행복한 상황입니다.

## 5. [Advanced] 어댑티브 해시 인덱스 (Adaptive Hash Index)

InnoDB는 스스로를 튜닝하는 지능형 엔진입니다. B+Tree 인덱스를 타고 내려가는 과정(Tree Traversal)이 너무 잦고 리소스 소모가 크다고 판단되면, 엔진은 자주 쓰이는 인덱스 리프 노드 페이지 주소를 **메모리 상의 해시 테이블**에 직접 기록합니다.

- **효과**: 트리 탐색 없이 한 번의 해시 연산으로 데이터 페이지를 찾습니다 (`O(log N)`에서 `O(1)`로 단축).

## 6. 인덱스 설계의 공학적 원칙

효율적인 인덱스 구성을 위해 고려해야 할 5가지 핵심 지표입니다.

1. **조회 빈도 및 패턴 분석**: `WHERE`, `JOIN`, `ORDER BY` 절에서 빈번하게 사용되는 칼럼을 인덱스 후보로 선정합니다.
2. **카디널리티(Cardinality) 평가**: 중복도가 낮고 선택도가 높은 칼럼을 인덱스 선두에 배치하여 검색 범위를 빠르게 축소해야 합니다.
3. **갱신 비용 고려**: 인덱스 칼럼 수정 시 리프 노드의 재배치 및 페이지 분할 비용이 발생하므로, 삽입/수정이 잦은 칼럼은 인덱스 생성을 신중히 결정합니다.
4. **데이터 크기 최소화**: 긴 문자열은 인덱스 페이지의 밀도를 떨어뜨리므로, 필요한 경우 접두사(Prefix) 인덱스 활용을 검토합니다.
5. **무결성 제약의 활용**: `NOT NULL` 제약 조건은 옵티마이저가 인덱스 스캔 방식을 결정하는 데 중요한 힌트가 됩니다.

## 7. 정리하며: 인덱스는 공간을 팔아 시간을 사는 거래다

| 인덱스 유형 | 물리적 실체 | 핵심 설계 포인트 |
| :--- | :--- | :--- |
| **Clustered** | 데이터 파일 본체 | 순차적 PK 사수 |
| **Secondary** | (Column + PK) 구조 | 커버링 인덱스로 최적화 |
| **Composite** | 다중 칼럼 결합 정렬 | 칼럼 배치 순서가 성능의 핵심 |
| **Hash Index** | 메모리 상의 O(1) 탐색 | 엔진의 자동 튜닝 믿기 |
