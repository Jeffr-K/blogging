## 데이터베이스 이상 현상: 동시성 환경에서의 데이터 무결성 붕괴

데이터베이스 엔진의 고립 레벨(Isolation Level)은 성능을 위해 완벽한 격리를 포기하는 대신 특정 **이상 현상(Anomaly)**을 허용하는 타협안입니다. 개발자는 단순히 레벨의 이름을 외우는 것이 아니라, **어떤 비즈니스 로직이 어떤 이상 현상에 취약한지**를 물리적으로 이해해야 합니다.

이 글에서는 고전적인 읽기 이상 현상부터, 현대적 분산 시스템과 스냅샷 고립 레벨에서 발생하는 고난도의 쓰기 이상 현상들을 기술적으로 분석합니다.

---

## 1. 읽기 이상 현상 (Read Phenomena)

조회 작업이 다른 트랜잭션의 미완료된 변경 사항이나 동시 변경 사항을 읽을 때 발생합니다.

### 1.1 Dirty Read (더티 리드)

- **현상**: A가 데이터를 수정 중이고 아직 커밋하지 않았는데, B가 그 수정된 값을 읽습니다. A가 나중에 롤백하면 B는 존재하지 않는 데이터를 읽은 셈이 됩니다.
- **영향**: 잘못된 잔액 정보 기반의 결제 승인 등 데이터 정합성 파괴의 주범입니다.

### 1.2 Non-repeatable Read (반복 불가능한 읽기)

- **현상**: 한 트랜잭션 내에서 같은 조회를 두 번 수행했을 때, 그 사이 다른 트랜잭션이 해당 데이터를 `UPDATE` 하여 결과값이 달라지는 현상입니다.
- **방지**: `REPEATABLE READ` 이상의 고립 레벨이 필요합니다.

### 1.3 Phantom Read (팬덤 리드)

- **현상**: 범위 조회를 두 번 수행했을 때, 그 사이 다른 트랜잭션이 새로운 행을 `INSERT` 하여 첫 번째 조회에 없던 행이 두 번째 조회에서 나타나는 현상입니다.

## 2. [Deep Dive] 쓰기 이상 현상 (Write Phenomena)

읽기 이상보다 훨씬 진단하기 어렵고 치명적인 결과(Data Corruption)를 초래합니다.

### 2.1 Lost Update (갱신 손실)

- **현상**: 두 트랜잭션이 동시에 동일 데이터를 수정할 때, 나중에 커밋한 트랜잭션이 먼저 커밋한 트랜잭션의 변경 사항을 덮어쓰는 행위입니다.
- **물리적 해결**: 원자적 연산(`UPDATE SET x = x + 1`)이나 낙관적/비관적 락을 통해 해결합니다.

### 2.2 Write Skew (쓰기 스큐)

- **중요성**: 오직 **스냅샷 고립(Snapshot Isolation)** 레벨에서만 발생하는 가장 교활한 이상 현상입니다.
- **시나리오 (의료 당직 시스템)**:
  1. 병원 규칙: 최소 1명의 의사는 당직을 서야 함.
  2. 현재 의사 A, B 둘 다 당직 중.
  3. 의사 A가 `SELECT count(*)` 수행 (결과: 2명). -> 당직 취소 시도 (`UPDATE A status = Off`).
  4. 동시에 의사 B도 `SELECT count(*)` 수행 (결과: 2명). -> 당직 취소 시도 (`UPDATE B status = Off`).
  5. 두 트랜잭션 모두 성공 (각각 다른 행을 건드렸으므로 충돌 아님).
- **결과**: 당직 의사가 0명이 되어 비즈니스 규칙이 붕괴됩니다.
- **해결**: `FOR UPDATE`를 통한 명시적 락(Select for Update)이나 직렬화(`SERIALIZABLE`) 레벨이 필요합니다.

## 3. [Architecture] Serializability vs Linearizability

많은 엔지니어가 혼동하는 두 개념의 명확한 차이입니다.

- **Serializability (고립성)**: 트랜잭션들이 동시에 실행되어도, 결과는 마치 순차적으로(하나씩) 실행된 것과 같음을 보장합니다. **트랜잭션 간의 고립**에 초점이 있습니다.
- **Linearizability (선형성)**: 어떤 작업이 완료된 즉시 모든 관찰자에게 그 결과가 보여야 함을 보장합니다. **원자적 객체와 시간**에 초점이 있으며, 분산 시스템의 정합성과 밀접합니다.

---

## 4. [Interview Master] 정합성 붕괴의 진단과 대응

시스템에서 이상 현상을 감지하고 해결하기 위한 공학적 접근법입니다.

1. **Predicate Lock (서술 잠금)**: 특정 행이 아닌, `WHERE age > 30`과 같은 **조건 범위 전체**를 잠그는 방식입니다. 팬덤 리드와 쓰기 스큐를 막는 가장 강력한 수단이지만 구현 비용이 큽니다.
2. **Materializing Conflicts (충돌 구체화)**: 쓰기 스큐를 막기 위해, 공유 자원(예: 당직표의 날짜 행)을 미리 테이블에 만들어두고 해당 행에 락을 거는 전략입니다.
3. **Conflict Detection (충돌 검출)**: 데이터베이스 엔진이 트랜잭션 커밋 시점에 사이클(Wait-for Graph)을 검사하여, 직렬화 불가능한 상태라면 강제로 트랜잭션을 중단(Abort)시킵니다.

---

## 5. 결론: "완벽한 고립은 존재하지 않는다"

우리는 성능을 위해 고립 레벨을 낮추고 이상 현상을 어느 정도 수용하며 시스템을 운영합니다. 엔지니어의 역할은 **"어떤 이상 현상이 우리 비즈니스에 치명적인가"**를 선별하고, 그 지점(Hotspot)에만 가장 강력한 격리 전략을 적용하는 것입니다.

이로써 데이터베이스의 최하단 물리 엔진부터 상위 SQL 구문, 그리고 추상적인 고립 모델에 이르기까지 **데이터베이스 엔지니어링의 정수**를 모두 다뤘습니다. 신중한 설계와 집요한 검증만이 오염되지 않는 순수한 데이터를 사수하는 유일한 길임을 잊지 마십시오.
