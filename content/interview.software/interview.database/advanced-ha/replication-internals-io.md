## 데이터 복제: 네트워크를 통한 물리적 일치화

데이터베이스의 고가용성(HA)과 읽기 부하 분산을 가능케 하는 핵심 기술은 **Replication(복제)**입니다. 마스터(Source) 노드에서 발생한 데이터의 변경 점을 슬레이브(Replica) 노드로 전달하여 동일한 상태를 유지하는 과정은, 내부적으로 여러 개의 I/O 스레드와 로그 파일이 교차하는 복잡한 물리적 프로세스입니다.

복제 지연(Replication Lag)이 발생하는 근본 원인을 이해하기 위해, 복제 엔진 내부의 3대 핵심 요소를 분석합니다.

---

## 1. 3대 핵심 로그와 스레드의 역할

성공적인 복제를 위해 데이터베이스 엔진은 세 가지 논리적/물리적 장치를 사용합니다.

### 1.1 Binary Log (Source Node)
- **역할**: 마스터 노드에서 발생한 모든 데이터 변경 사항(DML, DDL)을 기록하는 물리 파일입니다.
- **물리적 오버헤드**: 쓰기 작업이 발생할 때마다 실제 데이터 페이지뿐만 아니라 바이너리 로그에도 순차적 쓰기(Sequential Write)가 발생하므로, 디스크 I/O 대역폭을 일부 점유합니다.

### 1.2 I/O Thread (Replica Node)
- **동작**: 슬레이브 노드에서 실행되는 스레드로, 네트워크를 통해 마스터의 바이너리 로그를 요청하고 읽어옵니다. 
- **Relay Log 기록**: 마스터로부터 받은 로그 데이터를 슬레이브의 로컬 디스크에 **Relay Log**라는 이름으로 임시 저장합니다.

### 1.3 SQL Thread (Replica Node)
- **동작**: Relay Log에 기록된 변경 사항을 순차적으로 읽어 슬레이브의 실제 데이터 페이지에 반영합니다.
- **병목의 주범**: 마스터는 멀티 스레드로 수만 건의 쓰기를 동시에 처리할 수 있는 반면, 고전적인 SQL Thread는 단일 스레드로 동작하여 복제 지연의 가장 큰 원인이 되기도 합니다.

---

## 2. 복제 지연(Replication Lag)의 물리적 병목 분석

복제 지연은 단순히 네트워크 속도의 문제가 아니라, 데이터베이스 엔진의 I/O 구조적 한계에서 기인합니다.

1.  **네트워크 레이턴시**: 마스터와 슬레이브 간의 물리적 거리가 멀수록 I/O Thread가 로그를 가져오는 시간이 증가합니다.
2.  **SQL Thread의 직렬화**: 마스터에서 병렬로 실행된 대량의 쓰기 작업이 슬레이브에서는 하나의 SQL Thread에 의해 직렬로 재현(Replay)되면서 처리 속도가 쓰기 발생 속도를 따라잡지 못하는 현상입니다.
3.  **대량 데이터 변경(Huge DML)**: 하나의 트랜잭션에서 수백만 건의 행을 고치면, 해당 변경 로그가 모두 전송되고 다시 실행될 때까지 다른 데이터의 복제가 중단됩니다.

---

## 3. Row-based vs Statement-based 복제 방식 비교

로그를 남기는 물리적 형식(Format)에 따라 복제 성능과 정합성이 결정됩니다.

- **Statement-based**: 실행된 SQL 구문 자체를 기록합니다. 로그 파일 크기가 작아 네트워크 전송이 빠르지만, `NOW()`나 `UUID()` 같은 비확정적 함수 사용 시 데이터 불일치가 발생할 위험이 있습니다.
- **Row-based**: 변경된 데이터의 물리적 'Row' 자체를 기록합니다. 정합성이 완벽하지만, 대량 수정 시 로그 파일 크기가 급속도로 팽창하여 네트워크 및 I/O 부하를 유발합니다. (현대적인 고성능 환경에서는 Row-based를 지향합니다.)

---

## 4. 결론: 복제 구조의 최적화 방향

안정적인 HA 클러스터 구축을 위해서는 복제 엔진의 물리적 한계를 인지해야 합니다.

1.  **멀티 스레드 복제(Parallel Replication)**: 최신 엔진 버전에서 제공하는 병렬 복제 기능을 활성화하여 SQL Thread 단계의 직렬 병목을 해소하십시오.
2.  **Row-based 포맷 권장**: 데이터 무결성을 위해 비결정적 SQL 구문에 취약한 Statement 방식보다 Row 방식을 우선적으로 고려하십시오.
3.  **지연 시간 모니터링**: `Seconds_Behind_Master` 지표를 상시 감시하여, 실시간 조회 정합성이 필요한 도메인에 대한 별도의 라우팅 정책을 수립하십시오.
