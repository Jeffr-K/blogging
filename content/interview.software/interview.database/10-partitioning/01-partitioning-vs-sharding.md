## 파티셔닝 vs 샤딩: 무엇이 다른가?

데이터베이스 커지면 "데이터를 나눈다"는 말을 자주 듣게 됩니다. 이때 가장 많이 혼용되는 개념이 **파티셔닝(Partitioning)**과 **샤딩(Sharding)**입니다. 둘 다 데이터를 쪼개는 것은 맞지만, 적용되는 층위와 목적이 완전히 다릅니다. 기초를 탄탄히 다져봅시다.

---

### 1. 파티셔닝 (Partitioning): "한 지붕 아래 방 나누기"

파티셔닝은 **단일 데이터베이스 서버 내**에서 하나의 큰 테이블의 데이터를 여러 개의 작은 물리적 파일로 나누어 저장하는 기술입니다.

- **범위**: 테이블 레벨의 분할입니다.
- **물리 구조**: 데이터는 별도의 파일들로 쪼개지지만, 관리 주체인 데이터베이스 엔진은 하나입니다.
- **사용 이유**: 백업의 편의성, 오래된 데이터의 신속한 삭제, 그리고 쿼리 성능(Pruning) 향상을 위해 사용합니다.

### 2. 샤딩 (Sharding): "옆집으로 이사 가기"

샤딩은 데이터를 **여러 대의 독립적인 데이터베이스 서버**로 물리적으로 분리하는 기술입니다.

- **범위**: 데이터베이스 서버 레벨의 분할입니다.
- **물리 구조**: 각 샤드는 자신만의 CPU, 메모리, 저장 장치를 가진 완전한 별개의 서버입니다.
- **사용 이유**: 단일 서버의 하드웨어 한계를 넘어서는 수평 확장이 필요할 때 사용합니다.

### 3. 결정적인 차이점 비교

| 구분 | 파티셔닝 (Partitioning) | 샤딩 (Sharding) |
| :--- | :--- | :--- |
| **물리 서버** | 단일 서버 | 여러 대의 서버 |
| **관리 복잡도** | 상대적으로 낮음 | 매우 높음 |
| **부하 분산** | I/O 부하 정도만 분산 | CPU, Memory, I/O 모두 분산 |
| **트랜잭션** | 일반 트랜잭션 사용 가능 | 분산 트랜잭션 필요 |
| **도입 시기** | 데이터가 비대해져 관리가 힘들 때 | 단일 서버 성능으로 감당 불가할 때 |

---

### 디자인 결론

보통 실무에서는 **파티셔닝을 먼저 검토**합니다. 파티셔닝만으로도 데이터 관리 효율이 훨씬 좋아지기 때문입니다. 하지만 전 세계 사용자를 대상으로 하거나, 초당 수만 건의 쓰기가 발생하는 거대 서비스라면 결국 샤딩으로 넘어가야 합니다.

어떤 기술이 더 우월한 것이 아니라, 현재 우리 서비스가 안고 있는 병목 지점이 **'관리의 어려움'**인지 **'자원의 부족'**인지를 정확히 진단하는 것이 전문가의 시각입니다.
