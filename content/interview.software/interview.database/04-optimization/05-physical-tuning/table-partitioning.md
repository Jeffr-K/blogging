## 테이블 파티셔닝: 단일 테이블의 물리적 한계 극복

단일 테이블에 억 단위 이상의 데이터가 적재되면 인덱스 트리 자체가 비대해져 메모리(Buffer Pool) 가용량을 초과하게 됩니다. 이 경우 잦은 디스크 I/O가 발생하며 성능이 한계에 도달하게 됩니다. 

사용자 관점에서는 하나의 논리적 테이블로 취급되지만, 데이터베이스 엔진 내부에서는 데이터를 물리적으로 여러 개의 독립된 파일로 나누어 관리하는 기술이 **테이블 파티셔닝(Table Partitioning)**입니다. 본 아티클에서는 파티셔닝의 물리적 분할 전략과 검색 최적화 기법을 분석합니다.

---

## 1. 파티션 푸르닝(Partition Pruning)의 작동 메커니즘

파티셔닝 환경에서 압도적인 검색 속도를 보장하는 핵심은 **파티션 푸르닝(Partition Pruning)** 기술에 있습니다.

- **물리적 정의**: 쿼리 조건(`WHERE`)을 분석하여 데이터가 존재할 가능성이 없는 파티션은 아예 스캔 대상에서 제외하는 기법입니다.
- **최적화 사례**: 로그 테이블을 연도별로 `logs_2024`, `logs_2025` 등으로 파티셔닝하였다고 가정합니다. `WHERE created_at = '2025-04-07'` 쿼리 실행 시 엔진은 `logs_2024` 파티션 파일은 접근조차 하지 않고 오직 `logs_2025` 페이지만 탐색합니다. 검색 데이터 집합을 1/N로 즉시 축소시키는 물리적 최적화입니다.

---

## 2. 주요 파티셔닝 분산 전략

1.  **Range Partitioning (범위 분할)**: 날짜, 숫자 등의 연속된 범위를 기준으로 데이터를 분산합니다. 이력 데이터의 최신성 관리에 가장 널리 사용됩니다.
2.  **List Partitioning (목록 분할)**: 특정 열의 값 목록(예: 지역 코드 'SEOUL', 'BUSAN')을 기준으로 파티션을 할당합니다.
3.  **Hash Partitioning (해시 분할)**: 특정 컬럼 값을 해시 함수에 통과시켜 각 파티션에 균등하게 분산시킵니다. 특정 파티션에 데이터가 편중되는 핫스팟(Hot-spot) 현상을 방출하기에 유리합니다.

---

## 3. 관리 측면의 물리적 이점: 데이터 아카이빙(Archiving)

파티셔닝은 단순 조회 성능뿐만 아니라 대규모 데이터의 유지보수(Operation) 용이성을 제공합니다.

- **고속 삭제 프로세스**: 보관 주기가 지난 수억 건의 데이터를 `DELETE` 명령으로 삭제하면 언두 로그(Undo Log) 누적과 잠금 경합이 심각해집니다. 반면 파티셔닝 환경에서는 해당 파티션 파일을 통째로 제거하는 **`DROP PARTITION`** 명령을 통해 물리적으로 즉각적인 데이터 정리가 가능합니다.

---

## 4. 실전 설계 시 고려해야 할 물리적 제약

- **PK 및 유니크 인덱스 제약**: 파티셔닝 적용 테이블의 모든 유니크 인덱스와 기본키(PK)에는 반드시 **파티션 키 컬럼**이 포함되어야 합니다. 그렇지 않으면 파티션 간의 중복 체크를 위해 모든 파티션을 스캔해야 하는 비효율이 발생합니다.
- **인덱스의 파편화 (Local Index)**: 각 파티션은 독립적인 인덱스 구조를 가집니다. 파티션을 넘나드는 조회(Cross-partition Query)가 빈번할 경우 단일 비파티션 테이블보다 성능이 저하될 수 있습니다.

---

## 5. 결론

테이블 파티셔닝은 **"거대 데이터 집합을 물리적으로 세분화하여 검색 범위를 국소화하는 전략"**입니다.

1. `Partition Pruning`을 통해 쿼리가 물리적으로 필요한 파티션만 탐색하도록 유도하십시오.
2. 대규모 이력 데이터의 생명주기 관리(Retention)를 자동화하고 인프라 부하를 경감시키십시오.
3. 쿼리 조건에 파티션 키를 반드시 포함하여 물리적 스캔 효율을 극대화하십시오.

이러한 물리적 분할을 넘어, 개별 데이터베이스 서버 노드 단위로 아예 데이터를 분산시키는 **샤딩(Sharding) 설계 전략**을 분석할 수 있습니다.
