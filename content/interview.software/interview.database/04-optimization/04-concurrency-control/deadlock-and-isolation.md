## 교착 상태 (Deadlock): 자원 경합의 불가피한 결과

데이터베이스 엔진은 데이터 정합성 보장을 위해 잠금(Lock) 메커니즘을 사용합니다. 그러나 두 개 이상의 트랜잭션이 서로가 점유한 자원의 잠금 해제를 무한히 대기하는 상황을 **데드락(Deadlock, 교착 상태)**이라 합니다. 

데드락은 단순한 논리적 오류가 아니라, 고도의 동시성 환경에서 발생하는 자원 경쟁 상태(Race Condition)의 물리적 결과물입니다. 본 아티클에서는 데드락 탐지의 내부 알고리즘과 **트랜잭션 격리 수준(Isolation Level)**이 성능에 미치는 물리적 임팩트를 분석합니다.

---

## 1. 데드락 탐지와 해결 알고리즘

데이터베이스 엔진은 자원 점유 상황을 지속적으로 모니터링하며 데드락 발생 여부를 판별합니다.

### 1.1 대기 그래프(Wait-for Graph) 분석

- **사이클 탐지(Cycle Detection)**: 엔진은 트랜잭션 간의 잠금 대기 관계를 그래프로 구성합니다. 이 그래프에서 순환 고리(A -> B -> A)가 발견되는 즉시 데드락으로 규정합니다.
- **희생자 선정(Victim Selection)**: 엔진은 데드락을 해소하기 위해 참여 트랜잭션 중 하나를 강제로 종료(Rollback)시킵니다. 일반적으로 롤백 비용을 최소화하기 위해 **데이터 수정량이 가장 적은 트랜잭션**을 선별하여 롤백을 수행합니다.

---

## 2. 트랜잭션 격리 수준과 동시 처리량의 관계

격리 수준이 높을수록 데이터 일관성은 정교해지지만, 잠금 유지 시간과 범위가 확대되어 전체적인 시스템 처리성능(Throughput)은 하락합니다.

1.  **READ UNCOMMITTED**: 잠금을 최소화하여 성능은 우수하나, Dirty Read 등 정합성 파괴 현상이 발생하므로 실무 적용이 제한적입니다.
2.  **READ COMMITTED**: 커밋된 데이터만 조회하며 대부분의 OLTP 환경(PostgreSQL 기본값)에서 성능과 일관성의 최적 타협점으로 선택됩니다.
3.  **REPEATABLE READ**: 트랜잭션 내 동일 조회 결과를 보장합니다(MySQL 기본값). 갭 락(Gap Lock)의 추가 발생으로 인해 데드락 발생 가능성이 READ COMMITTED 대비 상대적으로 높습니다.
4.  **SERIALIZABLE**: 직렬 실행과 동일한 수준의 무결성을 보장하지만, 광범위한 잠금 설정으로 인해 동시 처리 효율이 가장 낮습니다.

---

## 3. 데드락 발생 억제를 위한 실전 설계 원칙

1.  **트랜잭션 생명주기 단축**: 잠금 점유 시간을 최소화하기 위해 트랜잭션 내부에서 네트워크 I/O나 외부 API 호출을 배제하십시오.
2.  **자원 접근 순서의 단일화**: 다중 테이블 수정 시 모든 트랜잭션이 동일한 순서로 테이블에 접근하도록 설계하여 상호 대기(A->B, B->A) 상황을 차단하십시오.
3.  **유효 인덱스 보장**: 인덱스 부재 시 넥스트 키 락이 테이블 단위로 확산되어 데드락 범위를 넓히는 현상을 방지하십시오.
4.  **최적의 격리 수준 선택**: 비즈니스 무결성 요건을 충족하는 범위 내에서 가급적 낮은 격리 수준을 유지하십시오.

---

## 4. 결론

데드락과 격리 수준은 **"데이터 무결성 확보를 위해 지불하는 성능적 비용"**의 균형점입니다.

1. 데드락 탐지는 엔진의 자동 기능이나, 발생 빈도가 높다면 어플리케이션의 트랜잭션 설계 결함을 의미합니다.
2. 서비스 워크로드에 최적화된 격리 수준을 결정하여 불필요한 잠금 경합을 방지하십시오.
3. 트랜잭션의 실행 시간(Duration)을 짧게 유지하여 자원 점유 시간을 물리적으로 최소화하십시오.

이로써 동시성 제어의 핵심 메커니즘 분석을 모두 마쳤습니다. 다음 테마는 하드웨어 리소스와 직접적으로 맞닿아 있는 **물리적 아키텍처와 메모리 튜닝**의 세계를 기고합니다.
