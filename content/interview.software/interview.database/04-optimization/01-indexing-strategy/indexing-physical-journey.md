## 인덱스의 물리적 여정: 페이지 내부의 포인터부터 디스크 I/O까지

인덱스는 단순히 '색인'이 아닙니다. 엔지니어에게 인덱스는 **"어떻게 하면 디스크 헤더를 최소한으로 움직여 원하는 레코드를 16KB Page 안에 효율적으로 배치할 것인가"**에 대한 최적화 결과물입니다.

이 글에서는 MySQL InnoDB 엔진의 **B+Tree**가 물리적으로 어떻게 페이지를 관리하며, 무작위 PK가 성능에 미치는 물리적 실체를 분석합니다.

---

## 1. InnoDB 페이지(Page)의 내부 해부도

InnoDB의 최소 데이터 저장 단위는 **16KB(16,384 Bytes)** 크기의 페이지입니다. 이 페이지 하나가 B+Tree의 노드(Node) 하나가 됩니다.

### 1.1 물리적 구조

- **File Header (38 Bytes)**: 페이지 번호, 이전/다음 페이지 포인터 (Double Linked List 구성).
- **Page Header (56 Bytes)**: 페이지 상태, 레코드 개수, 계층 깊이 등.
- **User Records**: 실제 데이터 혹은 자식 노드의 주소.
- **Free Space**: 새로운 데이터가 들어갈 빈 공간.
- **Page Trailer (8 Bytes)**: 체크섬 정보를 통해 데이터 무결성 검증.

> **핵심 분석**: 페이지 안의 레코드는 물리적으로 정렬되어 저장되지 않습니다. 대신 Heap처럼 비어있는 공간에 순차적으로 쌓이고, **'Next Record' 포인터**를 통해 논리적으로만 연결됩니다. 즉, 페이지 안에서도 **연결 리스트(Linked List)**를 탐색하는 비용이 발생합니다.

---

## 2. B+Tree 탐색의 수학: 왜 Depth는 3~4 환경에 머무는가?

보통 인덱스 트리의 깊이(Height)가 3~4단계를 넘지 않는 이유는 다음과 같습니다.

- **계산**: 페이지당 약 1,000개의 인덱스 항목(16B 기준)을 담을 수 있다고 가정하면:
  - Depth 1 (Root): 1,000개 레코드
  - Depth 2: 1,000,000개 레코드
  - Depth 3: 1,000,000,000개 레코드 (10억 건)
- 대부분의 서비스는 **단 3~4번의 페이지 읽기(I/O)**만으로 10억 개의 데이터 중 단 하나를 찾아낼 수 있습니다.

## 3. 페이지 분할(Page Split)의 물리적 비용

인덱스 성능의 가장 큰 적은 무작위 삽입에 의한 **페이지 분할**입니다.

### 3.1 페이지 분할 프로세스

1. 엔진은 새로운 페이지를 할당받습니다.
2. 기존 페이지의 절반(50%)을 새 페이지로 복사합니다.
3. 이 과정에서 상위 노드(Parent)의 인덱스 정보도 갱신됩니다.
4. **결과**: 이 조정 과정에서 페이지 락(Index Latch)이 발생하며 동시성이 급격히 하락합니다.

### 3.2 실전 테스트: 무작위 UUID vs 순차 PK

```sql
-- 1. 순차 PK 테이블
CREATE TABLE users_sequential (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    name VARCHAR(100)
) ENGINE=InnoDB;

-- 2. 무작위 PK 테이블
CREATE TABLE users_random (
    id BINARY(16) PRIMARY KEY, -- UUID v4
    name VARCHAR(100)
) ENGINE=InnoDB;

-- 50만 건 삽입 후 메트릭 확인
SHOW ENGINE INNODB STATUS;
-- 'innodb_buffer_pool_reads' 지표 측정 결과
-- Random PK는 Sequential 대비 약 3~4배의 Disk Read 발생 (페이지 파편화 때문)
```

---

## 4. Fill Factor: 페이지의 가용 공간 확보

엔진 설정 중 `innodb_fill_factor`는 페이지가 분할되기 전 얼마나 데이터를 채울지 결정합니다.

- **기본값**: 대부분 100% (실제로는 1/16은 예약 공간).
- **최적화 전략**: 쓰기 위주의 테이블에서 이 값을 **80~90%**로 낮추면, 약간의 공간 낭비는 생기지만 페이지 분할 빈도를 줄여 쓰기 전체 응답 속도를 향상시킬 수 있습니다.

---

## 5. 결론

인덱스 설계 시 다음 세 가기 원칙을 준수해야 합니다.

1. **포인터 추적**: 랜덤 I/O는 성능의 적입니다. 한 페이지 안에 최대한 많은 정보를 담아야 합니다.
2. **PK의 순차성**: 이것은 설계 취향이 아니라 물리적 페이지 정렬을 위한 필수 조건입니다.
3. **통계 유지**: `OPTIMIZE TABLE`은 단순히 용량을 줄이는 게 아니라, 쪼개진 페이지들을 다시 병합하여 **인덱스 트리의 균형**을 맞추는 작업입니다.

다음 시간에는 이 물리적 토대 위에 쌓아 올리는 **커버링 인덱스(Covering Index)의 메모리 구조**를 분석합니다.
