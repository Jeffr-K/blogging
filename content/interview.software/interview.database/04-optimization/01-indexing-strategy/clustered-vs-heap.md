## 데이터 저장 아키텍처: MySQL vs PostgreSQL

가장 널리 쓰이는 두 오픈소스 RDBMS인 **MySQL(InnoDB)**과 **PostgreSQL**은 데이터를 물리적으로 저장하는 방식에서 근본적인 차이를 보입니다. MySQL은 데이터 자체가 인덱스의 일부인 **클러스터드 인덱스(Clustered Index)** 방식을, PostgreSQL은 데이터가 무작위로 저장되고 인덱스가 이를 가리키는 **힙 테이블(Heap Table)** 방식을 취합니다.

이 아키텍처의 차이가 왜 성능의 향방을 결정짓는지 그 내부 메커니즘을 분석합니다.

---

## 1. MySQL InnoDB: 클러스터드 인덱스 (Clustered Index)

MySQL(InnoDB)에서 테이블은 곧 **기본키(PK) 트리** 그 자체입니다.

- **물리적 정렬**: 실제 레코드가 PK 순서대로 디스크에 정렬되어 저장됩니다. PK로 조회 시 수백만 건 중에서도 단 몇 번의 I/O만으로 데이터 페이지에 도달할 수 있어 검색 속도가 매우 빠릅니다.
- **이차 인덱스(Secondary Index)의 구조**: 이차 인덱스는 실제 데이터 주소가 아닌 PK를 값으로 가집니다. 따라서 이차 인덱스로 검색 시 **(이차 인덱스 스캔 → PK 트리 스캔 → 데이터 도달)**이라는 **이중 작업(Double Lookup)**이 발생합니다.

---

## 2. PostgreSQL: 힙 테이블 (Heap Table)

PostgreSQL은 데이터가 들어오는 순서대로 아무 위치(Heap)에나 저장됩니다.

- **독립된 데이터 저장소**: 테이블 데이터(`Heap`)와 인덱스(`Index`)가 완전히 분리되어 있습니다. 모든 인덱스(PK 포함)는 해당 데이터의 물리적 주소인 **`ctid`**를 가리킵니다.
- **단일 룩업(Single Lookup)**: 어떤 인덱스로 검색하든 `ctid`를 얻어 바로 데이터에 접근합니다. MySQL과 같은 이중 스캔 구조가 아니므로 인덱스 구성이 상대적으로 자유롭습니다.

---

## 3. 성능적 트레이드오프 분석

### 3.1 삽입(Insert) 성능

- **MySQL**: PK 순서가 무작위인 경우(예: UUID v4), B+Tree를 계속 재정렬(Page Split)해야 하므로 삽입 성능이 급격히 저하됩니다. 반드시 순차적인 PK 설계(Auto-increment)가 수반되어야 합니다.
- **PostgreSQL**: 비어있는 페이지에 데이터를 즉시 삽입할 수 있어 삽입 속도가 상대적으로 빠르며 PK 설계의 제약이 덜합니다.

### 3.2 업데이트(Update) 성능

- **PostgreSQL**: MVCC(Multi-Version Concurrency Control) 방식 때문에 수정 시 기존 데이터를 지우고 새 데이터를 추가하는 `UPDATE = DELETE + INSERT` 방식을 취합니다. 잦은 업데이트 시 데이터 파편화가 발생하며 **VACUUM** 부하가 수반됩니다.
- **MySQL**: 인덱스 컬럼이 아닌 데이터만 수정할 경우, 인덱스 트리를 건드리지 않고 제자리에서 수정(Update-in-place)이 가능하여 대량 업데이트에 유리한 면이 있습니다.

---

## 4. 인덱스 온리 스캔 (Index-only Scan)

테이블 데이터에 접근하지 않는 최적화 기법에서도 두 엔진은 아키텍처에 따른 차이를 보입니다.

- **MySQL**: 클러스터드 인덱스 구조 덕분에 복합 인덱스 설계만 잘 되어 있다면 커버링 인덱스의 활용도가 매우 높습니다.
- **PostgreSQL**: 힙 테이블 구조에서는 데이터의 가시성(Visibility) 확인을 위해 테이블 접근이 필요할 수 있습니다. 이를 효율화하기 위해 **Visibility Map**이라는 추가 장치를 사용합니다.

---

## 5. 결론

엔진 아키텍처의 차이는 시스템의 병목 지점(Bottleneck)과 밀접하게 연관됩니다.

1. **MySQL (InnoDB)**: 대용량 읽기 성능이 핵심이고 PK 기반 조회가 빈번한 워크로드에 최적화되어 있습니다.
2. **PostgreSQL**: 복잡한 쿼리 처리, 다양한 인덱스 타입(GIN/GiST) 활용, 잦은 삽입이 발생하는 환경에서 강력한 성능을 발휘합니다. 단, 진공 청소(Vacuum) 프로세스 관리가 핵심입니다.

지금까지 인덱스의 물리적 구조와 아키텍처별 차이를 분석했습니다. 다음 테마는 쿼리의 실행 과정을 투명하게 공개하는 **실행 계획과 옵티마이저의 의사 결정**입니다.
