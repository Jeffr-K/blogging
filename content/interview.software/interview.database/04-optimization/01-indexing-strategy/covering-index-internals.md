## 커버링 인덱스: 테이블 액세스의 원천 차단

데이터베이스 성능을 저하시키는 가장 결정적인 요인은 인덱스 탐색 후 실제 데이터를 가져오기 위해 **데이터 페이지(Table Page)**에 추가로 접근하는 행위입니다. 이를 **ID 리드(ID Lookup)** 또는 **북마크 룩업(Bookmark Lookup)**이라 부릅니다.

만약 쿼리 수행에 필요한 모든 컬럼이 인덱스에 이미 포함되어 있다면, 엔진은 데이터 페이지에 접근할 필요가 없어집니다. 이것이 **커버링 인덱스(Covering Index)**의 핵심 원리입니다.

---

## 1. 테이블 액세스의 물리적 비용 분석

인덱스 리프 노드에는 인덱스 키와 함께 실제 데이터의 위치(PK 또는 Row ID)가 담겨 있습니다. 일반적인 조회 프로세스는 다음과 같습니다.

1. **Index Scan**: 인덱스 트리에서 조건에 맞는 키를 탐색합니다.
2. **Table Access (I/O)**: 찾은 PK를 기반으로 실제 데이터가 저장된 데이터 페이지를 디스크에서 읽어옵니다. (가장 높은 비용 발생)
3. **Data Return**: 결과셋을 클라이언트에게 반환합니다.

커버링 인덱스는 여기서 **2단계(Table Access)를 생략**합니다. 인덱스 페이지만 읽고 바로 결과를 반환하므로 물리적 I/O 횟수를 획기적으로 줄입니다.

---

## 2. 실행 계획 분석: Using index

MySQL `EXPLAIN` 결과의 `Extra` 필드에 **`Using index`**가 표시된다면 커버링 인덱스가 효율적으로 작동하고 있다는 의미입니다.

- **Using index**: 인덱스 리프 노드의 데이터만으로 쿼리를 완료함. (최고 속도)
- **Using index condition (ICP)**: 인덱스 조건으로 필터링을 시도하지만, 최종적으로는 테이블 접근이 필요함.

---

## 3. 실전 사례: 페이지네이션 최적화

대량의 게시판 데이터를 조회하는 페이지네이션에서 커버링 인덱스는 필수적입니다.

```sql
-- 1. 비효율적인 쿼리 (매 행마다 테이블 접근 발생)
SELECT * FROM posts ORDER BY created_at DESC LIMIT 100000, 20;

-- 2. 커버링 인덱스 최적화 (PK만 먼저 추출하여 접근 최소화)
SELECT * FROM posts p
JOIN (
  SELECT id FROM posts ORDER BY created_at DESC LIMIT 100000, 20
) as temp ON p.id = temp.id;
```

서브쿼리 내부에서 `ORDER BY`와 `LIMIT`이 인덱스만 타고(`Using index`) 수행되므로, 실제로 전체 데이터를 가져오기 위해 테이블에 접근하는 횟수는 단 20번으로 제한됩니다.

---

## 4. 인덱스 비대화 방지 및 트레이드오프

커버링 인덱스 구성을 위해 너무 많은 컬럼을 인덱스에 포함시키면 다음과 같은 부작용이 발생합니다.

- **저장 공간 비용**: 인덱스 크기가 비대해져 메모리(Buffer Pool) 효율이 저하됩니다.
- **DML 성능 저하**: 인덱스에 포함된 컬럼 수정 시 인덱스 트리 재구성이 필요하므로 `UPDATE` 성능이 하락합니다.

---

## 5. 결론

커버링 인덱스는 **테이블 접근을 물리적으로 차단하는 강력한 최적화 수단**입니다.

1. `EXPLAIN`에서 `Using index` 여부를 주기적으로 점검하십시오.
2. 자주 조회되는 핵심 컬럼들로 최적화된 복합 인덱스를 구성하십시오.
3. 인덱스 비대화를 막기 위해 반드시 필요한 컬럼만 선별하여 설계에 반영하십시오.

다음 아티클에서는 설계 난도가 가장 높은 **복합 인덱스(Composite Index)의 컬럼 순서 결정 논리**를 분석합니다.
