## 인덱스 컨디션 푸시다운: 엔진 간 통신 최적화

MySQL 5.6 버전부터 도입된 **인덱스 컨디션 푸시다운(ICP)**은 스토리지 엔진과 서버 엔진 사이의 데이터 전송 효율을 극대화하는 기능입니다. 이 기술은 데이터베이스의 **스토리지 엔진(InnoDB 등)**과 **MySQL 엔진(Server)** 사이의 물리적 데이터 전송량을 획기적으로 줄여줍니다.

이번 아티클에서는 ICP의 작동 메커니즘과 옵티마이저의 실행 계획을 강제로 교정하는 **인덱스 힌트(Index Hint)** 전략을 분석합니다.

---

## 1. ICP의 물리적 작동 원리 분석

복합 인덱스 `(last_name, first_name)`가 존재하고 다음과 같은 쿼리를 실행한다고 가정합니다.
`SELECT * FROM users WHERE last_name = 'Kim' AND first_name LIKE '%lee%';`

### 1.1 ICP 이전의 처리 방식
스토리지 엔진은 첫 번째 인덱스 조건인 `last_name = 'Kim'`에 해당하는 모든 레코드를 MySQL 엔진으로 전송합니다. 이후 MySQL 엔진은 전송받은 데이터를 하나씩 대조하며 `first_name LIKE '%lee%'` 조건을 필터링합니다. 이 과정에서 불필요한 데이터 전송 오버헤드가 발생합니다.

### 1.2 ICP 도입 이후의 처리 방식
MySQL 엔진은 `first_name`에 대한 필터링 조건까지 **스토리지 엔진으로 미리 전달(Pushdown)**합니다. 스토리지 엔진은 실제 데이터 행(Row)을 읽기 전에 인덱스 노드 내에서 두 조건을 모두 검증하고, 최종적으로 부합하는 결과만MySQL 엔진으로 전송합니다. 이를 통해 디스크 I/O와 엔진 간 데이터 전송 비용을 최소화합니다.

---

## 2. 실행 계획 확인: Using index condition

`EXPLAIN` 결과의 `Extra` 필드에 **`Using index condition`**이 나타난다면 ICP가 성공적으로 적용되고 있음을 의미합니다. 이는 단순한 `Using where`보다 스토리지 레벨에서 더 정교한 필터링이 이루어지고 있다는 기술적 증거입니다.

---

## 3. 인덱스 힌트: 옵티마이저 실행 경로 교정

옵티마이저는 데이터 통계 정보가 부정확하거나 쿼리가 복잡할 경우 비효율적인 인덱스를 선택할 수 있습니다. 이때 인덱스 힌트를 통해 실행 경로를 직접 통제할 수 있습니다.

- **`USE INDEX`**: 특정 인덱스 사용을 권장하지만, 옵티마이저가 더 낮은 비용의 경로를 발견하면 무시될 수 있습니다.
- **`FORCE INDEX`**: 옵티마이저의 비용 계산 결과를 무시하고 **강제로 특정 인덱스를 사용**하도록 명령합니다. 풀 테이블 스캔이 압도적으로 유리한 상황이 아니면 해당 인덱스를 강제 적용합니다.
- **`IGNORE INDEX`**: 특정 인덱스가 비효율적인 실행 계획을 유발할 때 검색 대상에서 제외시킵니다.

---

## 4. 인덱스 힌트 적용의 실전 기준

인덱스 힌트는 옵티마이저의 자동 최적화 능력을 제한하므로 신중하게 적용해야 합니다.

- **통계 정보 불일치**: 대규모 데이터의 급격한 유입으로 인해 엔진의 통계 정보가 실제 데이터 분포를 반영하지 못할 때.
- **조인 순서 오류**: 복잡한 다중 조인 상황에서 드라이빙 테이블(Driving Table) 선정이 잘못되어 쿼리 지연이 발생할 때.
- **인덱스 스캔 임계점 초과**: 인덱스 스캔 범위가 너무 넓어(보통 20~30% 이상) 오히려 풀 테이블 스캔이 물리적으로 유리함에도 인덱스를 고집하는 경우.

---

## 5. 결론

ICP는 **데이터 필터링 지점을 하위 엔진으로 전진시키는 기술**이며, 인덱스 힌트는 **엔진의 판단 오류를 물리적으로 교정하는 기술**입니다.

1. `EXPLAIN` 분석을 통해 ICP의 적용 여부를 확인하고 인덱스 스캔 효율을 극대화하십시오.
2. 인덱스 힌트는 최후의 수단으로 활용하되, 적용 후에는 데이터 분포 변화에 따른 정기적인 실행 계획 재검토가 수반되어야 합니다.
