## 데이터의 군살을 걷어내다: 정규화(Normalization)

데이터베이스를 설계할 때 모든 정보를 하나의 거대한 테이블에 무차별적으로 담으면, 데이터를 삽입, 삭제, 수정할 때 논리적 모순이 발생하는 **이상 현상(Anomaly)**을 마주하게 됩니다.

**정규화(Normalization)**는 이러한 이상 현상을 제거하기 위해 함수적 종속성(Functional Dependency)을 기반으로 테이블을 논리적인 최소 단위로 쪼개는 고도의 설계 전략입니다. 마스터 레벨에서 반드시 짚고 넘어가야 할 1정규형부터 BCNF까지의 정수를 전수합니다.

---

## 1. 정규화의 전제 조건: 함수적 종속성 (Functional Dependency)

정규화를 이해하려면 **'A가 B를 결정한다 (A -> B)'**는 함수적 종속성을 먼저 이해해야 합니다.

- **결정자(Determinant)**: 다른 속성 값을 고유하게 결정하는 속성 (예: 학번).
- **종속자(Dependent)**: 결정자에 의해 값이 정해지는 속성 (예: 이름).

> "학번(A)을 알면 이름(B)을 반드시 알 수 있다." 면 A -> B입니다. 이 관계가 꼬여있을 때 이상 현상이 발생합니다.

---

## 2. 제1정규형 (1NF): 속성의 원자성 (Atomicity)

**현상**: 하나의 컬럼에 여러 개의 값이 들어있거나(다중 값), 유사한 컬럼이 반복되는 경우.

### [위배 사례: 수강 신청 테이블]

| 학생ID | 이름 | 수강과목 |
| :--- | :--- | :--- |
| 101 | 김철수 | **수학, 과학, 영어** |

- **문제점**: '수학' 강좌를 듣는 학생을 조회하려면 쉼표로 구분된 문자열을 파싱해야 하며, 인덱스를 탈 수 없습니다.
- **1NF 해결**: 각 행은 하나의 원자 값(Atomic Value)만 가져야 합니다.

### [1NF 정규화 결과]

| 학생ID | 이름 | 수강과목 |
| :--- | :--- | : :--- |
| 101 | 김철수 | 수학 |
| 101 | 김철수 | 과학 |
| 101 | 김철수 | 영어 |

---

## 3. 제2정규형 (2NF): 부분 함수 종속성 제거

**현상**: 기본키가 복합키(A, B)일 때, 어떤 속성이 기본키 전체가 아닌 **일부(A 혹은 B)**에만 종속된 경우. (주로 M:N 관계의 교차 테이블에서 발생)

### [위배 사례: 강의 등록 테이블]

- 기본키: **(학생ID, 과목코드)**
- 일반 속성: 성적, **강의실 위치**

| 학생ID | 과목코드 | 성적 | 강의실 위치 |
| :--- | :--- | :--- | :--- |
| 101 | CS01 | A | 301호 |
| 102 | CS01 | B | **301호** |

- **문제점 (부분 종속)**: '강의실 위치'는 (학생ID, 과목코드) 전체가 아니라 **과목코드**에만 의존합니다. CS01 과목의 강의실이 바뀌면 모든 학생 행을 수정해야 하는 **수정 이상**이 발생합니다.
- **2NF 해결**: 부분 함수 종속성을 제거하여 별도의 테이블로 분리합니다.

### [2NF 정규화 결과]

- **성적 테이블**: (학생ID, 과목코드, 성적)
- **과목 정보 테이블**: (과목코드, 강의실 위치)

---

## 4. 제3정규형 (3NF): 이행적 함수 종속성 제거

**현상**: 기본키(PK)가 아닌 속성들끼리 종속 관계가 있는 경우. 즉, **A(PK) -> B -> C** 관계가 성립할 때.

### [위배 사례: 사원 테이블]

- 기본키: **사원번호**
- 일반 속성: 이름, **부서코드, 부서명**

| 사원번호 | 이름 | 부서코드 | 부서명 |
| :--- | :--- | :--- | :--- |
| E01 | 이영희 | D01 | 인사팀 |
| E02 | 박민수 | D01 | **인사팀** |

- **문제점 (이행 종속)**: 사원번호가 부서코드를 결정하고, 부서코드가 다시 부서명을 결정합니다. 부서명이 바뀌면 해당 부서의 모든 사원 행을 고쳐야 합니다. 만약 사원이 한 명도 없는 부서는 부서명 정보를 저장할 수 없는 **삽입 이상**도 발생합니다.
- **3NF 해결**: 이행적 관계인 (부서코드 -> 부서명)을 분리합니다.

### [3NF 정규화 결과]

- **사원 테이블**: (사원번호, 이름, 부서코드)
- **부서 테이블**: (부서코드, 부서명)

---

## 5. BCNF (보이스-코드 정규형): 결정자이자 후보키

**현상**: 3NF를 만족하지만, 모든 **결정자가 후보키**가 아닌 경우. 주로 복합키가 얽힌 상황에서 발생합니다.

### [위배 사례: 수강 교수 테이블]

- 기본키: **(학생ID, 과목명)**
- 결정 관계: **(학생ID, 과목명) -> 교수명**, **교수명 -> 과목명** (한 교수는 한 과목만 담당한다고 가정)

| 학생ID | 과목명 | 교수명 |
| :--- | :--- | :--- |
| 101 | 데이터베이스 | 강교수 |
| 102 | 데이터베이스 | **강교수** |
| 103 | 알고리즘 | 최교수 |

- **문제점**: '교수명'은 PK의 일부인 '과목명'을 결정하는 **결정자**이지만, 교수명 자체는 행을 식별할 수 있는 **후보키가 아닙니다**. 강교수가 퇴사하면 '데이터베이스'라는 과목 정보가 사라지는 **삭제 이상**이 발생합니다.
- **BCNF 해결**: 결정자인 '교수명'을 기준으로 테이블을 분해합니다.

### [BCNF 정규화 결과]

- **수강 테이블**: (학생ID, 교수명)
- **교수-과목 테이블**: (교수명, 과목명)

---

## 6. 마스터의 총평: 정규화의 물리적 트레이드오프

정규화는 데이터 무결성을 위한 신성한 과정이지만, 실무에서는 **조인(Join) 연산의 부하**라는 비용을 동반합니다.

1. **무결성 사수**: 3NF까지는 데이터 정합성을 위해 반드시 지켜야 할 '최소한의 가이드라인'입니다.
2. **연쇄 삭제 주의**: 테이블이 쪼개질수록 한쪽 데이터를 삭제할 때 연관된 수많은 테이블의 정합성을 체크해야 하는 오버헤드가 발생합니다.
3. **읽기 성능 vs 쓰기 성능**: 정규화는 중복을 제거해 쓰기/수정 성능을 높이지만, 조인을 유발해 읽기 성능을 떨어뜨립니다. 이 간극을 메우는 것이 바로 다음 장에서 다룰 **반정규화(Denormalization)** 전략입니다.

---

## 요약

| 정규형 | 핵심 해결 과제 | 주요 키워드 |
| :--- | :--- | :--- |
| **1NF** | 원자성 확보 | 다중 값 제거, 반복 그룹 제거 |
| **2NF** | 부분 함수 종속성 제거 | 복합키와 일반 속성의 관계 정립 |
| **3NF** | 이행적 함수 종속성 제거 | 비기본키 속성 간의 종속 제거 |
| **BCNF** | 결정자의 후보키화 | 결정자(Determinant)는 반드시 키여야 함 |

이제 정규화가 단순히 테이블을 쪼개는 기술이 아니라, 데이터 간의 권력 구조(함수 종속성)를 바로잡는 과정임을 이해했을 것입니다. 이 기초 위에 **4NF(다치 종속)**와 **5NF(조인 종속)**라는 더 깊은 심연으로 들어갈 준비가 되었습니다.
