## 정형의 감옥에서 벗어나기: 비정형 데이터

모든 데이터를 칼럼으로 만들 수는 없다. 사용자가 직접 추가하는 옵션, 제품마다 다른 상세 사양, 수시로 바뀌는 외부 API 응답 값 등 RDBMS의 정적인 스키마로는 감당하기 힘든 **비정형(Semi-structured) 데이터**들이 존재한다.

이를 위해 과거부터 쓰여온 **EAV(Entity-Attribute-Value)** 모델과 현대의 **JSONB** 기술은 상반된 철학을 가지고 있다. 이번 아티클에서는 두 방식의 설계 방식과 실무적 트레이드오프를 딥다이브해 본다.

---

## 1. 딥다이브: EAV (Entity-Attribute-Value) 모델

테이블 하나에 `엔티티ID`, `속성명`, `값` 세 줄만 가지고 모든 데이터를 표현하는 방식이다.

- **장점**: 어떤 새로운 속성이 추가되어도 테이블 스키마 변경(`ALTER TABLE`)이 아예 필요 없다. 극도로 유연하다.
- **단점: 조인(Join)의 지옥**: 사용자의 이름, 나이, 주소를 한 줄의 결과로 보고 싶다면, 한 테이블을 자기 자신과 세 번 조인해야 한다. 쿼리의 복잡도가 기하급수적으로 늘어나며 성능이 수직 낙하한다. (검색과 통계가 사실상 불가능하다.)

---

## 2. 현대적 대안: JSONB (Binary JSON)

PostgreSQL과 MySQL 8.0 등이 지원하는 타입으로, 하나의 칼럼에 JSON 형식의 데이터를 통째로 넣고 **인덱싱(GIN Index 등)**까지 입히는 방식이다.

- **장점**: 스키마리스(Schemaless)의 유연성을 RDBMS 안에서 누릴 수 있다. 복잡한 관계 없이 키-값 쌍의 데이터를 빠르게 조회할 수 있다.
- **단점**: 데이터 크기가 커지면 저장 공간을 많이 차지하고, 복잡한 비즈니스 로직(데이터 타입 검증 등)을 데이터베이스 차원에서 강제하기 어렵다.

---

## 3. 실전 가이드: 언제 무엇을 쓸까?

- **EAV**: 정적인 속성이 거의 없고, 수만 개의 동적 속성을 관리해야 할 때 (예: 의료 기록 시스템의 특정 파운드리 데이터).
- **JSONB**: 메인 속성은 칼럼으로 만들고, "기타 상세 옵션"이나 "외부 연동 데이터"처럼 부가적인 정보를 담을 때 (대부분의 사이드 프로젝트나 일반적인 커머스 옵션 체계에서 선호).

---

## 요약

비정형 데이터 모델링은 **"유연성과 성능 사이의 아슬아슬한 줄타기"**다.

- **EAV**는 설계의 끝판왕 같은 유연함을 주지만, 조인 쿼리의 지옥을 선사한다.
- **JSONB**는 현대적인 유연함을 제공하면서 인덱스로 성능까지 잡지만, 데이터 타입의 엄밀함은 포기해야 한다.
- 가급적 핵심 데이터는 **칼럼**으로 설계하고, 정말 예측 불가능한 영역만 **JSONB**로 처리하는 하이브리드 전략이 가장 현명하다.

계층 설계와 비정형 데이터 수용까지 마스터했다면, 이제 데이터의 시간이 흐르는 궤적을 기록하는 **이력 및 상태 데이터 관리(History & State Management)**의 지평을 탐구할 준비가 된 것이다!
