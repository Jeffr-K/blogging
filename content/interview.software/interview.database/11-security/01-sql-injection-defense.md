## SQL Injection 공격과 원천 봉쇄

데이터베이스 보안의 첫 번째 관문이자, 수십 년간 수많은 기업을 위기에 빠뜨린 고전적인 공격 방식이 바로 **SQL Injection**입니다. 이 문서에서는 공격의 원리를 파헤치고, 어떻게 개발 단계에서 이를 원천적으로 차단할 수 있는지 배웁니다.

---

### 1. 공격 원리의 핵심: "데이터를 명령어로 오해하게 만들기"

해커는 입력창에 단순한 아이디가 아니라, SQL 문법의 일부인 `' OR 1=1 --` 같은 문자열을 넣습니다. 서버가 이 입력을 검증 없이 쿼리에 합치면 어떤 일이 벌어질까요?

- **정상 쿼리**: `SELECT * FROM users WHERE id = 'user123'`
- **오염된 쿼리**: `SELECT * FROM users WHERE id = '' OR 1=1 --'`

`OR 1=1` 때문에 조건은 항상 참이 되고, 그 뒤의 구문은 `--`로 주석 처리됩니다. 결과적으로 모든 사용자 정보가 조회되거나 비밀번호 없이 로그인이 성공하는 참사가 일어납니다.

### 2. 필살기: 프리페어드 스테이트먼트 (Prepared Statements)

이 공격을 막는 가장 강력하고 확실한 방법입니다.

- **원리**: 쿼리의 '틀(Pre-compile)'을 미리 만들어 데이터베이스 엔진에 보냅니다. 그다음 사용자 데이터(Parameter)만 따로 보냅니다.
- **방어 기제**: 데이터베이스 엔진은 나중에 들어온 데이터를 무조건 '단순 문자열'로만 인식합니다. 아무리 악성 SQL 코드가 들어있어도 절대로 명령어로 실행하지 않습니다.

### 3. ORM의 함정과 주의점

현대 개발 환경에서 JPA, Hibernate, Sequelize 같은 ORM을 쓰면 기본적으로 인젝션 방어가 되지만, 방심은 금물입니다.

- **네이티브 쿼리 주의**: `em.createNativeQuery("... WHERE id = " + input)` 처럼 직접 하드코딩으로 문자열을 합치는 순간 방어막은 무너집니다.
- **동적 정렬(Order By)**: `ORDER BY` 절에는 파라미터 바인딩이 안 되는 경우가 많습니다. 이때 들어오는 입력값은 반드시 화이트리스트(허용된 컬럼명) 방식으로 검증해야 합니다.

---

### 결론

SQL 인젝션 방어는 "입력값을 잘 걸러내는 것(Filter)"이 아니라, **"쿼리와 데이터를 물리적으로 분리하는 것"**입니다. 모든 쿼리에서 Prepared Statements를 사용하는 습관을 들이는 것만으로도 서비스의 보안 수준은 비약적으로 상승합니다.
