## 복합 인덱스 심화 (Composite Index Mastery)

실무에서 가장 많이 실수하고, 또 가장 큰 성능 개선의 기회가 숨어 있는 곳이 바로 **복합 인덱스(Composite Index, Combined Index)**입니다. 컬럼 하나가 아닌 두 개 이상의 컬럼을 묶은 이 인덱스는, 설계 방식에 따라 마법 같은 속도를 내기도 하고 전혀 쓸모없는 쓰레기 데이터로 전락하기도 합니다.

무엇이 이 차이를 만드는지, 서술형으로 아주 상세하게 파헤쳐 보겠습니다.

---

## 1. 정렬의 곱셈 법칙을 이해하라

복합 인덱스 `(A, B, C)`를 만들었다는 것은, 데이터가 다음 순서로 물리적 정렬이 이루어진다는 뜻입니다.

1. 먼저 **A 컬럼**을 기준으로 전체 데이터가 정렬됩니다.
2. A값이 같은 행들 사이에서만 **B 컬럼** 기준으로 정렬됩니다.
3. A와 B가 모두 같은 행들 사이에서만 **C 컬럼** 기준으로 정렬됩니다.

이것이 인덱스의 동작 원리인 **'가장 왼쪽 매칭 법칙(Leftmost Prefix Rule)'**이 생겨난 근본적인 이유입니다. 만약 A를 건너뛰고 B만으로 검색하려고 하면, B는 인덱스 전체에 흩어져 있기 때문에 인덱스를 탈 수 없게 됩니다.

## 2. 복합 인덱스 설계의 필살기 3원칙

### 1) 등호(=)가 부등호(>, <)보다 앞서야 한다

이것은 매우 중요한 원칙입니다. `status = 'SHIPPING'`과 `order_date > '2024-04-01'` 두 조건을 사용한다면 인덱스는 무조건 `(status, order_date)` 순이어야 합니다.

- 만약 `(order_date, status)` 순으로 만들면? `order_date`로 범위를 필터링한 뒤에는 `status`가 정렬되어 있지 않기 때문에 인덱스 효율이 급격히 떨어집니다.
- **결론**: 정확히 일치하는 조건(Point Lookup)을 앞쪽에, 범위 조건(Range Lookup)을 뒤쪽에 배치하십시오.

### 2) 카디널리티(Cardinality)의 함정에 빠지지 마라

"중복도가 낮은(카디널리티가 높은) 컬럼을 앞에 두라"는 조언을 많이 듣습니다. 이는 단일 인덱스일 때는 100% 맞지만, 복합 인덱스일 때는 상황에 따라 다릅니다.

- **예시**: `주민번호`와 `성별` 컬럼이 있을 때, 쿼리가 항상 `성별 = '남' AND 주민번호 = '...'` 형태로 들어온다면 `(성별, 주민번호)`도 나쁘지 않습니다. 어차피 두 컬럼이 모두 조회 조건에 포함된다면 어느 쪽이 앞이든 엔진은 데이터를 잘 찾아냅니다.
- 하지만 쿼리가 유연하게 들어온다면, 더 많은 데이터 군집을 한 번에 날려버릴 수 있는 주민번호를 앞에 두는 것이 범용성 면에서 압도적으로 유리합니다.

### 3) ORDER BY와 GROUP BY를 활용하라

인덱스는 '정렬' 그 자체입니다. 인덱스 순서와 동일하게 `ORDER BY`를 사용하면 데이터베이스는 별도의 정렬 작업(Sort Merge, Quick Sort 등) 없이 인덱스 스캔만으로 결과를 반환합니다. 실무에서 상위 10개의 최신 글을 가져오는 기능 등이 느리다면, 대부분 인덱스 순서와 정렬 순서가 맞지 않기 때문입니다.

## 3. DBMS별 실전 사례 (MySQL vs PostgreSQL)

### 사례: "최근 한 달간 특정 상태의 주문 중 결제 금액이 큰 순서대로 조회"

- **비효율적인 인덱스**: `(order_date, status, total_price)`
  - 날짜 범위가 먼저 나오면 그 뒤의 정렬 상태가 무의미해집니다.
- **최적의 인덱스**: `(status, order_date, total_price)`
  - 상태를 등호(=)로 고정하고, 그 안에서 날짜 범위를 찾고, 이미 정렬된 금액순으로 결과를 뽑아냅니다.

- **MySQL Syntax**:

    ```sql
    CREATE INDEX idx_status_date_price ON orders (status, order_date DESC, total_price DESC);
    ```

- **PostgreSQL Syntax**:

    ```sql
    CREATE INDEX idx_status_date_price ON orders (status, order_date DESC, total_price DESC);
    ```

## 4. 인덱스 설계자가 흔히 하는 실수

1. **너무 많은 컬럼을 묶는 것**: 컬럼이 5~6개 넘어가는 거대한 복합 인덱스는 관리가 힘들고 쓰기 성능을 파괴합니다. 꼭 필요한 검색 조건 위주로 타이트하게 구성해야 합니다.
2. **중복 인덱스 생성**: `(A, B)` 인덱스가 있는데 `(A)` 인덱스를 또 만드는 것은 공간 낭비입니다. 인덱스 브라우징만으로도 A의 조건은 처리가 가능하기 때문입니다.

복합 인덱스는 데이터 사이의 **'위계 질서'**를 잡는 일입니다. 사용자의 쿼리 패턴을 종이에 적어보고, 어떤 조건이 먼저 오고 어떤 조건이 범위를 좁히는지 수학적으로 시뮬레이션해 보십시오. 그 정성이 깃든 인덱스 하나가 수천만 건의 데이터를 춤추게 할 것입니다.
