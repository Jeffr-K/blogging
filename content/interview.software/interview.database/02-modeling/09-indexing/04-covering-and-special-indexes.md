## 특수 인덱스와 최적화 기법

인덱스의 기본을 익혔다면, 이제는 서비스 성능을 한 단계 끌어올릴 수 있는 '필살기' 같은 기술들을 배울 차례입니다. 데이터베이스별로 특화된 고급 인덱싱 기법들은 수천만 건의 데이터 속에서 마법 같은 퍼포먼스를 보여줍니다.

---

## 1. 커버링 인덱스 (Covering Index): "인덱스만 보고 대답하기"

모든 인덱스 튜닝의 끝판왕은 결국 **커버링 인덱스**입니다.

### 핵심 원리

데이터베이스 엔진이 쿼리를 처리할 때 가장 비싼 작업은 '인덱스에서 찾은 주소로 실제 테이블(디스크)을 다시 뒤져보는 것'입니다.

- 만약 쿼리가 요구하는 컬럼이 인덱스 자체에 모두 포함되어 있다면?
- 엔진은 테이블 데이터를 아예 열어보지도 않고 인덱스 트리의 리프 노드만 보고 결과를 반환합니다.
- 이를 **Index Only Scan**이라고 부릅니다.

### 실무 활용

- `SELECT id, status FROM orders WHERE user_id = 100`이라는 쿼리가 잦다면?
- 인덱스를 단순히 `(user_id)`가 아니라 `(user_id, status)` 또는 `(user_id, status, id)`로 구성합니다. (MySQL InnoDB는 PK가 자동으로 포함되므로 `(user_id, status)`면 충분합니다.)
- 디스크 I/O가 획기적으로 줄어들어 속도가 수십 배 빨라집니다.

---

## 2. 부분 인덱스 (Partial Index / Filtered Index)

모든 행을 인덱싱하면 리소스 낭비가 심할 때가 있습니다. (예: 수억 건의 주문 중 '취소된 건'은 0.1%인데, 이 취소 건만 검색할 때)

### PostgreSQL의 강점

PostgreSQL은 `WHERE` 조건을 붙인 인덱스를 지원합니다.

```sql
-- 배송 전 상태(READY)인 데이터만 인덱스에 담습니다.
CREATE INDEX idx_ready_orders ON orders (user_id) WHERE status = 'READY';
```

- **장점**: 인덱스 크기가 매우 작고, 삽입/삭제 시 인덱스 업데이트 오버헤드도 최소화됩니다.

---

## 3. 표현식 인덱스 (Expression/Functional Index)

데이터를 가공해서 검색할 때(예: 소문자 검색, 날짜 가공) 인덱스가 안 먹히는 문제를 해결합니다.

### 문제 상황

```sql
-- 이 쿼리는 인덱스가 있어도 못 탑니다. 컬럼이 LOWER() 함수로 감싸졌기 때문입니다.
SELECT * FROM users WHERE LOWER(email) = 'hong@test.com';
```

### 해결책

- **PostgreSQL**:

    ```sql
    CREATE INDEX idx_lower_email ON users (LOWER(email));
    ```

- **MySQL (8.0+)**:

    ```sql
    ALTER TABLE users ADD INDEX ((LOWER(email)));
    ```

- 가공된 값 자체를 인덱스 트리에 미리 계산해서 저장해두므로 검색 시 즉시 매칭됩니다.

---

## 4. 인덱스 포기(Skip)와 브린(BRIN) 인덱스

### Index Skip Scan (MySQL 8.0, PG 15+)

- `(A, B)` 복합 인덱스가 있을 때, A 조건 없이 B만 조회해도 인덱스를 지능적으로 건너뛰며 사용하는 기술입니다. A의 카디널리티가 낮을 때 효과적입니다.

### BRIN (Block Range Index) - PostgreSQL 전용

- 시간 순서대로 쌓이는 거대 데이터(로그, 히스토리)에 최적화된 인덱스입니다.
- 수만 개의 행을 하나로 묶어 '최소값 ~ 최대값' 범위 정보만 저장합니다.
- 용량은 B+Tree의 1%도 안 되면서, 거대 테이블의 범위 검색 성능을 획기적으로 개선합니다.

---

## 5. 결론: 언제 어떤 인덱스를 쓸 것인가?

- **조회하는 컬럼이 적고 빈도가 압도적이다**: 커버링 인덱스를 설계하세요.
- **특정 조건(예: 활성 사용자)만 검색한다**: 부분 인덱스를 고려하세요.
- **가공된 데이터로 검색한다**: 표현식 인덱스가 정답입니다.
- **거대한 시계열 데이터를 보관한다**: BRIN 인덱스를 검토하세요.

인덱스는 무조건 많이 거는 것이 아니라, 엔진의 특성과 데이터의 성격을 매칭시키는 정교한 **전략 게임**입니다. 당신의 쿼리 분석 결과에 따라 가장 강력한 무기를 선택하시길 바랍니다.
