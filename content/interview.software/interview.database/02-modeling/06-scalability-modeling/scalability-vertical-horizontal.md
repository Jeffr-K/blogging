## 성벽을 높일 것인가, 영토를 넓힐 것인가?

데이터베이스가 거대해질 때 우리는 두 가지 갈림길에 선다. 테이블의 칼럼(Column)을 쪼개어 페이지 효율을 높일 것인가, 아니면 레코드(Row)를 여러 서버로 찢어 부하를 분산할 것인가.

이 두 방식은 각각 **수직적 분할(Vertical Partitioning)**과 **수평적 분할(Sharding)**이라 불리며, 대규모 시스템 설계의 정수와 같은 기술이다. 이번 아티클에서는 두 물리적 분사 방식의 설계 철학과 실무적 선택 기준을 딥다이브해 본다.

---

## 1. 딥다이브: 수직적 분할 (Vertical Partitioning)

테이블의 칼럼을 성격에 따라 나누어 독립적인 테이블로 분리하는 방식이다.

- **왜 하는가?**: 레코드 하나가 너무 비대해지면 한 페이지(16KB)에 담을 수 있는 행의 수가 줄어든다. 이는 디스크 I/O를 폭발적으로 늘린다.
- **설계 전략**: 자주 검색되는 핵심 칼럼(Hot Column)과 가끔 보는 상세 정보 칼럼(Cold Column)을 분리하라.
- **장점**: 페이지 밀도가 높아져서 검색 성능이 비약적으로 향상된다.

---

## 2. 딥다이브: 수평적 분할 (Sharding)

데이터 열(Row)을 기준으로 조각내어 아예 다른 물리적 서버로 보내버리는 방식이다.

- **왜 하는가?**: 단일 하드웨어의 CPU, 메모리, 네트워크 대역폭만으로는 더 이상 트래픽과 데이터를 감당할 수 없을 때 최후의 수단으로 선택한다.
- **설계 전략**: 데이터를 고르게 분산시킬 샤드 키(Shard Key)를 정교하게 선정하라 (예: `user_id % 4`).
- **장점**: 물리적 자원의 무한 확장이 가능하여, 구글이나 카카오 같은 대규모 서비스를 지탱하는 근간이 된다.

---

## 3. 실무의 고충: 샤딩(Sharding)의 대가

- **조인 실종**: 샤딩된 테이블끼리는 직접 조인(Join)할 수 없다. 필요한 데이터를 애플리케이션 계층에서 각각 가져와 합치거나, 중복 데이터를 모든 서버에 복제해야 한다.
- **트랜잭션 지옥**: 여러 서버의 데이터를 동시에 수정할 때, 원자성(Atomic)을 보장하기 위한 분산 트랜잭션 오버헤드가 매우 크다.

---

## 4. 실전 가이드: 단계별 확장 전략

1. **최적화**: 먼저 인덱스를 튜닝하고 쿼리를 개선하라.
2. **수직 분할**: 너무 넓은 테이블을 의미 단위로 쪼개어 I/O 효율을 높여라.
3. **파티셔닝**: 단일 서버 안에서 물리적 파일을 쪼개어 아카이빙 효율을 높여라.
4. **수평 분할(샤딩)**: 위의 모든 과정을 거쳤음에도 부하가 몰릴 때, 비로소 서버를 분리하라.

---

## 요약

물리적 분할은 **"시스템의 숨구멍을 틔워주는 고도의 수술"**이다.

- `수직 분할`로 한 페이지에 더 많은 데이터를 욱여넣어 I/O를 절감하자.
- `수평 분할(샤딩)`로 물리적 한계를 정면 돌파하자.
- 분할 시 잃게 되는 조인과 트랜잭션의 편의성을 애플리케이션 설계로 보완할 준비를 철저히 하자.

이 분할의 대전제를 이해했다면, 이제 MySQL과 같은 엔진에서 물리적 저장 순서를 좌우하는 **인덱스 친화적인 PK 선정의 정교함**을 딥다이브하며 본 테마를 마무리한다!
