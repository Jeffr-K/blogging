## 물리적 모델링: 논리를 넘어 하드웨어의 한계에 도전하기

논리적 모델링이 "데이터를 중복 없이 정교하게 쪼개는 것"에 집중했다면, **물리적 모델링(Physical Modeling)**은 그 쪼개진 데이터들을 실제 디스크와 메모리라는 물리적 환경 위에 **"어떻게 가장 빠르게 배치할 것인가"**를 결정하는 단계입니다.

여기서부터는 이론적인 정규화의 규칙을 잠시 내려두고, **디스크 I/O**, **CPU 연산 비용**, **메모리 캐시 히트율**이라는 현실 세계의 물리 법칙을 설계에 반영해야 합니다. 기술전수자로서, 데이터베이스의 성능을 결정짓는 최후의 1% 디자인을 전수하겠습니다.

## 1. [Physical Depth] 스토리지 엔진의 선택: InnoDB의 물리적 실체

대부분의 MySQL 환경에서 **InnoDB**를 쓰지만, 왜 그래야 하는지 물리적 이유를 알아야 합니다.

- **클러스터드 인덱스(Clustered Index)**: `InnoDB` 는 데이터를 PK(기본키) 순서대로 물리적으로 정렬하여 저장합니다. 이는 PK 기반 조회가 곧 `물리적 최단 경로` 임을 뜻합니다.
- **MVCC (Multi-Version Concurrency Control)**: 읽기와 쓰기가 서로를 방해하지 않도록 Undo Log를 관리하는 방식입니다.
- **Buffer Pool**: 디스크의 16KB 페이지를 메모리에 캐싱하여 I/O를 최소화하는 핵심 장치입니다.

> ![info] MVCC (Multi-Version Concurrency Control)
>
> "내가 읽는 동안 누가 수정해도, 나는 **과거의 깨끗한 데이터(Snapshot)**를 본다." 는 전략 입니다. 기존 방식은 누군가 데이터를 수정 중이면 다른 사람은 읽지 못하게 막았습니다(Lock). 하지만 MVCC는 Undo Log라는 '과거 기록 저장소'를 활용해 이를 해결합니다.
>
> 동작 원리:
>
> 1. A가 잔액: 100원을 200원으로 수정하기 시작합니다.
> 2. DB는 기존의 100원 데이터를 Undo Log에 복사해둡니다.
> 3. 이때 B가 잔액을 조회하면, 수정 중인 200원이 아니라 Undo Log에 있는 **100원**을 읽어갑니다.
>
> 장점: 읽기(Read)와 쓰기(Write)가 서로를 기다릴 필요가 없습니다. 성능이 비약적으로 향상되죠.
> 단점: Undo Log를 관리해야 하므로 추가적인 저장 공간이 필요합니다.
> 팁: 트랜잭션 격리 수준(Isolation Level) 및 격리 수준(Isolation Level)에 따라 어떤 버전의 데이터를 보여줄지 결정합니다.

> ![info] Buffer Pool
>
> "DB 전용 메모리 캐시 영역. 모든 데이터는 여기서 놀다가 가끔씩 디스크로 나간다." 는 전략입니다. DB 입장에서 디스크(SSD/HDD)는 너무 느린 거북이입니다. 그래서 메모리(RAM)의 일부를 Buffer Pool이라는 거대한 바구니로 할당해 데이터를 미리 담아둡니다.
>
> 동작 원리:
>
> 1. 조회: 데이터가 필요하면 디스크로 바로 안 가고 Buffer Pool을 먼저 뒤집니다. 있으면 대박(Cache Hit), 없으면 디스크에서 16KB 단위(Page)로 통째로 들고 와서 여기에 담습니다.
> 2. 수정: 데이터를 수정할 때도 디스크를 바로 안 고칩니다. Buffer Pool에 있는 페이지만 수정(Dirty Page)하고 끝냅니다.
> 3. Flush: 나중에 DB가 여유로울 때 수정된 내용들을 모아서 한꺼번에 디스크에 씁니다.
>
> 팁: `innodb_buffer_pool_size`는 MySQL 성능 튜닝의 1순위 설정값입니다. 보통 서버 메모리의 **50~80%**를 여기에 할당하죠.

`Buffer Pool` 덕분에 실제 데이터 파일로 가는 I/O를 획기적으로 줄여서 속도를 잡고, `MVCC` 덕분에 여러 사용자가 동시에 접근해도 Lock 없이 데이터를 주고받는 동시성을 잡습니다. 이것이 바로 InnoDB가 현대 웹 서비스의 표준이 된 이유입니다.

### [실전 가이드] 엔진 선택의 기준

| 서비스 성격 | 추천 엔진 | 이유 |
| :--- | :--- | :--- |
| **일반 웹 서비스 (OLTP)** | **InnoDB** | 트랜잭션 보장(ACID), 행 단위 잠금(Row-level Lock). |
| **대량 로그 수집 (Write Heavy)** | **RocksDB / LSM-Tree** | 압축률이 높고 순차 쓰기에 최적화된 엔진. |
| **읽기 전용 마스터 데이터** | **MyISAM** | 트랜잭션은 없으나 구조가 단순하여 읽기 성능이 매우 빠름. (특수 케이스) |

## 2. 데이터 타입 선정의 '한 끗' 차이

칼럼의 데이터 타입을 정하는 것은 단순히 저장 공간을 아끼는 것이 아니라, **하나의 데이터 페이지(16KB)에 몇 개의 행을 담을 수 있는가**를 결정하는 전략적 선택입니다.

### 2.1 정수형 타입 (Integer)

- `TINYINT` (1 Byte), `INT` (4 Bytes), `BIGINT` (8 Bytes).
- **💡 전수자의 조언**: 사용자 수가 가파르게 성장할 서비스의 PK는 고민하지 말고 `BIGINT`를 선택하십시오. `INT`의 21억 건 한계는 생각보다 금방 찾아옵니다. 하지만 상태(Status) 값이나 카테고리 ID라면 `TINYINT`를 써서 인덱스 크기를 절반으로 줄여야 합니다.

### 2.2 문자열 타입 (VARCHAR vs CHAR)

- **VARCHAR**: 실제 길이만큼만 저장 (공간 절약). 하지만 갱신 시 데이터가 커지면 **'Row Migration(행 이동)'** 발생 가능.
- **CHAR**: 고정 길이 저장. 공간 낭비는 있으나 업데이트 시 데이터 위치가 고정되어 오버헤드가 적음. (예: MD5 해시값, 고정 코드)

### [물리적 페이지 점유 계산식]

```text
페이지 크기(16,384) - 헤더(약 120) / (평균 레코드 크기) = 한 페이지당 담을 수 있는 행 수
레코드 크기가 200B면 약 80행, 400B면 40행으로 급감함. 
I/O 횟수는 정확히 2배 늘어남.
```

## 3. 인덱스 설계의 물리적 매커니즘

인덱스는 공짜가 아닙니다. **"성능을 위해 쓰기 비용을 미리 지불하는 보험"**입니다.

### 3.1 클러스터드 인덱스 (Clustered Index)

- 테이블당 단 하나만 존재할 수 있는 물리적 정렬 순서입니다.
- **주의**: PK가 무작위(UUID 등)라면, 새로운 데이터가 삽입될 때마다 기존 페이지의 중간을 비우고 밀어내는 **페이지 분할(Page Split)**이 발생하여 시스템이 마비될 수 있습니다.

### 3.2 보조 인덱스 (Secondary Index)

보조 인덱스는 리프 노드에 실제 데이터 주소(ROWID)가 아닌 **부모(Clustered Index)의 PK 값**을 저장합니다.

- **설계 이유**: 데이터 수정으로 인해 레코드의 물리적 위치가 바뀌더라도, 모든 보조 인덱스를 일일이 수정하지 않고 PK 값만 유지하여 **인덱스 관리 오버헤드를 최소화**하기 위함입니다.
- **동작 방식**: 보조 인덱스 탐색 후 PK를 획득하고, 이 PK로 다시 클러스터드 트리를 탐색하는 **더블 룩업(Double Lookup)**이 발생합니다.
- **커버링 인덱스(Covering Index)**: 조회하려는 모든 컬럼이 인덱스 내에 포함된 상태로, 더블 룩업 과정을 완전히 생략하여 성능을 극대화합니다.

```sql
-- 인덱스: (user_id, status)
SELECT user_id, status FROM Orders WHERE user_id = 10;
```

위 쿼리는 인덱스 페지만 보고 결과를 바로 돌려줍니다. 메인 테이블(클러스터드 인덱스)로 갈 필요가 없으니 성능이 몇 배는 빠릅니다. 실행 계획(EXPLAIN)에서 `Using index`라고 뜨면 이 상태입니다.

### 3.3 [실무 FAQ] PK 설계와 확장성 가이드

**Q. 초기 설계 시 INT 대신 BIGINT를 사용해야 하는 물리적 이유는 무엇입니까?**

1. **용량 한계**: `INT`(21억 건) 한계는 일일 500만 건 트래픽 발생 시 약 1.2년(420일) 내에 도달하며, 초과 시 서비스가 마비됩니다.
2. **마이그레이션 비용**: 운영 중 PK 타입을 변경하려면 데이터 전체 복사와 인덱스 재구성을 유발하여 막대한 다운타임(Downtime)을 발생시킵니다.
3. **정밀도 일관성**: 자바의 `Long`과 DB의 `BIGINT`를 매핑하여 데이터 오버플로우를 사전에 방어하십시오.

**Q. 비즈니스 고유값이 있는데 왜 별도의 인공 키(Surrogate Key)를 쓰나요?**

- **변경 유연성**: 이메일 등 자연 키는 정책에 따라 바뀔 위험이 큽니다. PK 변경은 참조하는 모든 FK 테이블의 수정을 유발하므로 불변하는 BIGINT id를 PK로 삼는 것이 정석입니다.
- **조인 효율**: 긴 문자열을 FK로 사용하면 인덱스 크기가 비대해져 조인 성능이 급감합니다.

### 3.4 [Portfolio Tip] 면접관을 사로잡는 엔티티 설계

**[위험한 설계: Integer 사용]**

```java
@Entity
public class Member {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Integer id; // 🚩 위험: 최대 21억까지만 수용 가능
}
```

**[권장 설계: Long 사용]**

```java
@Entity
public class Member {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id; // ✨ 정답: BIGINT 매핑으로 안정성 확보

    @Column(unique = true, length = 100)
    private String email;
}
```

- **면접 답변**: "MySQL InnoDB에서 PK 타입 변경은 테이블 전체 복사를 유발하므로, 초기 설계 단계부터 확장성을 고려하여 BIGINT 대응 타입인 Long을 선택했습니다."
- **추가 기술**: 무작위 UUID는 물리적 삽입 순서를 뒤흔들어 **페이지 분할(Page Split)**을 유발하여 삽입 성능을 저하시킵니다.

## 4. [Interview Master] 반정규화(Denormalization)의 결정적 순간

논리 모델러가 쪼개놓은 테이블을 다시 합치는 결단입니다.

### 4.1 반정규화를 해야 하는 상황

1. **조인 성능 한계**: 3개 이상의 거대 테이블이 조인되어 CPU 점유율이 90%를 넘을 때.
2. **반복적인 집계 쿼리**: 합계나 카운트를 위해 매번 수백만 건을 스캔해야 할 때.

### [반정규화 실전 사례: 주문상품 테이블에 상품명 중복 저장]

```sql
-- 논리 모델: 주문상품(item_id, order_id, product_id, count)
-- 물리 모델: 주문상품(item_id, order_id, product_id, product_name, count) -- product_name 중복 추가

/* 
  장점: 상품명을 보기 위해 Product 테이블을 조인할 필요 없음.
  위험: 상품명이 바뀌면? (다행히 이커머스에서 주문 시점의 상품명은 변하지 않는 스냅샷이어야 함)
*/
```

## 5. [Deep Dive] 물리적 파티셔닝(Partitioning)

데이터가 수억 건을 넘어가면 인덱스조차 무거워집니다. 이때는 데이터를 물리적 파일 단위로 쪼겁니다.

### 5.1 범위 파티셔닝 (Range Partitioning)

- 주문 날짜를 기준으로 월별로 쪼개는 방식입니다.

```sql
CREATE TABLE orders (
    id INT NOT NULL,
    order_date DATETIME NOT NULL,
    ...
) PARTITION BY RANGE (YEAR(order_date)) (
    PARTITION p2023 VALUES LESS THAN (2024),
    PARTITION p2024 VALUES LESS THAN (2025),
    PARTITION pmax VALUES LESS THAN MAXVALUE
);
```

- **효과**: 2023년 주문만 조회하면 p2023 파일만 열어봅니다 (**Partition Pruning**). I/O가 1/N로 줄어듭니다.

## 6. [전수자의 가이드] 물리 모델링의 5가지 황금률

1. **인공 키(PK)의 순차성을 사수하라**: 무작위 키는 디스크 단편화의 주범이다.
2. **데이터 타입은 '다이어트' 하라**: 작을수록 메모리에 더 많은 데이터를 담는다.
3. **조인은 최소화하되, 무결성은 지켜라**: 반정규화 데이터는 동기화 전략(Trigger, Batch)을 반드시 세워라.
4. **인덱스의 개수를 제한하라**: 인덱스가 5개 이상이면 INSERT 성능이 급격히 떨어진다.
5. **NULL을 가급적 피해라**: `NOT NULL` 설정은 엔진이 인덱스와 데이터를 최적으로 읽게 돕는 힌트가 된다.
