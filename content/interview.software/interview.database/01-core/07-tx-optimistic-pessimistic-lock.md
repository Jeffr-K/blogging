## 낙관적 락과 비관적 락: 자원 경합 해결의 두 가지 전략

데이터베이스 기반의 동시성 제어(Concurrency Control)에서 핵심 과제는 데이터 무결성을 보장하면서도 시스템의 처리량(Throughput)을 최대화하는 것입니다. 이를 위해 개발자는 자원 충돌의 빈도와 비즈니스 정합성의 중요도에 따라 낙관적(Optimistic) 또는 비관적(Pessimistic) 전략을 선택하게 됩니다.

## 1. Pessimistic Lock (비관적 락): "아무도 믿지 않는다"

비관적 락은 데이터에 접근하는 시점에 즉시 **배타적 잠금(Exclusive Lock)**을 거는 방식입니다. "내가 데이터를 수정하는 동안 누군가 반드시 이 데이터를 건드릴 것이다"라고 비관적으로 가정합니다.

### 1.1 물리적 구현: `SELECT ... FOR UPDATE`

데이터베이스 엔진 차원에서 특정 행(Row)에 락을 겁니다. 다른 트랜잭션은 해당 행에 대한 읽기(S-Lock)나 쓰기(X-Lock)를 시도할 때 대기 상태(Wait)에 빠집니다.

```sql
-- Transaction A 시작
START TRANSACTION;
SELECT * FROM inventory WHERE product_id = 100 FOR UPDATE; -- 락 획득
-- 비즈니스 로직 수행 (재고 차감 등)
-- ...
COMMIT; -- 락 해제
```

### 1.2 비관적 락의 장단점

- **장점**: 데이터 무결성을 DB 레이어에서 100% 보장합니다. 충돌이 잦은 환경에서 롤백 비용을 아낄 수 있습니다.
- **단점**: 동시성이 크게 떨어집니다. 대기가 길어지면 트랜잭션 타임아웃이나 **데드락(Deadlock)**의 위험이 상존합니다.

---

## 2. Optimistic Lock (낙관적 락): "나중에 확인하자"

낙관적 락은 실제 DB에 락을 걸지 않습니다. 대신 **버전(Version)**이나 **타임스탬프**를 활용하여 데이터 수정 시점에 충돌 여부를 확인합니다. "설마 내가 수정하는 짧은 시간 동안 다른 누군가 건드리겠어?"라고 낙관적으로 가정합니다.

### 2.1 물리적 구현: 버전 관리 (Versioning)

애플리케이션 레벨에서 구현되는 것이 일반적입니다. (예: JPA `@Version`)

```sql
-- 1. 데이터 조회 (Version 포함)
SELECT id, balance, version FROM accounts WHERE id = 1; -- version: 5

-- 2. 비즈니스 로직 수행 (balance 계산)
-- ...

-- 3. 업데이트 시점에 버전 체크
UPDATE accounts 
SET balance = 900, version = 6 -- 현재 버전을 하나 올림
WHERE id = 1 AND version = 5; -- 조회했을 때의 버전과 일치하는지 확인

-- 4. 결과 처리
-- 업데이트된 행의 개수가 0이라면, 누군가 중간에 버전을 가로챘음을 의미 (OptimisticLockException 발생)
```

### 2.2 낙관적 락의 장단점

- **장점**: DB에 실제 락을 걸지 않으므로 동시 처리 성능이 매우 우수합니다. 락 점유로 인한 병목이 없습니다.
- **단점**: 충돌이 발생했을 때의 뒤처리가 번거롭습니다. (재시도 로직 구현 필요)

---

## 3. 동시성 제어 전략의 선택 기준

성능과 데이터 정밀도 사이의 트레이드오프를 고려한 가이드라인은 다음과 같습니다.

### 비관적 락 권장 케이스 (High Conflict)

1. **재고 시스템**: 한정판 상품 판매와 같이 짧은 시간에 동일 레코드에 대한 수정 요청이 폭주하여 충돌 시 재시도 비용이 매우 높을 때.
2. **핵심 금융 도메인**: 데이터 오차 발생 시의 리스크가 크고, 대기(Wait)가 발생하더라도 확실한 순차 처리가 보장되어야 할 때.

### 낙관적 락 권장 케이스 (Low Conflict)

1. **조회 위주 서비스**: 조회 빈도가 압도적으로 높고 수정 충돌 확률이 낮은 대합실 형태의 게시판 등.
2. **독립적 자원 관리**: 사용자 개인 프로필과 같이 소유자 본인만 수정하여 충돌 가능성이 낮은 도메인.

## 4. [Deep Dive] 데드락(Deadlock)의 물리적 진단

비관적 락을 남발하면 마주하게 되는 재앙이 바로 데드락입니다.

### 데드락 발생 시나리오

- 트랜잭션 1: A를 잠그고 B를 잠그려 함.
- 트랜잭션 2: B를 잠그고 A를 잠그려 함.
- 결과: 두 트랜잭션이 서로를 기다리며 영원히 무한 대기.

### [실전 대응법]

1. **정렬된 접근**: 모든 트랜잭션이 자원(A, B)을 항상 같은 순서로 잠그도록 설계하십시오. (가장 효과적인 예방법)
2. **락 타임아웃 설정**: `innodb_lock_wait_timeout`을 짧게 설정하여 시스템 전체가 마비되는 것을 방지하십시오.
3. **낙관적 락으로의 전환**: 데드락이 빈번하다면 비즈니스 모델을 낙관적 락이나 대기열(Queue) 기반의 메시징 시스템으로 전환하는 것을 고려하십시오.

## 5. [Architecture] 분산 환경에서의 락 (Distributed Lock)

DB가 한 대가 아니라 여러 대로 찢어졌거나, 여러 인스턴스가 하나의 자원을 바라볼 때는 DB 자체의 락만으로 부족합니다.

- **Redis Redlock**: 메모리 기반의 초고속 분산 락.
- **Zookeeper**: 고가용성을 보장하는 강력한 분산 조정 시스템.
- **Etcd**: 분산 키-값 저장소를 활용한 락.

---

## 6. 동시성 제어의 설계 원칙

효율적인 락 설계를 위한 세 가지 핵심 원칙입니다.

1. **트랜잭션 수명 최소화**: 락을 점유하는 시간(Lock Duration)을 최소로 유지하여 자원 대기 행렬을 줄여야 합니다.
2. **조회 성능 보호**: MVCC를 활용하여 조회 작업이 쓰기 작업에 의해 블로킹되지 않도록 설계하십시오.
3. **충돌 빈도 기반 전환**: 실제 운영 환경의 충돌 메트릭을 분석하여, 필요 이상으로 강한 비관적 락은 낙관적 락이나 메시지 큐 기반의 비동기 처리로 전환을 고려하십시오.

### [락 비교 요약표]

| 항목 | 비관적 락 (Pessimistic) | 낙관적 락 (Optimistic) |
| :--- | :--- | :--- |
| **잠금 시점** | 데이터 조회(Read) 시점 | 데이터 수정(Update) 시점 |
| **물리적 장소** | 데이터베이스 엔진 | 애플리케이션 코드 |
| **주요 기술** | `SELECT ... FOR UPDATE` | 버전(Version), 타임스탬프 |
| **동시성** | 낮음 (대기 발생) | 높음 (락 프리) |
| **적합한 곳** | 충돌 빈도가 잦은 핵심 자원 | 충돌 빈도가 거의 없는 일반 자원 |

다음 아티클에서는 이러한 락들이 실제 인덱스의 구조 위에 어떻게 안착되는지, **인덱스의 종류와 내부 동작 원리**를 전수하겠습니다.
