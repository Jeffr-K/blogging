## 데이터베이스 조인 알고리즘: 물리적 연산의 메커니즘 분석

관계형 데이터베이스에서 조인(Join)은 논리적으로 테이블을 합치는 과정이지만, 물리적으로는 메모리와 CPU 보드 위에서 수많은 데이터 페이지를 대조하는 일련의 알고리즘입니다. 옵티마이저가 수립하는 실행 계획의 핵심은 **"어떤 조인 알고리즘을 사용하여 I/O 비용을 최소화할 것인가"**에 집중됩니다.

이 글에서는 현대 데이터베이스 엔진이 사용하는 주요 조인 알고리즘의 물리적 동작 원리와 메모리 관리 방식을 분석합니다.

---

## 1. Nested Loop Join (NLJ)

가장 고전적인 방식이자, 인덱스가 잘 설계된 OLTP(Online Transaction Processing) 시스템에서 가장 선호되는 방식입니다.

### 1.1 기본 동작 원리

외부 테이블(Outer Table / Driving Table)의 각 행을 하나씩 순회하며, 내부 테이블(Inner Table / Driven Table)에서 조건을 만족하는 행을 찾는 방식입니다.

- **Nested Loop**: 이중 `for` 루프와 동일한 시간 복잡도를 가집니다 (`O(N * M)`).

### 1.2 성능 최적화: Index Nested Loop Join

내부 테이블의 조인 칼럼에 인덱스가 있을 때의 동작입니다.

1. 외부 테이블의 행을 하나 읽습니다.
2. 해당 행의 조인 키를 사용하여 내부 테이블의 **B+Tree 인덱스를 탐색**합니다.
3. 인덱스 리프 노드에서 데이터 위치를 찾아 즉시 접근합니다.

- **결과**: 내부 테이블 전체를 스캔하지 않고 `log M` 수준의 탐색만 수행하므로 매우 빠릅니다.

### 1.3 Block Nested Loop Join (BNL)

내부 테이블에 인덱스가 없을 때 사용되는 고육지책입니다.

- **Join Buffer**: 외부 테이블의 행들을 메모리상의 조인 버퍼에 가득 채운 뒤, 내부 테이블을 한 번 풀 스캔하며 버퍼 내의 행들과 대조합니다.
- **효과**: 내부 테이블의 풀 스캔 횟수를 외부 테이블 행 수만큼이 아닌, `외부 테이블 페이지 수 / 조인 버퍼 크기`만큼으로 줄여줍니다.

## 2. Hash Join (해시 조인)

MySQL 8.0.18 버전부터 도입된 현대적인 알고리즘으로, 대량의 데이터를 인덱스 없이 조인할 때 NLJ보다 압도적인 성능을 냅니다.

### 2.1 Build Phase (해시 테이블 생성)

1. 두 테이블 중 크기가 더 작은 테이블(Build Input)을 선택합니다.
2. 조인 키를 해시 함수에 통과시켜 **메모리상의 해시 테이블**을 구축합니다.

### 2.2 Probe Phase (탐색)

1. 나머지 테이블(Probe Input)을 행 단위로 읽습니다.
2. 조인 키를 동일한 해시 함수에 통과시켜 메모리상의 해시 테이블 버킷에 접근합니다.
3. 값이 일치하면 조인 결과에 포함합니다.

### 2.3 Grace Hash Join (메모리 부족 시)

해시 테이블이 가용 메모리(`join_buffer_size`)를 초과하면, 데이터를 여러 개의 파티션(Partition)으로 나누어 디스크에 임시 저장한 뒤 개별적으로 처리합니다. 이때 발생하는 디스크 I/O가 성능 저하의 주원인이 됩니다.

## 3. Sort Merge Join (정렬 병합 조인)

주로 인덱스가 없거나 데이터가 너무 커서 해시 테이블을 만들기 어려울 때, 혹은 이미 데이터가 정렬되어 있을 때 사용됩니다.

### 3.1 동작 과정

1. **Sort**: 두 테이블을 조인 칼럼 기준으로 각각 정렬합니다. (이미 인덱스에 의해 정렬되어 있다면 생략)
2. **Merge**: 두 테이블의 포인터를 가장 앞줄에 두고 시작합니다.
   - 양쪽 값이 같으면 결과에 포함하고 두 포인터를 모두 이동합니다.
   - 한쪽 값이 작으면 해당 포인터만 다음 행으로 이동합니다.
3. **결과**: 단 한 번의 전체 스캔(Scan)으로 모든 조인이 완료됩니다.

---

## 4. [Analysis] 옵티마이저는 어떻게 결정하는가?

옵티마이저는 비용 기반 모델(Cost-based Optimizer)을 사용하여 알고리즘을 선택합니다.

- **인덱스 활용도**: 인덱스가 있다면 99% 확률로 **Index NLJ**를 선택합니다.
- **데이터 크기**: 인덱스가 없고 데이터가 크다면 **Hash Join**을 우선순위에 둡니다.
- **메모리 가용성**: 해시 조인이 효율적이라 판단되어도 메모리가 너무 부족하다면 **Sort Merge Join**이 강제될 수 있습니다.

### [물리적 알고리즘 비교 테이블]

| 알고리즘 | 시간 복잡도 | 메모리 요구량 | 주요 특징 |
| :--- | :--- | :--- | :--- |
| **NLJ** | `O(N * log M)` | 매우 낮음 | 인덱스 필수, OLTP 최적화 |
| **Hash Join** | `O(N + M)` | 높음 (BuildInput 크기) | 비정규화된 대량 데이터 처리 |
| **Merge Join** | `O(N log N + M log M)` | 낮음/중간 | 대량 데이터 병합, 정합성 위주 |

---

## 5. 실무에서의 성능 트러블슈팅

1. **인덱스 누락(Index Miss)**: 실행 계획(Execution Plan)에서 `BNL`이나 `Hash Join`이 너무 자주 보인다면, 조인 칼럼의 인덱스 설계를 재점검해야 합니다. (DW 환경이 아닌 일반 API 서버라면)
2. **조인 순서의 역전**: `STRAIGHT_JOIN` 힌트를 사용하여 옵티마이저가 잘못 판단한 드라이빙 테이블 순서를 강제로 조정해야 하는 경우도 있습니다.
3. **메모리 설정**: `join_buffer_size`가 너무 작으면 Hash Join의 Grace 단계(Disk I/O)가 빈번해져 쿼리가 초 단위로 느려질 수 있습니다.

---

## 6. 결론: 알고리즘의 이해가 쿼리 튜닝의 시작이다

조인 쿼리가 느려졌을 때 단순히 "데이터가 많다"고 치부하지 마십시오. **NLJ가 인덱스를 못 타고 있는지, Hash Join이 메모리 부족으로 디스크 파티셔닝을 하고 있는지** 그 물리적 증상을 구별해내는 것이 엔지니어의 통찰력입니다.

쿼리에 적절한 인덱스를 부여하고, 메모리 임계점을 관리하며, 옵티마이저가 최적의 경로를 찾도록 돕는 것이 데이터베이스 아키텍처 설계의 본질입니다.
