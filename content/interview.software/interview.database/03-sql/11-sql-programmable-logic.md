## Programmable SQL: 데이터베이스 내부의 로직 엔진

관계형 데이터베이스(RDBMS)는 단순한 저장소를 넘어 스스로 연산하고 판단하는 프로그래밍 환경을 제공합니다. SQL은 기본적으로 선언적이지만, **저장 프로시저(Stored Procedure)**와 **트리거(Trigger)**를 통해 절차적인 제어 흐름(Loop, IF-ELSE)과 이벤트 기반 자동화를 구현할 수 있습니다.

비즈니스 로직을 애플리케이션 서버와 데이터베이스 중 어디에 배치할 것인가는 시스템 성능과 유지보수에 결정적인 영향을 미칩니다. 이들의 아키텍처적 특성을 분석합니다.

---

## 1. 저장 프로시저(Stored Procedure)의 물리적 이점

애플리케이션 서버에서 수많은 쿼리를 날려 데이터를 가공하는 대신, DB 내부에서 바로 실행되는 프로시저는 다음과 같은 물리적 이점을 가집니다.

### 1.1 네트워크 트래픽 절감

애플리케이션 서버와 DB 서버 사이의 거대한 데이터 전송(Network Round-trip)을 최소화합니다. 수만 건의 행을 읽어 로직을 태워야 할 때, 결과값만 애플리케이션에 전달하므로 네트워크 대역폭을 획기적으로 아낍니다.

### 1.2 실행 계획의 재사용

프로시저는 최초 한 번 컴파일되어 DB 엔진의 실행 계획 캐시에 저장됩니다. 매번 쿼리를 파싱하고 최적화하는 오버헤드를 줄여 응답 속도를 향상시킵니다.

---

## 2. 트리거(Trigger)의 정합성 보장

트리거는 특정 테이블에 `INSERT`, `UPDATE`, `DELETE` 이벤트가 발생할 때 자동으로 실행되는 로직입니다.

### 2.1 감사 로그(Audit Log)와 데이터 동기화

데이터의 변경 이력을 남기거나, 특정 칼럼의 변경에 따라 연관 테이블의 합계 값을 자동으로 갱신할 때 사용됩니다. 애플리케이션 개발자가 로그 기록을 누락하더라도 DB 엔진 차원에서 반드시 실행되므로 **최후의 무결성 보루** 역할을 합니다.

---

## 3. 아키텍처적 트레이드오프: 로직을 어디에 둘 것인가?

많은 시니어 개발자들은 "상태를 가진 DB에는 로직을 최소화하라"고 조언합니다. 그 이유는 다음과 같습니다.

### 3.1 확장의 어려움 (Scalability)

애플리케이션 서버는 인스턴스를 수평 확장(Scale-out)하기 쉽지만, 데이터베이스는 확장이 훨씬 어렵고 비용이 많이 듭니다. DB가 복잡한 연산까지 수행하게 되면 전체 시스템의 병목 지점이 될 위험이 큽니다.

### 3.2 버전 관리와 테스트의 불편함

절차적인 PL/SQL 소스 코드는 형상 관리(Git)와 단위 테스트(Unit Test)를 수행하기에 애플리케이션 코드보다 훨씬 까다롭습니다. 로직이 파편화되면 디버깅이 어려워집니다.

---

## 4. 실전 가이드: 프로그래밍 SQL을 사용해야 할 때

1. 일괄 처리(Batch Process): 대량의 데이터 정제 작업처럼 네트워크 비용이 성공을 결정짓는 경우.
2. 강력한 보안: 민감한 데이터에 대해 애플리케이션이 직접 접근하지 못하게 하고, 검증된 프로시저만을 통해서만 호출을 허용해야 할 때.
3. 공유 로직: 서로 다른 언어(Node.js, Python, Java 등)로 구현된 여러 서비스가 동일한 복잡한 데이터 조작 규칙을 공유해야 할 때.

---

## 5. Programmable SQL 운영 수칙

1. 루프 최적화 필수: 프로시저 내부의 커서(Cursor)를 통한 행 단위 루프는 성능의 적입니다. 가급적 집합 기반 연산으로 대체하십시오.
2. 트리거 연쇄 반응 주의: 트리거가 다른 트리거를 호출하고, 그것이 다시 원래 테이블을 건드릴 때 발생하는 순환 호출은 시스템을 즉시 다운시킵니다.
3. 예외 처리(Exception Handling): 로직 실패 시의 롤백 전략을 명확히 정의하여 데이터가 중간 지점에서 꼬이지 않도록 설계합니다.
