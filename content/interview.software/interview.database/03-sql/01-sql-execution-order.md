## SQL 실행 순서: 문법 너머의 논리적 흐름

우리는 보통 `SELECT`로 시작하여 `ORDER BY`로 끝나는 쿼리를 씁니다. 하지만 데이터베이스 엔진은 우리가 쓴 순서대로 쿼리를 읽지 않습니다.

SQL의 논리적 실행 순서(Logical Query Processing Order)를 파헤칩니다. 이 순서를 모르면 `SELECT`에서 정의한 별칭(Alias)을 왜 `WHERE` 절에서 쓸 수 없는지, 왜 `HAVING`이 `WHERE`보다 느린지 이해할 수 없습니다. 이 딥다이브를 통해 쿼리 성능 최적화의 첫 걸음을 떼어 봅시다.

---

## 1. SQL 논리적 실행 순서 10단계

데이터베이스 엔진이 쿼리를 처리하는 실제 순서는 다음과 같습니다. 이 순서를 머릿속에 '지도'처럼 그려야 합니다.

1. **FROM**: 조회할 테이블을 먼저 지정합니다 (Join 포함).
2. **ON**: 조인 조건을 확인합니다.
3. **JOIN**: 테이블 간의 결합을 수행하여 가상 테이블을 만듭니다.
4. **WHERE**: 행 단위로 조건을 필터링하여 데이터를 걸러냅니다.
5. **GROUP BY**: 필터링된 데이터를 특정 기준에 따라 그룹화합니다.
6. **HAVING**: 그룹화된 결과물에 대해 다시 필터링을 수행합니다.
7. **SELECT**: 어떤 칼럼을 보여줄지 결정합니다 (이때 계산식이나 함수가 동작).
8. **DISTINCT**: 중복된 결과 행을 제거합니다.
9. **ORDER BY**: 결과물을 특정 순서로 정렬합니다.
10. **LIMIT / OFFSET**: 보여줄 행의 개수와 시작점을 제한합니다.

---

## 2. 각 단계별 상세 분석과 성능의 분수령

### 2.1 FROM & JOIN (The Entry Point)

쿼리의 시작은 언제나 **소스(Source)**를 찾는 것입니다.

- 여기서 가장 큰 오버헤드는 **카르테시안 곱(Cartesian Product)**입니다. 조인 조건이 잘못되면 데이터가 기하급수적으로 불어나 엔진이 멈출 수 있습니다.
- **💡 팁**: `FROM` 절에서 서브쿼리를 쓰는 `Inline View`는 가급적 피하고, 필요하다면 `CTE(With)`를 활용하여 가독성과 범위를 명확히 하십시오.

### 2.2 WHERE vs HAVING (The Filtering)

- **WHERE**: 데이터가 그룹화되기 **전**에 행을 버립니다. 물리적으로 인덱스를 탈 수 있는 유일한 필터링 지점입니다.
- **HAVING**: 데이터가 모두 그룹화된 **후**에 필터링합니다. 이미 메모리에 올라온 데이터를 전수 조사하므로, `WHERE`로 처리할 수 있는 조건을 `HAVING`에 넣는 것은 최악의 안티패턴입니다.

### [실전 예시: 왜 WHERE가 더 빠른가?]

```sql
-- 나쁜 사례 (그룹화 후 전체 필터링)
SELECT category_id, COUNT(*)
FROM products
GROUP BY category_id
HAVING category_id > 10;

-- 좋은 사례 (필터링 후 그룹화)
SELECT category_id, COUNT(*)
FROM products
WHERE category_id > 10
GROUP BY category_id;
```

두 쿼리의 결과는 같습니다. 하지만 좋은 사례는 인덱스를 통해 10 이하의 카테고리는 읽지도 않고 넘어가므로 성능 차이가 수백 배 날 수 있습니다.

## 3. SELECT는 왜 7단계인가?

가장 뒤늦게 실행되는 `SELECT`의 특성 때문에 발생하는 현상이 있습니다.

### 별칭(Alias) 사용의 금약

```sql
SELECT (price * count) AS total_price
FROM orders
WHERE total_price > 10000; -- 컴파일 에러! 
```

**이유**: `WHERE`(4단계) 시점에는 `total_price`(7단계)라는 이름이 아직 존재하지 않습니다. 엔진은 "그런 칼럼은 없다"고 답할 것입니다.
반면, `ORDER BY`(9단계)에서는 `total_price`를 마음껏 쓸 수 있습니다.

---

## 4. ORDER BY의 물리적 비용: Filesort

`ORDER BY`는 엔진에게 가장 고통스러운 작업 중 하나입니다.

- **Index 정렬**: 이미 인덱스가 정렬되어 있다면 거저먹는 작업입니다.
- **Filesort**: 인덱스가 없다면 엔진은 임시 공간(Sort Buffer)에 데이터를 옮기고 수작업으로 정렬을 수행합니다. 데이터가 많으면 디스크까지 써야 하는 이 작업은 쿼리를 느리게 만드는 주범입니다.

## 5. SQL 키워드 총정리 (Keywords A-Z)

실무에서 자주 쓰이는 핵심 키워드들의 의미와 주의사항을 전수합니다.

- **DISTINCT**: 중복을 제거할 때 내부적으로 **정렬**이나 **해싱(Hashing)**을 수반합니다. 성능 저하의 원인이 될 수 있으니 꼭 필요한 경우에만 쓰십시오.
- **EXISTS vs IN**:
  - `IN`은 서브쿼리의 결과를 모두 메모리에 올린 뒤 비교합니다.
  - `EXISTS`는 조건에 맞는 행을 하나라도 찾으면 즉시 멈춥니다. 대용량 데이터 조회 시 `EXISTS`가 훨씬 효율적입니다.
- **UNION vs UNION ALL**: `UNION`은 중복을 제거하기 위해 내부적으로 정렬을 하지만, `UNION ALL`은 그냥 붙입니다. **무조건 `UNION ALL`을 우선 고려하십시오.**

## 7. 정리하며: 결코 잊지 말아야 할 체크리스트

| 키워드 | 실행 순서 | 특징 및 주의점 |
| :--- | :---: | :--- |
| **FROM** | 1 | 데이터의 근원지. 드라이빙 테이블 선정이 관건 |
| **WHERE** | 4 | 인덱스를 활용할 수 있는 마지막 보루 |
| **GROUP BY** | 5 | 집계 함수를 쓰기 위한 물리적 묶음 |
| **HAVING** | 6 | 그룹에 대한 조건. `WHERE`와 철저히 구분할 것 |
| **SELECT** | 7 | 가공 및 별칭 부여. 성능엔 큰 영향 없음 |
| **ORDER BY** | 9 | 정렬 비용 발생. 가급적 인덱스 정렬 활용 |

다음 아티클에서는 가장 난도가 높고 면접의 단골인 **조인(Join)의 종류와 내부 동작 원리(Nested Loop Join 등)**를 분석하겠습니다.
