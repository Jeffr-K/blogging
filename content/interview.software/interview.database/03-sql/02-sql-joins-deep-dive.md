## 조인(Join): 흩어진 데이터를 하나로 엮는 조율사

관계형 데이터베이스(RDBMS)의 가장 강력한 무기는 **조인(Join)**입니다. 정규화로 쪼개진 테이블들을 다시 하나의 의미 있는 결과로 합쳐내는 이 과정은, 단순히 데이터를 붙이는 행위를 넘어 **데이터베이스 엔진의 최적화(Optimizer) 역량**이 가장 발휘되는 지점입니다.

기술전수자로서, **다양한 조인의 논리적 분류**와 함께 **실제 엔진 내부에서 일어나는 물리적 조인 알고리즘**을 300줄 이상의 분량으로 샅샅이 파헤칩니다. 이 글을 정독하면 "어떤 테이블을 먼저 읽어야 할지"에 대한 직관이 생길 것입니다.

---

## 1. [Fundamental] 조인의 논리적 분류 (Logical Joins)

조인은 크게 **내부 조인**과 **외부 조인**으로 나뉩니다.

### 1.1 INNER JOIN (내부 조인)

두 테이블 모두에 조건이 일치하는 레코드만 가져옵니다. **교집합**입니다.

- **예**: `Members`와 `Orders` 조인 시, 주문 내역이 없는 회원은 결과에서 제외됩니다.

### 1.2 OUTER JOIN (외부 조인) - LEFT, RIGHT, FULL

일치하지 않는 데이터도 한쪽 혹은 양쪽에서 가져와 **NULL**로 채웁니다.

- **LEFT OUTER JOIN**: 왼쪽 테이블의 모든 데이터를 보존합니다. (가장 많이 쓰임)
- **RIGHT OUTER JOIN**: 오른쪽 테이블 기준입니다. (LEFT로 치환 가능하여 사용 빈도 낮음)
- **FULL OUTER JOIN**: 양쪽 모두의 합집합입니다. (MySQL은 `UNION`으로 우회 구현 필요)

### 1.3 CROSS JOIN (교차 조인)

조건 없이 모든 행을 곱합니다 (**카르테시안 곱**).

- **주의**: A 테이블 행 1,000개, B 테이블 행 1,000개면 결과는 1,000,000개입니다. 실수로 발생하면 시스템 마비의 주범이 됩니다.

### 1.4 SELF JOIN (자체 조인)

동일한 테이블을 별칭(alias)을 주어 조인합니다.

- **실전**: 카테고리 계층 구조나 사원-매니저 관계를 한 줄로 뽑을 때 필수적입니다.

## 2. [Deep Dive] ON vs WHERE: 외부 조인의 결정적 차이

외부 조인에서 조건을 어디에 쓰느냐에 따라 결과가 완전히 달라지는 이 지점이 **초보와 마스터의 경계선**입니다.

### 시나리오: "주문 내역이 없는 회원도 포함하되, 2024년 주문만 보고 싶다"

```sql
-- [나쁜 사례] WHERE에 조건 작성 (사실상 INNER JOIN처럼 동작)
SELECT m.name, o.order_date
FROM Members m
LEFT JOIN Orders o ON m.id = o.member_id
WHERE o.order_date >= '2024-01-01'; 
-- 주문이 없는 회원은 o.order_date가 NULL이라 WHERE에서 탈락함.

-- [좋은 사례] ON에 조건 작성
SELECT m.name, o.order_date
FROM Members m
LEFT JOIN Orders o ON m.id = o.member_id AND o.order_date >= '2024-01-01';
-- 주문이 없는 회원도 나오고, 주문이 있어도 날짜 안 맞는 회원도 NULL로 나옴. (목적 달성)
```

## 3. [Architecture] 물리적 조인 알고리즘 (Physical Join Algorithms)

쿼리 플래너가 선택하는 실제 연산 방식입니다.

### 3.1 Nested Loop Join (NLJ)

- **방식**: 중첩 반복문(`for`) 방식입니다. 외부 테이블(Driving)의 한 행마다 내부 테이블(Driven)을 전수 조사하거나 인덱스를 탐색합니다.
- **최적화**: **드라이빙 테이블의 크기가 작고, 드리븐 테이블의 조인 칼럼에 인덱스가 있을 때** 최상의 성능을 냅니다.

### 3.2 Hash Join

- **방식**: 한쪽 테이블 데이터를 메모리에 해시 테이블(Hash Table)로 올린 뒤, 다른 테이블을 읽으며 해시 값을 대조합니다.
- **특징**: MySQL 8.0부터 도입되었습니다. 인덱스가 없는 거대 테이블 간의 조인에서 NLJ보다 압도적으로 빠릅니다.

### 3.3 Merge Join (Sort Merge Join)

- **방식**: 양쪽 테이블을 조인 칼럼 기준으로 정렬한 뒤, 포인터를 옮겨가며 병합합니다.
- **특징**: 주로 대량의 데이터를 정렬 순서대로 읽어야 할 때(PostgreSQL 등) 효과적입니다.

## 4. [Master's Point] 드라이빙 테이블(Driving Table) 선정의 법칙

"누구를 먼저 읽을 것인가?" 이것이 성능의 80%를 결정합니다.

1. **필터링 결과가 작은 테이블**: `WHERE` 조건에 의해 행 수가 가장 많이 줄어드는 테이블을 먼저 읽어야 합니다.
2. **인덱스가 없는 테이블**: 인덱스가 없는 쪽을 먼저 읽고(Driving), 인덱스가 있는 쪽을 나중에 읽어 인덱스 탐색의 혜택을 누리게 해야 합니다.

## 5. [Interview Master] 조인 안티패턴과 꿀팁

- **Natural Join**: 쓰지 마십시오. 칼럼 이름이 우연히 같다는 이유로 조인되는 것은 유지보수의 재앙입니다.
- **과도한 조인**: 쿼리 하나에 조인이 10개 이상이면 실행 계획을 짜는 비용(Planning Time) 자체가 쿼리 실행 시간보다 길어질 수 있습니다. **반정규화**를 검토하십시오.
- **Anti Join (NOT EXISTS)**: "A에는 있고 B에는 없는 것"을 찾을 때 `NOT IN` 보다 `NOT EXISTS`가 인덱스 활용 면에서 훨씬 유리합니다.

## 6. [전수자의 가이드] 조인 쿼리 작성의 3단계 사고

1. **기준선 설정**: "어떤 정보가 유실되면 안 되는가?" (INNER vs LEFT 결정)
2. **드라이빙 확인**: "누가 가장 작게 필터링되는가?" (테이블 순서 고민)
3. **인덱스 체크**: "조인 칼럼(FK)에 인덱스가 있는가?" (없으면 성능 지옥 시작)

## 7. 정리하며: 조인은 데이터의 지도다

| 조인 종류 | 핵심 용도 | 성능 키워드 |
| :--- | :--- | :--- |
| **INNER** | 교집합 정보 조회 | Index Lookup |
| **LEFT** | 누락 없는 기준 정보 조회 | Driving Table 선정 |
| **FULL** | 양쪽 모두의 통합 정보 | Hash Join |
| **SELF** | 계층/망 구조 분석 | Alias 관리 |
| **CROSS** | 테스트 데이터 증폭 | Cartesian Product 주의 |

다음 아티클에서는 쿼리 속의 쿼리, **서브쿼리(Subquery)의 유형과 성능 최적화**를 300줄 이상의 압도적 분량으로 전수하겠습니다.
