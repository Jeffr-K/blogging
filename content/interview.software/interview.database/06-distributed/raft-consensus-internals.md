## 분산 합의(Consensus): 혼돈 속의 질서 확립

여러 노드가 독립적으로 작동하는 분산 환경에서 "지금 현재 데이터의 상태는 무엇인가?"에 대해 모든 노드가 동의를 얻는 것은 매우 어려운 과제입니다. 특히 일부 노드가 장애로 중단되거나 네트워크 지연이 발생할 때, 시스템의 일관성을 유지하기 위한 물리적 합의 과정이 필요합니다.

그중 **Raft** 알고리즘은 이해하기 쉽고 구현이 명확하여 현대 분산 데이터베이스(Etcd, CockroachDB 등)의 핵심 합의 엔진으로 채택되고 있습니다. 본 아티클에서는 Raft가 리더를 선출하고 데이터를 전파하는 물리적 메커니즘을 분석합니다.

---

## 1. Raft의 세 가지 논리적 상태 (Role)

Raft 클러스터 내의 각 노드는 언제나 다음 세 가지 상태 중 하나를 유지합니다.

1.  **Leader (리더)**: 클라이언트의 모든 요청을 수락하고 로그 복제를 지휘하는 단 하나의 실무 결정권자입니다.
2.  **Follower (팔로워)**: 리더의 지시를 수동적으로 수락하고 로그를 기록하는 노드입니다. 리더로부터 주기적인 생존 신호(Heartbeat)를 받습니다.
3.  **Candidate (후보자)**: 리더가 죽었다고 판단될 때, 새로운 리더가 되기 위해 선거를 제안하는 임시 상태입니다.

---

## 2. 리더 선출(Leader Election): 선거의 물리적 절차

리더 선출은 **임기(Term)**라는 논리적 시간 단위를 기준으로 수행됩니다.

1.  **Timeout 발생**: 팔로워가 일정 시간(Election Timeout) 동안 리더의 Heartbeat를 받지 못하면, 자신의 상태를 `Candidate`로 전환합니다.
2.  **투표 요청**: 후보자는 다른 노드들에게 "내가 새로운 리더가 되고 싶으니 투표해달라"는 요청(RequestVote RPC)을 보냅니다.
3.  **과반수 획득(Quorum)**: 클러스터 노드의 과반수(n/2 + 1) 이상의 찬성표를 얻은 후보자가 해당 임기(Term)의 새로운 `Leader`로 등극합니다.
4.  **권위 증명**: 새로운 리더는 즉시 다른 노드들에게 Heartbeat를 보내 자신의 통치를 선포하고 선거를 종료시킵니다.

---

## 3. 로그 복제(Log Replication): 데이터 정합성의 사수

리더는 클라이언트로부터 받은 쓰기 요청을 다음 단계에 거쳐 모든 노드에 확정(Commit)시킵니다.

1.  **Append Entries**: 리더는 로컬 로그에 데이터를 먼저 쓰고, 팔로워들에게 해당 데이터를 복제하라고 명령합니다.
2.  **Quorum 확인**: 팔로워들로부터 "로그를 잘 기록했다"는 응답이 과반수 이상 도착하면, 리더는 해당 데이터가 **'안전하게 보장됨(Committed)'**이라고 판단합니다.
3.  **Apply to State Machine**: 커밋이 확정되면 리더는 실제 데이터베이스 상태에 값을 반영하고, 팔로워들에게도 최종 반영을 지시합니다.

---

## 4. 장애 대응: 리더가 죽거나 네트워크 파티션이 발생할 때

Raft는 네트워크 단절 상황에서도 데이터 정합성을 물리적으로 보호합니다.

- **Split Vote 방지**: 여러 후보자가 동시에 등장할 경우, 무작위 타임아웃(Randomized Timeout) 기법을 사용하여 선거가 무한 루프에 빠지는 것을 차단합니다.
- **최신성 검증**: 투표 시 "나보다 로그가 더 최신인 노드"에게만 투표하도록 강제하여, 과거 데이터를 가진 노드가 리더가 되는 대참사를 방지합니다.

---

## 5. 결론: 합의 알고리즘은 분산 시스템의 신뢰 기반이다

Raft는 복잡한 분산 환경에 **강한 일관성(Strong Consistency)**을 부여하는 토대입니다.

1.  과반수 원칙(Quorum)을 통해 일부 노드 장애 상황에서도 시스템 가용성을 유지합니다.
2.  임기(Term)와 로그 인덱스를 통해 데이터의 선후 관계를 물리적으로 강제합니다.
3.  리더 선출과 로그 복제 알고리즘은 분산 DB의 ACID 트랜잭션을 실현하는 핵심 엔진입니다.

다음 아티클에서는 분산 환경에서 수천 대의 서버에 걸쳐 데이터를 원자적으로 수정하는 **분산 트랜잭션 2PC(Two-Phase Commit)** 아키텍처를 분석합니다.
