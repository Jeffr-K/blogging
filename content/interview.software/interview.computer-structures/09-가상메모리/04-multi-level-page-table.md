## 다단계 페이지 테이블

64비트 주소 공간에서 단순 페이지 테이블은 수백 GB를 차지합니다. **다단계 구조**로 실제 사용하는 부분만 할당합니다.

---

## 1. 단순 페이지 테이블의 문제

```
32비트 단순 페이지 테이블:
  페이지 크기: 4KB = 2^12
  페이지 수:   2^32 / 2^12 = 2^20 = 1M 엔트리
  PTE 크기:   4 바이트
  테이블 크기: 4MB (프로세스당)

64비트로 확장하면?
  실제 사용 주소: 48비트
  페이지 수: 2^48 / 2^12 = 2^36 = 64G 엔트리
  PTE 크기: 8 바이트
  테이블 크기: 512GB (프로세스당!) ← 불가능

문제: 프로세스의 실제 사용 메모리는 주소 공간의 극히 일부
  - 텍스트/데이터: 낮은 주소 일부
  - 스택: 높은 주소 일부
  - 대부분은 빈 공간 (매핑 없음)
```

---

## 2. 2단계 페이지 테이블 원리

```
아이디어: 페이지 테이블을 페이지 테이블의 페이지 테이블로!

VPN을 두 부분으로 분리:
┌───────┬───────┬───────────┐
│ VPN1  │ VPN2  │  Offset   │
│ (10)  │ (10)  │  (12)     │
└───────┴───────┴───────────┘

Level 1 (페이지 디렉터리):
  2^10 = 1024 엔트리
  각 엔트리 → Level 2 테이블 (또는 NULL)

Level 2 (페이지 테이블):
  VPN1이 가리키는 경우만 존재!
  2^10 = 1024 엔트리 → PFN

비용:
  사용하는 VPN1 범위만 Level 2 테이블 할당
  희소 주소 공간에서 매우 효율적
```

## 3. x86-64 4단계 페이지 테이블

```
48비트 가상 주소 구조:
┌──────┬──────┬──────┬──────┬──────────┐
│ PGD  │ PUD  │ PMD  │ PT   │ Offset   │
│ (9)  │ (9)  │ (9)  │ (9)  │ (12)     │
└──────┴──────┴──────┴──────┴──────────┘

CR3 레지스터 → PGD (Page Global Directory) 기준 주소

탐색:
CR3 → PGD[PGD 인덱스] → PUD 기준
    → PUD[PUD 인덱스] → PMD 기준
    → PMD[PMD 인덱스] → PT 기준
    → PT[PT 인덱스]   → PFN
PA = PFN × 4096 + Offset

각 테이블: 2^9 = 512 엔트리 × 8 바이트 = 4KB (페이지 1개)

5단계 페이지 테이블 (Linux 5.x+, x86-64):
  57비트 가상 주소 지원 → PGD 위에 PML5 추가
```

## 4. 메모리 절약 효과

```
예: 코드(4MB) + 스택(8MB)만 사용하는 프로세스

단순 1단계 페이지 테이블:
  전체 페이지 테이블: 512GB

4단계 페이지 테이블:
  PGD: 4KB (1개)
  PUD: 4KB × 2 (코드용, 스택용)
  PMD: 4KB × 수 개
  PT:  4KB × (코드 페이지 수 + 스택 페이지 수)
  → 수백 KB 수준!

핵심: 사용하지 않는 주소 범위의 상위 테이블 엔트리 = NULL
  하위 테이블은 아예 할당되지 않음
```

## 5. 역 페이지 테이블 (Inverted Page Table)

```
대안적 설계: VA 기준이 아닌 PA 기준
  물리 프레임 수만큼의 엔트리
  각 엔트리: (PID, VPN)

장점:
  테이블 크기 = 물리 메모리 크기에만 비례
  가상 주소 공간 크기와 무관

단점:
  VA→PA 변환 시 선형 탐색 or 해시 필요 → 느림
  TLB 미스 처리가 복잡

사용: PowerPC, IA-64 등 일부 아키텍처
```

---

## 6. 페이지 테이블 접근 최적화

```
TLB와의 협력:
  TLB 히트: 페이지 테이블 탐색 완전 생략
  TLB 미스: 4단계 테이블 탐색 (메모리 4회 접근)
  → 지역성 덕분에 TLB 히트율 99%+

Huge Page (Large Page):
  2MB, 1GB 크기 페이지 사용
  PMD 또는 PUD 단계에서 직접 물리 주소 지정
  TLB 엔트리 1개로 더 큰 메모리 커버
  데이터베이스, HPC 환경에서 유용
```

## 핵심 요약

- **문제**: 64비트 주소 공간의 단순 페이지 테이블 = 수백 GB.
- **해결**: 다단계 구조 → 실제 사용 부분만 테이블 할당.
- **x86-64**: PGD → PUD → PMD → PT → PFN (4단계, 각 9비트).
- **절약**: 빈 주소 범위는 상위 엔트리 NULL로 하위 테이블 없음.
- **TLB**: 다단계 탐색 비용을 대부분의 경우 제거.
