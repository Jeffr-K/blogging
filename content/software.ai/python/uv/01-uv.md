## 종속성 관리

### 종속 필드

프로젝트의 종속성은 여러 필드에 정의되어 있습니다.

- [project.dependencies](https://docs.astral.sh/uv/concepts/projects/dependencies/#project-dependencies): 게시된 종속성입니다.
- [project.optional-dependencies](https://docs.astral.sh/uv/concepts/projects/dependencies/#optional-dependencies): 게시된 선택적 종속성 또는 "추가 기능".
- [project.dependency-groups](https://docs.astral.sh/uv/concepts/projects/dependencies/#dependency-groups): 개발에 필요한 로컬 종속성입니다.
- [tool.uv.sources](https://docs.astral.sh/uv/concepts/projects/dependencies/#dependency-sources): 개발 중 필요한 라이브러리를 구할 수 있는 대체 소스입니다.

> project.dependencies`<p> ` 및 `<p>` project.optional-dependencies필드는 프로젝트를 게시하지 않을 경우에도 사용할 수 있습니다. 이 dependency-groups기능은 최근에 표준화되었으며 아직 모든 도구에서 지원되지 않을 수 있습니다.

uv adduv는 `--dependency` 및 ` --dependency`를 사용하여 프로젝트의 종속성을 수정하는 것을 지원 uv remove하지만, 종속성 메타데이터는 `--dependency` 파일을 직접 편집하여 업데이트할 수도 있습니다 pyproject.toml.

### 종속성 추가

종속성을 추가하려면:

```bash
$ uv add httpx
```

해당 필드에 항목이 추가됩니다 project.dependencies.

```toml
[project]
name = "example"
version = "0.1.0"
dependencies = ["httpx>=0.27.2"]
```

, , 또는 플래그 --dev를 사용하여 대체 필드에 종속성을 추가할 수 있습니다.--group--optional

종속성에는 >=0.27.2패키지의 최신 호환 버전에 대한 제약 조건(예: )이 포함됩니다. 제약 조건의 종류는 를 사용하여 조정 --bounds하거나 직접 제공할 수 있습니다.

```bash
$ uv add "httpx>=0.20"
```

패키지 레지스트리 이외의 소스에서 종속성을 추가할 때 uv는 sources 필드에 항목을 추가합니다. 예를 들어 httpxGitHub에서 추가하는 경우 다음과 같습니다.

```bash
uv add "httpx @ git+https://github.com/encode/httpx"
```

여기 에는 Git 소스 항목이pyproject.toml 포함됩니다 .

```toml
[project]
name = "example"
version = "0.1.0"
dependencies = [
    "httpx",
]

[tool.uv.sources]
httpx = { git = "https://github.com/encode/httpx" }
```

종속성을 사용할 수 없는 경우 uv는 오류를 표시합니다.

```bash
uv add "httpx>9999"
```

##### 요구 사항 파일에서 종속성 가져오기

파일 에 선언된 종속성은 다음 옵션을 requirements.txt사용하여 프로젝트에 추가할 수 있습니다 -r.

```bash
$ uv add -r requirements.txt
```

자세한 내용은 pip 마이그레이션 가이드를 참조하세요 .

### 종속성 제거

종속성을 제거하려면:

```bash
$ uv remove httpx
```
--dev, --group, 또는 플래그 --optional를 사용하여 특정 테이블에서 종속성을 제거할 수 있습니다.

[제거된 종속성](https://docs.astral.sh/uv/concepts/projects/dependencies/#dependency-sources)에 대해 소스가 정의되어 있고 해당 종속성에 대한 다른 참조가 없는 경우 해당 종속성도 제거됩니다.

### 종속성 변경

기존 종속성을 변경하려면, 예를 들어 다른 제약 조건을 사용하려면 다음과 같습니다 httpx.

```bash
$ uv add "httpx>0.1.0"
```

> 이 예제에서는 종속성에 대한 제약 조건을 변경하고 있습니다 pyproject.toml. 종속성의 고정된 버전은 새 제약 조건을 충족하기 위해 필요한 경우에만 변경됩니다. 제약 조건 내에서 패키지 버전을 최신 버전으로 강제로 업데이트하려면 다음과 같이 사용합니다 --upgrade-package <name>. 예:

```bash
$ uv add "httpx>0.1.0" --upgrade-package httpx
```

패키지 업그레이드에 대한 자세한 내용은 잠금 파일 문서를 참조하십시오 .

다른 종속성 소스를 요청하면 테이블이 업데이트됩니다 . 예를 들어 개발 중에 로컬 경로를 tool.uv.sources사용하도록 요청할 수 있습니다 .httpx

```bash
uv add "httpx @ ../httpx"
```

### 플랫폼별 종속성

종속성이 특정 플랫폼이나 특정 Python 버전에만 설치되도록 하려면 환경 마커를 사용하십시오 .

예를 들어, 리눅스에는 설치 jax하지만 윈도우나 macOS에는 설치하지 않으려면 다음과 같이 하면 됩니다.

```bash
uv add "jax; sys_platform == 'linux'"
```

결과적 pyproject.toml으로 종속성 정의에 환경 마커가 포함됩니다.

```toml
[project]
name = "project"
version = "0.1.0"
requires-python = ">=3.11"
dependencies = ["jax; sys_platform == 'linux'"]
```

마찬가지로 numpyPython 3.11 이상 버전에 포함하려면 다음과 같이 하세요.

```bash
$ uv add "numpy; python_version >= '3.11'"
```

> 사용 가능한 마커 및 연산자에 대한 전체 목록은 Python 의 환경 마커 문서 참조(https://peps.python.org/pep-0508/#environment-markers)

> 팁: 종속성 소스는 플랫폼별로 변경할 수도 있습니다 .

### 프로젝트 종속성

이 project.dependencies표는 PyPI에 업로드하거나 휠을 빌드할 때 사용되는 종속성을 나타냅니다. 개별 종속성은 종속성 지정자 구문을 사용하여 지정되며, 이 표는 PEP 621 표준을 따릅니다.

project.dependencies프로젝트에 필요한 패키지 목록과 설치 시 사용해야 하는 버전 제약 조건을 정의합니다. 각 항목에는 종속성 이름과 버전이 포함됩니다. 플랫폼별 패키지에 대한 추가 정보 또는 환경 변수 마커가 항목에 포함될 수 있습니다. 예를 들면 다음과 같습니다.

```toml
[project]
name = "albatross"
version = "0.1.0"
dependencies = [
  # Any version in this range
  "tqdm >=4.66.2,<5",
  # Exactly this version of torch
  "torch ==2.2.2",
  # Install transformers with the torch extra
  "transformers[torch] >=4.39.3,<5",
  # Only install this package on older python versions
  # See "Environment Markers" for more information
  "importlib_metadata >=7.1.0,<8; python_version < '3.10'",
  "mollymawk ==0.1.0"
]
```











### 의존성 소스

이 tool.uv.sources표는 개발 중에 사용되는 대체 종속성 소스를 표준 종속성 표에 추가하여 확장한 것입니다.

종속성 소스는 표준에서 지원하지 않는 일반적인 패턴 project.dependencies(예: 편집 가능한 설치 및 상대 경로)에 대한 지원을 추가합니다. 예를 들어 foo프로젝트 루트를 기준으로 하는 디렉터리에서 설치하려면 다음과 같이 합니다.

```toml
[project]
name = "example"
version = "0.1.0"
dependencies = ["foo"]

[tool.uv.sources]
foo = { path = "./packages/foo" }
```

uv는 다음과 같은 종속성 소스를 지원합니다.

- 인덱스 : 특정 패키지 인덱스에서 확인된 패키지입니다.
- Git : Git 저장소.
- URL : 원격 휠 또는 소스 배포판.
- 경로 : 로컬 휠, 소스 배포판 또는 프로젝트 디렉터리.
- 워크스페이스 : 현재 워크스페이스의 구성원입니다.

> 소스 정보는 uv에서만 존중됩니다. 다른 도구를 사용하는 경우 표준 프로젝트 테이블의 정의만 사용됩니다. 다른 도구를 사용하여 개발하는 경우 소스 테이블에 제공된 모든 메타데이터는 해당 도구의 형식에 맞게 다시 지정해야 합니다.


##### Index

특정 인덱스에서 Python 패키지를 추가하려면 다음 --index옵션을 사용하십시오.

```bash
$ uv add torch --index pytorch=https://download.pytorch.org/whl/cpu
```

uv는 인덱스를 저장 [[tool.uv.index]]하고 항목을 추가합니다 [tool.uv.sources].

```toml
[project]
dependencies = ["torch"]

[tool.uv.sources]
torch = { index = "pytorch" }

[[tool.uv.index]]
name = "pytorch"
url = "https://download.pytorch.org/whl/cpu"
```

index소스 를 사용하면 패키지가 지정된 인덱스에 고정되어 다른 인덱스에서는 다운로드되지 않습니다.

인덱스를 정의할 때, 해당 인덱스가 명시적으로 지정된 패키지에만 사용되도록 하려면explicit 플래그를 포함할 수 있습니다 . 이 플래그가 설정되지 않은 경우, 다른 곳에서 찾을 수 없는 패키지는 인덱스에서 가져올 수 있습니다.tool.uv.sourcesexplicit

```toml
[[tool.uv.index]]
name = "pytorch"
url = "https://download.pytorch.org/whl/cpu"
explicit = true
```

##### Git

Git 종속성 소스를 추가하려면 Git 호환 URL 앞에 `.`을 붙이세요 git+.

```bash
# Install over HTTP(S).
$ uv add git+https://github.com/encode/httpx

# Install over SSH.
$ uv add git+ssh://git@github.com/encode/httpx
```

```toml
[project]
dependencies = ["httpx"]

[tool.uv.sources]
httpx = { git = "https://github.com/encode/httpx" }
```

특정 Git 참조(예: 태그)를 요청할 수 있습니다.

```bash
$ uv add git+https://github.com/encode/httpx --tag 0.27.0
```

```toml
[project]
dependencies = ["httpx"]

[tool.uv.sources]
httpx = { git = "https://github.com/encode/httpx", tag = "0.27.0" }
```

또는 브랜치별로 가져올 수 있다:

```bash
$ uv add git+https://github.com/encode/httpx --branch main
```

```toml
[project]
dependencies = ["httpx"]

[tool.uv.sources]
httpx = { git = "https://github.com/encode/httpx", branch = "main" }
```

또는 특정 커밋을 기반으로:

```bash
$ uv add git+https://github.com/encode/httpx --rev 326b9431c761e1ef1e00b9f760d1f654c8db48c6
```

subdirectory패키지가 저장소 루트에 없는 경우 A를 지정할 수 있습니다.

```bash
$ uv add git+https://github.com/langchain-ai/langchain#subdirectory=libs/langchains
```

```toml
[project]
dependencies = ["langchain"]

[tool.uv.sources]
langchain = { git = "https://github.com/langchain-ai/langchain", subdirectory = "libs/langchain" }
```

Git LFS 지원 여부는 소스별로 설정할 수 있습니다. 기본적으로 Git LFS 객체는 가져오지 않습니다.

```bash
uv add --lfs git+https://github.com/astral-sh/lfs-cowsay
```

```toml
[project]
dependencies = ["lfs-cowsay"]

[tool.uv.sources]
lfs-cowsay = { git = "https://github.com/astral-sh/lfs-cowsay", lfs = true }
```

- 이 경우 lfs = trueuv는 항상 이 Git 소스에 대한 LFS 객체를 가져옵니다.
- 이 경우 lfs = falseuv는 해당 Git 소스에 대한 LFS 객체를 절대 가져오지 않습니다.
- 생략할 경우, UV_GIT_LFS환경 변수는 명시적인 설정 없이 모든 Git 소스에 사용됩니다 lfs.

> Git LFS를 사용하여 소스를 설치하기 전에 시스템에 Git LFS가 설치 및 구성되어 있는지 확인하십시오. 그렇지 않으면 빌드 오류가 발생할 수 있습니다.


##### URL

URL 소스를 추가하려면 https://휠(확장자가 .wheel인 파일 .whl) 또는 소스 배포판(일반적으로 .wheel .tar.gz또는 .source로 끝나는 파일 )의 URL을 제공하세요. 지원되는 모든 형식은 여기를.zip 참조하세요 .

```bash
$ uv add "https://files.pythonhosted.org/packages/5c/2d/3da5bdf4408b8b2800061c339f240c1802f2e82d55e50bd39c5a881f47f0/httpx-0.27.0.tar.gz"
```

다음과 같은 결과가 나타납니다 pyproject.toml:

[project]
dependencies = ["httpx"]

[tool.uv.sources]
httpx = { url = "https://files.pythonhosted.org/packages/5c/2d/3da5bdf4408b8b2800061c339f240c1802f2e82d55e50bd39c5a881f47f0/httpx-0.27.0.tar.gz" }

##### wheel

.whl경로 소스를 추가하려면 휠 파일(확장자가 .로 끝남 ), 소스 배포판(일반적으로 .tar.gz또는 로 끝남, 지원되는 모든 형식은 여기.zip 참조 ) 또는 . 파일이 포함된 디렉터리 의 경로를 제공하십시오 .pyproject.toml

```bash
$ uv add /example/foo-0.1.0-py3-none-any.whl
```

다음과 같은 결과가 나타납니다 pyproject.toml:

```bash
[project]
dependencies = ["foo"]

[tool.uv.sources]
foo = { path = "/example/foo-0.1.0-py3-none-any.whl" }
```

경로는 상대 경로일 수도 있습니다.

```bash
$ uv add ./foo-0.1.0-py3-none-any.whl
```

또는 프로젝트 디렉토리의 경로:

```bash
$ uv add ~/projects/bar/
```

> 디렉토리를 경로 종속성으로 사용할 경우, uv는 기본적으로 해당 대상을 패키지로 빌드하고 설치하려고 시도합니다. 자세한 내용은 가상 종속성 문서를 참조하십시오.

기본적으로 경로 종속성에는 편집 가능한 설치가 사용 되지 않습니다. 프로젝트 디렉터리의 경우 편집 가능한 설치를 요청할 수 있습니다.

```bash
$ uv add --editable ../projects/bar/
```

그 결과 다음과 같은 결과가 나타납니다 pyproject.toml:

```toml
[project]
dependencies = ["bar"]

[tool.uv.sources]
bar = { path = "../projects/bar", editable = true }
```

> 동일한 저장소에 여러 패키지가 있는 경우 워크스페이스가 더 적합할 수 있습니다.

##### Workspace Member

워크스페이스 멤버에 대한 종속성을 선언하려면 멤버 이름을 .으로 추가하세요 { workspace = true }. 모든 워크스페이스 멤버는 명시적으로 지정해야 합니다. 워크스페이스 멤버는 항상 편집 가능합니다 . 워크스페이스에 대한 자세한 내용은 워크스페이스 문서를 참조하세요 .

```toml
[project]
dependencies = ["foo==0.1.0"]

[tool.uv.sources]
foo = { workspace = true }

[tool.uv.workspace]
members = [
  "packages/foo"
]
```

##### 플랫폼별 소스

소스에 대한 호환 환경 마커를 종속성 지정자 로 제공하면 소스를 특정 플랫폼 또는 Python 버전으로 제한할 수 있습니다 .

httpx예를 들어, macOS에서만 GitHub에서 코드를 가져오려면 다음을 사용하세요.

```toml
[project]
dependencies = ["httpx"]

[tool.uv.sources]
httpx = { git = "https://github.com/encode/httpx", tag = "0.27.2", marker = "sys_platform == 'darwin'" }
```

##### 다중 출저

PEP 508 호환 환경 마커 로 구분되는 소스 목록을 제공하여 단일 종속성에 대해 여러 소스를 지정할 수 있습니다 .

httpx예를 들어 macOS와 Linux에서 서로 다른 태그를 가져오려면 다음과 같이 합니다 .

```toml
[project]
dependencies = ["httpx"]

[tool.uv.sources]
httpx = [
  { git = "https://github.com/encode/httpx", tag = "0.27.2", marker = "sys_platform == 'darwin'" },
  { git = "https://github.com/encode/httpx", tag = "0.24.1", marker = "sys_platform == 'linux'" },
]
```

이 전략은 환경적 특징에 따라 서로 다른 인덱스를 사용하는 것까지 확장됩니다. 예를 들어, torch플랫폼에 따라 서로 다른 PyTorch 인덱스에서 설치하는 경우입니다.

```toml
[project]
dependencies = ["torch"]

[tool.uv.sources]
torch = [
  { index = "torch-cpu", marker = "platform_system == 'Darwin'"},
  { index = "torch-gpu", marker = "platform_system == 'Linux'"},
]

[[tool.uv.index]]
name = "torch-cpu"
url = "https://download.pytorch.org/whl/cpu"
explicit = true

[[tool.uv.index]]
name = "torch-gpu"
url = "https://download.pytorch.org/whl/cu124"
explicit = true
```

##### 소스 비활성화

uv에게 해당 테이블을 무시하도록 지시하려면 tool.uv.sources(예: 패키지에 게시된 메타데이터를 사용하여 해결하는 것을 시뮬레이션하려면) 다음 --no-sources플래그를 사용하십시오.

```toml
uv lock --no-sources
```

또한, 이를 사용하면 uv가 주어진 종속성을 만족시킬 수 있는 작업 공간 구성원을--no-sources 발견하지 못하게 됩니다 .

### 선택적 종속성

라이브러리로 배포되는 프로젝트에서는 기본 종속성 트리를 줄이기 위해 일부 기능을 선택 사항으로 만드는 것이 일반적입니다. 예를 들어, Pandas는 Excel 파서를 설치하지 않도록 하는 excel추가 기능 과 plot추가 기능을matplotlib 제공하며, 사용자가 명시적으로 요구하지 않는 한 설치가 필요하지 않습니다. 추가 기능은 `extra` 구문을 사용하여 요청할 수 있습니다 package[<extra>](예: `extra` pandas[plot, excel]).

선택적 종속성은 종속성 지정자[project.optional-dependencies] 구문 에 따라 추가 이름과 해당 종속성을 매핑하는 TOML 테이블인 에 지정됩니다 .

tool.uv.sources선택적 종속성은 일반 종속성과 동일한 방식으로 항목을 가질 수 있습니다 .

```toml
[project]
name = "pandas"
version = "1.0.0"

[project.optional-dependencies]
plot = [
  "matplotlib>=3.6.3"
]
excel = [
  "odfpy>=1.4.1",
  "openpyxl>=3.1.0",
  "python-calamine>=0.1.7",
  "pyxlsb>=1.0.10",
  "xlrd>=2.0.1",
  "xlsxwriter>=3.0.5"
]
```

선택적 종속성을 추가하려면 다음 --optional <extra>옵션을 사용하십시오.

```bash
$ uv add httpx --optional network
```

> 선택적 종속성이 서로 충돌하는 경우, 명시 적으로 충돌하는 것으로 선언 하지 않으면 해결에 실패합니다 .

소스는 특정 선택적 종속성에만 적용되도록 선언할 수도 있습니다. 예를 들어, torch선택적 cpu또는 gpu추가 종속성에 따라 서로 다른 PyTorch 인덱스에서 가져오려면 다음과 같이 할 수 있습니다.

```toml
[project]
dependencies = []

[project.optional-dependencies]
cpu = [
  "torch",
]
gpu = [
  "torch",
]

[tool.uv.sources]
torch = [
  { index = "torch-cpu", extra = "cpu" },
  { index = "torch-gpu", extra = "gpu" },
]

[[tool.uv.index]]
name = "torch-cpu"
url = "https://download.pytorch.org/whl/cpu"

[[tool.uv.index]]
name = "torch-gpu"
url = "https://download.pytorch.org/whl/cu124"
```

### 개발 종속성

선택적 종속성과 달리 개발 종속성은 로컬에서만 사용되며 PyPI 또는 기타 인덱스에 게시할 때 프로젝트 요구 사항에 포함되지 않습니다 . 따라서 개발 종속성은 [project]표에 포함되지 않습니다.

개발 종속성은 tool.uv.sources일반 종속성과 동일한 방식으로 항목을 가질 수 있습니다.

개발 종속성을 추가하려면 다음 --dev플래그를 사용하십시오.

```bash
$ uv add --dev pytest
```

uv는 개발 종속성 선언을 위해 ( PEP 735[dependency-groups] 에 정의된 ) 테이블을 사용합니다. 위 명령은 그룹을 생성합니다.dev

```toml
[dependency-groups]
dev = [
  "pytest >=8.1.1,<9"
]
```

해당 그룹은 특별하게 처리되며 , 종속성 포함 또는 제외 여부를 전환하는 플래그가 있습니다. 모든 기본 그룹을 비활성화하려면 해당 옵션을 참조하십시오 . dev또한 , 해당 그룹은 기본적으로 동기화 됩니다 .--dev--only-dev--no-dev--no-default-groupsdev

##### 종속 집단

개발 종속성은 플래그를 사용하여 여러 그룹으로 나눌 수 있습니다 --group.

예를 들어, 그룹에 개발 종속성을 추가하려면 다음과 같이 합니다 lint.

```bash
$ uv add --group lint ruff
```

그 결과 다음과 같은 [dependency-groups]정의가 나옵니다.

```toml
[dependency-groups]
dev = [
  "pytest"
]
lint = [
  "ruff"
]
```

그룹이 정의되면 , --all-groups, --no-default-groups, --group, --only-group및 --no-group옵션을 사용하여 그룹 간의 종속성을 포함하거나 제외할 수 있습니다.

> , , 및 플래그는 각각 --dev, , 및 와 동일합니다 .--only-dev--no-dev--group dev--only-group dev--no-group dev

uv는 모든 종속성 그룹이 서로 호환되어야 하며, 잠금 파일을 생성할 때 모든 그룹을 함께 해결합니다.

한 그룹에 선언된 종속성이 다른 그룹의 종속성과 호환되지 않으면 uv는 오류를 발생시키며 프로젝트 요구 사항을 해결하는 데 실패합니다.

> 종속성 그룹 간에 충돌이 있는 경우, 명시 적으로 충돌한다고 선언하지 않으면 해결이 실패합니다 .

##### 둥지 그룹

종속 그룹은 다른 종속 그룹을 포함할 수 있습니다. 예:

```toml
[dependency-groups]
dev = [
  {include-group = "lint"},
  {include-group = "test"}
]
lint = [
  "ruff"
]
test = [
  "pytest"
]
```

포함된 그룹의 종속성은 그룹 내에 선언된 다른 종속성과 충돌할 수 없습니다.

##### 기본 그룹

기본적으로 uv는 dev환경 변수에 종속성 그룹을 포함합니다(예: during uv run또는 uv sync). 포함할 기본 그룹은 설정을 사용하여 변경할 수 있습니다 tool.uv.default-groups.

```toml
[tool.uv]
default-groups = ["dev", "foo"]
```

모든 종속성 그룹을 기본적으로 활성화하려면 "all"그룹 이름을 나열하는 대신 다음을 사용하십시오.

```toml
[tool.uv]
default-groups = ["all"]
```

> uv run또는 도중에 이 동작을 비활성화하려면 uv sync를 사용하십시오 --no-default-groups. 특정 기본 그룹을 제외하려면 를 사용하십시오 --no-group <name>.

##### 그룹requires-python

기본적으로 종속성 그룹은 프로젝트의 requires-python범위와 호환되어야 합니다.

종속성 그룹이 프로젝트와 다른 Python 버전 범위를 요구하는 경우, 예를 들어 다음과 같이 requires-python그룹에 대한 범위를 지정할 수 있습니다 [tool.uv.dependency-groups].

```toml
[project]
name = "example"
version = "0.0.0"
requires-python = ">=3.10"

[dependency-groups]
dev = ["pytest"]

[tool.uv.dependency-groups]
dev = {requires-python = ">=3.12"}
```

##### 유산dev-dependencies

[dependency-groups]표준화되기 전에는 uv는 해당 tool.uv.dev-dependencies필드를 사용하여 개발 종속성을 지정했습니다. 예:

```toml
[tool.uv]
dev-dependencies = [
  "pytest"
]
```

이 섹션에 선언된 종속성은 의 내용과 결합됩니다 dependency-groups.dev. 결국 이 dev-dependencies필드는 더 이상 사용되지 않고 제거될 것입니다.

> 해당 필드가 이미 존재하는 경우 tool.uv.dev-dependencies, uv add --dev새 섹션을 추가하는 대신 기존 섹션을 사용합니다 dependency-groups.dev.

### 빌드 종속성

프로젝트가 Python 패키지 구조로 되어 있는 경우 , 프로젝트 빌드에는 필요하지만 실행에는 필요하지 않은 종속성을 선언할 수 있습니다. 이러한 종속성은 PEP 518 에 따라 [build-system]아래 표 에 명시되어 있습니다 .build-system.requires

예를 들어, 프로젝트에서 setuptools빌드 백엔드로 를 사용하는 경우 setuptools빌드 종속성으로 를 선언해야 합니다.

```toml
[project]
name = "pandas"
version = "0.1.0"

[build-system]
requires = ["setuptools>=42"]
build-backend = "setuptools.build_meta"
```

기본적으로 uv는 tool.uv.sources빌드 종속성을 해결할 때 이를 존중합니다. 예를 들어 빌드에 로컬 버전을 사용하려면 setuptools소스를 다음과 같이 추가하세요 tool.uv.sources.

```toml
[project]
name = "pandas"
version = "0.1.0"

[build-system]
requires = ["setuptools>=42"]
build-backend = "setuptools.build_meta"

[tool.uv.sources]
setuptools = { path = "./packages/setuptools" }
```

패키지를 게시할 때, 다른 빌드 도구(예: )를 사용하는 경우처럼 가 비활성화된 경우에도 uv build --no-sources패키지가 올바르게 빌드되는지 확인하기 위해 를 실행하는 것이 좋습니다 .tool.uv.sourcespypa/build

### 편집 가능한 종속성

파이썬 패키지가 포함된 디렉토리를 일반적인 방식으로 설치하면 먼저 휠(wheel) 파일이 생성되고, 그 휠 파일이 가상 환경에 설치되면서 모든 소스 파일이 복사됩니다. 패키지 소스 파일을 수정하면 가상 환경에는 이전 버전이 포함되게 됩니다.

편집 가능한 설치 방식은 가상 환경 내의 프로젝트 링크( .pth파일)를 추가하여 이 문제를 해결합니다. 이 링크는 인터프리터에게 소스 파일을 직접 포함하도록 지시합니다.

편집 가능한 항목에는 몇 가지 제약 사항이 있습니다(주로 빌드 백엔드가 이를 지원해야 하고, 네이티브 모듈은 가져오기 전에 다시 컴파일되지 않습니다). 하지만 가상 환경이 항상 패키지의 최신 변경 사항을 사용하므로 개발에는 유용합니다.

uv는 기본적으로 워크스페이스 패키지에 대해 편집 가능한 설치를 사용합니다.

편집 가능한 종속성을 추가하려면 다음 --editable플래그를 사용하십시오.

```bash
$ uv add --editable ./path/foo
```

또는 워크스페이스에서 편집 가능한 종속성 사용을 거부하려면 다음과 같이 하세요.

```bash
$ uv add --no-editable ./path/foo
```

### 가상 종속성

uv는 종속성을 "가상"으로 만들 수 있도록 허용합니다. 즉, 종속성 자체는 패키지 로 설치되지 않지만 해당 종속성은 패키지로 설치됩니다.

기본적으로 종속성은 가상 파일이 아닙니다.

path소스 가 있는 종속성은 명시적으로 설정하면 가상으로 구성될 수 있습니다 tool.uv.package = false. uv를 사용하여 종속 프로젝트 에서 작업하는 것과는 달리, 빌드 시스템이 선언되지 않은 경우에도 패키지가 빌드됩니다 .

종속성을 가상으로 처리하려면 package = false소스에 다음과 같이 설정하십시오.

```toml
[project]
dependencies = ["bar"]

[tool.uv.sources]
bar = { path = "../projects/bar", package = false }
```

종속성이 설정하는 경우 소스에 tool.uv.package = false선언하여 재정의할 수 있습니다 .package = true

```toml
[project]
dependencies = ["bar"]

[tool.uv.sources]
bar = { path = "../projects/bar", package = true }
```

workspace마찬가지로, 소스 가 있는 종속성은 명시적으로 설정하면 가상 종속성이 될 수 있습니다 . 빌드 시스템이 선언되지 않은 tool.uv.package = false경우에도 워크스페이스 멤버는 빌드됩니다 .

종속성이 아닌 워크스페이스 멤버는 기본적으로 가상 멤버일 수 있습니다. 예를 들어, 부모 멤버가 다음과 같은 경우 pyproject.toml입니다.

```toml
[project]
name = "parent"
version = "1.0.0"
dependencies = []

[tool.uv.workspace]
members = ["child"]
```

그리고 child 는 pyproject.toml빌드 시스템을 제외했습니다.

```toml
[project]
name = "child"
version = "1.0.0"
dependencies = ["anyio"]
```

그러면 child워크스페이스 멤버는 설치되지 않지만, 전이적 종속성은 anyio 설치됩니다.

반면, 부모가 다음과 같은 종속성을 선언한 경우 child:

```toml
[project]
name = "parent"
version = "1.0.0"
dependencies = ["child"]

[tool.uv.sources]
child = { workspace = true }

[tool.uv.workspace]
members = ["child"]
```

그런 다음 child제작 및 설치가 진행될 것입니다.

### 종속성 지정자

uv는 [PEP 508](https://peps.python.org/pep-0508/) 에 정의된 [표준 의존성 지정자](https://packaging.python.org/en/latest/specifications/dependency-specifiers/)를 사용합니다 . 의존성 지정자는 순서대로 다음과 같은 요소로 구성됩니다.

- 종속성 이름
- 원하시는 추가 옵션 (선택 사항)
- 버전 지정자
- 환경 표시자(선택 사항)
- 버전 지정자는 쉼표로 구분하여 합산합니다. 예를 들어, 는 "최소 1.2.3 이상, 2 미만, 그리고 1.4.0이 아닌 foo >=1.2.3,<2,!=1.4.0버전"으로 해석됩니다 .foo

지정자는 필요한 경우 후행 0으로 채워지므로 foo ==2foo 2.0.0과도 일치합니다.

별표(*)는 등호와 함께 마지막 자리에 사용할 수 있습니다. 예를 들어, foo ==2.1.*는 2.1 시리즈의 모든 릴리스를 허용합니다. 마찬가지로, ~=마지막 자리가 같거나 더 큰 경우에도 일치합니다. 예를 들어, foo ~=1.2 는 와 같고 foo >=1.2,<2, foo ~=1.2.3는 와 같습니다 foo >=1.2.3,<1.3.

추가 기능은 이름과 버전 사이에 대괄호 안에 쉼표로 구분하여 입력합니다(예: pandas[excel,plot] ==2.2). 추가 기능 이름 사이의 공백은 무시됩니다.

일부 종속성은 특정 환경(예: 특정 Python 버전 또는 운영 체제)에서만 필요합니다. 예를 들어 모듈 importlib-metadata의 백포트를 설치하려면 `pip install -p` importlib.metadata를 사용하십시오 importlib-metadata >=7.1.0,<8; python_version < '3.10'. Windows에 설치하려면 colorama(다른 플랫폼에서는 생략) `pip install -p`를 사용하십시오 colorama >=0.4.6,<5; platform_system == "Windows".

and표시자는 쉼표 (, or)와 괄호(,) 로 결합됩니다 (예: aiohttp >=3.7.4,<4; (sys_platform != 'win32' or implementation_name != 'pypy') and python_version >= '3.10'). 표시자 내의 버전은 따옴표로 묶어야 하지만, 표시자 외부 의 버전은 따옴표로 묶지 않아도 됩니다 .





## 프로젝트에서 명령 실행

프로젝트를 진행할 때, 해당 프로젝트는 가상 환경(주소는 명시되지 않음)에 설치됩니다 .venv. 이 가상 환경은 기본적으로 현재 셸과 격리되어 있으므로, 프로젝트가 필요한 명령(예: `npm install`)은 python -c "import example"실행되지 않습니다. 따라서, `npm install` 대신 `npm install`을 사용하여 uv run프로젝트 환경에서 명령을 실행하십시오.

```bash
$ uv run python -c "import example"
```

uv를 사용하면 run지정된 명령을 실행하기 전에 프로젝트 환경이 최신 상태인지 확인합니다.

주어진 명령어는 프로젝트 환경에서 제공될 수도 있고, 프로젝트 환경 외부에 존재할 수도 있습니다. 예를 들면 다음과 같습니다.

```bash
# Presuming the project provides `example-cli`
$ uv run example-cli foo

# Running a `bash` script that requires the project to be available
$ uv run bash scripts/foo.shs
```

### 추가 종속성 요청

호출 시마다 추가적인 종속성 또는 종속성의 다른 버전을 요청할 수 있습니다.

이 --with옵션은 호출에 대한 종속성을 포함하는 데 사용됩니다. 예를 들어, 다른 버전을 요청할 때 사용할 수 있습니다 httpx.

```bash
$ uv run --with httpx==0.26.0 python -c "import httpx; print(httpx.__version__)"

$ uv run --with httpx==0.25.0 python -c "import httpx; print(httpx.__version__)"
```

프로젝트 요구 사항과 관계없이 요청하신 버전이 적용됩니다. 예를 들어, 프로젝트에서 특정 버전을 요구하더라도 httpx==0.24.0위의 출력 결과는 동일합니다.

해당 호출은 지정된 종속성만 나열된 상태로 프로젝트와 완전히 분리되어uv run example.py 실행됩니다 .

### 신호 처리

uv는 실패 시 더 나은 오류 메시지를 제공하기 위해 프로세스 제어권을 생성된 명령에 넘겨주지 않습니다. 따라서 uv는 요청된 명령이 실행되는 자식 프로세스에 일부 신호를 전달하는 역할을 합니다.

유닉스 시스템에서 uv는 SIGKILL, SIGCHLD, SIGIO, SIGPOLL을 제외한 대부분의 신호를 자식 프로세스로 전달합니다. 터미널은 Ctrl-C를 누르면 포그라운드 프로세스 그룹으로 SIGINT를 전송하므로, uv는 SIGINT가 두 번 이상 전송되었거나 자식 프로세스 그룹이 uv의 그룹과 다른 경우에만 자식 프로세스로 SIGINT를 전달합니다.

Windows에서는 이러한 개념이 적용되지 않으며, uv는 Ctrl-C 이벤트를 무시하고 자식 프로세스가 깔끔하게 종료될 수 있도록 처리를 자식 프로세스로 넘깁니다.















## 잠금 및 동기화

락킹은 프로젝트의 종속성을 락파일 로 정리하는 과정입니다 . 동기화는 락파일에서 일부 패키지를 프로젝트 환경 에 설치하는 과정입니다 .

uv에서는 잠금 및 동기화가 자동으로 이루어집니다 . 예를 들어, uv run`lock` 명령어를 사용하면 요청된 명령어를 실행하기 전에 프로젝트가 잠기고 동기화됩니다. 이를 통해 프로젝트 환경이 항상 최신 상태로 유지됩니다. 마찬가지로, `lock` 명령어처럼 잠금 파일을 읽는 명령어는 uv tree실행 전에 자동으로 잠금 파일을 업데이트합니다.

자동 잠금 기능을 비활성화하려면 다음 --locked옵션을 사용하십시오.

```bash
$ uv run --locked ...
```

잠금 파일이 최신 상태가 아니면 uv는 잠금 파일을 업데이트하는 대신 오류를 발생시킵니다.

잠금 파일이 최신 상태인지 확인하지 않고 사용하려면 다음 --frozen옵션을 사용하십시오.

```bash
uv run --frozen ...
```

마찬가지로 환경이 최신 상태인지 확인하지 않고 명령을 실행하려면 다음 --no-sync 옵션을 사용하십시오.

```bash
uv run --no-sync ...
```

### 잠금 파일 확인 중

uv는 락파일이 최신 상태인지 판단할 때 프로젝트 메타데이터와 일치하는지 확인합니다. 예를 들어, 프로젝트에 종속성을 추가하면 pyproject.toml락파일이 오래된 것으로 간주됩니다. 마찬가지로, 종속성의 버전 제약 조건을 변경하여 잠금 버전이 제외되면 락파일이 오래된 것으로 간주됩니다. 하지만 버전 제약 조건을 변경하여 기존 잠금 버전이 포함되도록 하면 락파일은 여전히 ​​최신 상태로 간주됩니다.

잠금 파일이 최신 상태인지 확인하려면 --check플래그를 전달하면 됩니다 uv lock.

### 잠금 파일 생성

잠금 파일은 자동으로 생성되지만 , 다음 명령어를 사용하여 명시적으로 생성하거나 업데이트할 수도 있습니다 uv lock.

```bash

```

### 환경 동기화

환경은 자동으로 동기화되지만 , 다음 명령어를 사용하여 명시적으로 동기화할 수도 있습니다 uv sync.

```bash
$ uv sync
```

환경을 수동으로 동기화하는 것은 특히 편집기가 필요한 종속 요소의 올바른 버전을 사용하고 있는지 확인하는 데 유용합니다.

##### 편집 가능한 설치

환경이 동기화되면 uv는 프로젝트(및 기타 작업 공간 구성원)를 편집 가능한 패키지로 설치하므로 변경 사항이 환경에 반영되기 위해 다시 동기화할 필요가 없습니다.

이러한 동작을 거부하려면 해당 --no-editable옵션을 사용하십시오.

> 프로젝트에 빌드 시스템이 정의되어 있지 않으면 설치되지 않습니다. 자세한 내용은 빌드 시스템 문서를 참조하십시오.

##### 선택적 종속성 동기화

uv는 테이블에서 선택적 종속성을 읽어옵니다 [project.optional-dependencies]. 이러한 종속성은 흔히 "추가 옵션"이라고 불립니다.

uv는 기본적으로 추가 기능을 동기화하지 않습니다. --extra추가 기능을 포함하려면 해당 옵션을 사용하십시오.

```bash
$ uv sync --extra foo
```

모든 추가 기능을 빠르게 활성화하려면 해당 --all-extras옵션을 사용하세요.

선택적 종속성을 관리하는 방법에 대한 자세한 내용은 선택적 종속성 문서를 참조하십시오 .



##### 개발 종속성 동기화

[dependency-groups]uv는 ( PEP 735 에 정의된 대로) 표 에서 개발 종속성을 읽습니다 .

해당 dev그룹은 특별히 처리되며 기본적으로 동기화됩니다. 기본 설정을 변경하는 방법에 대한 자세한 내용은 기본 그룹 문서를 참조하세요.

### 잠긴 패키지 버전 업그레이드

기존 파일이 있는 경우 , uv는 실행 시 uv.lock이전에 고정된 패키지 버전을 우선적으로 사용합니다 . 패키지 버전은 프로젝트의 종속성 제약 조건에서 이전에 고정된 버전을 제외하는 경우에만 변경됩니다.uv syncuv lock

모든 패키지를 업그레이드하려면:

```bash
$ uv lock --upgrade
```

다른 모든 패키지의 잠금된 버전을 유지하면서 특정 패키지만 최신 버전으로 업그레이드하려면 다음 단계를 따르세요.

```bash
$ uv lock --upgrade-package <package>
```

특정 패키지 하나를 특정 버전으로 업그레이드하려면 다음 단계를 따르세요.

```bash
$ uv lock --upgrade-package <package>==<version>
```

모든 경우에 업그레이드는 프로젝트의 종속성 제약 조건에 따라 제한됩니다. 예를 들어, 프로젝트에서 패키지의 상한 버전을 정의한 경우 업그레이드는 해당 버전을 초과하지 않습니다.

> uv는 Git 종속성에 유사한 논리를 적용합니다. 예를 들어, Git 종속성이 브랜치를 참조하는 경우 , `--report` 또는 ` --report` 플래그가 사용되지 않는 한, uv는 해당 브랜치 의 최신 커밋보다 main기존 파일의 잠긴 커밋 SHA를 우선적으로 사용합니다 .uv.lockmain--upgrade--upgrade-package

이러한 플래그는 잠금 파일 및 환경 변수를 업데이트 uv sync하거나 업데이트하는 데 에도 사용할 수 있습니다 .uv run

### 부분 설치

때로는 여러 단계에 걸쳐 설치를 수행하는 것이 유용할 수 있습니다. 예를 들어 Docker 이미지를 빌드하는 동안 최적의 레이어 캐싱을 위해 이러한 작업을 수행할 수 있습니다. uv sync이를 위해 여러 플래그가 제공됩니다.

- --no-install-project현재 프로젝트를 설치하지 마십시오.
- --no-install-workspace루트 프로젝트를 포함하여 워크스페이스의 어떤 멤버도 설치하지 마십시오.
- --no-install-package <NO_INSTALL_PACKAGE>다음 패키지를 설치하지 마십시오.

이러한 옵션을 사용하면 대상의 모든 종속성이 여전히 설치됩니다.

예를 들어, 프로젝트--no-install-project 는 제외되지만 해당 프로젝트의 종속성은 그대로 유지됩니다.

이러한 플래그를 잘못 사용하면 패키지에 필요한 종속성이 누락되어 환경이 손상될 수 있습니다.

##### 격리 구축

기본적으로 uv는 PEP 517 에 따라 선언된 빌드 종속성과 함께 모든 패키지를 격리된 가상 환경에서 빌드합니다 .

일부 패키지는 의도적이든 아니든 이러한 격리 구축 방식과 호환되지 않습니다.

예를 들어, `python` flash-attn과 같은 패키지 deepspeed는 프로젝트 환경에 설치된 PyTorch 버전과 동일한 버전을 대상으로 빌드되어야 합니다. 이러한 패키지를 격리된 환경에서 빌드하면 의도치 않게 다른 버전의 PyTorch를 대상으로 빌드되어 런타임 오류가 발생할 수 있습니다.

경우에 따라 패키지가 선언된 빌드 종속성 목록에서 필수 종속성을 실수로 누락할 수 있습니다. 예를 들어, 를 설치하기 전에 프로젝트 환경에 가 설치되어 있어야 cchardet하지만 , 이를 빌드 종속성으로 선언하지 않는 경우가 있습니다.cythoncchardet

이러한 문제를 해결하기 위해 uv는 빌드 격리 동작을 수정하는 두 가지 별도의 접근 방식을 지원합니다.

빌드 종속성 목록 확장 : 이 기능을 사용하면 패키지를 격리된 환경에 설치하되, 패키지 자체에서 extra-build-dependencies 설정으로 선언하지 않은 추가 빌드 종속성을 사용할 수 있습니다. 예를 들어, `package.js`와 같은 패키지의 경우 , 해당 빌드 종속성(예: `package.js`)이 프로젝트 환경에 설치되었거나 설치될 패키지 버전과 일치하도록 flash-attn강제할 수도 있습니다 .torch

특정 패키지에 대한 빌드 격리 비활성화 : 이 기능을 사용하면 격리된 환경에서 빌드하지 않고도 패키지를 설치할 수 있습니다.

가능하다면 빌드 격리를 완전히 비활성화하는 것보다는 빌드 종속성을 추가하는 것을 권장합니다. 빌드 격리를 비활성화하는 방식은 패키지 자체를 설치하기 전에 빌드 종속성이 프로젝트 환경에 설치되어야 하므로 설치 단계가 복잡해지고, 프로젝트 환경에 불필요한 패키지가 포함될 수 있으며, 다른 환경에서 프로젝트 환경을 재현하기 어려워질 수 있기 때문입니다.

###### 빌드 종속성 증강

특정 패키지의 빌드 종속성 목록을 확장하려면 해당 패키지를 . extra-build-dependencies의 목록 에 추가하세요 pyproject.toml.

예를 들어, 추가 빌드 종속성으로 빌드하려면 다음을 cchardet포함 하세요 .cythonpyproject.toml

```toml
[project]
name = "project"
version = "0.1.0"
description = "..."
readme = "README.md"
requires-python = ">=3.12"
dependencies = ["cchardet"]

[tool.uv.extra-build-dependencies]
cchardet = ["cython"]
```

빌드 종속성이 프로젝트 환경에 설치되었거나 설치될 패키지 버전과 일치하도록 하려면 표 match-runtime = true에 설정하십시오 extra-build-dependencies. 예를 들어, 추가 빌드 종속성으로 빌드하려면 다음을 포함 deepspeed하십시오 .torchpyproject.toml

```toml
[project]
name = "project"
version = "0.1.0"
description = "..."
readme = "README.md"
requires-python = ">=3.12"
dependencies = ["deepspeed", "torch"]

[tool.uv.extra-build-dependencies]
deepspeed = [{ requirement = "torch", match-runtime = true }]
```

이렇게 하면 프로젝트 환경에 설치된 버전 deepspeed과 동일한 버전으로 빌드가 보장됩니다 .torch

마찬가지로, 추가 빌드 종속성으로 빌드하려면 다음을 flash-attn포함 하세요 .torchpyproject.toml

```toml
[project]
name = "project"
version = "0.1.0"
description = "..."
readme = "README.md"
requires-python = ">=3.12"
dependencies = ["flash-attn", "torch"]

[tool.uv.extra-build-dependencies]
flash-attn = [{ requirement = "torch", match-runtime = true }]

[tool.uv.extra-build-variables]
flash-attn = { FLASH_ATTENTION_SKIP_CUDA_BUILD = "TRUE" }
```

> 이 FLASH_ATTENTION_SKIP_CUDA_BUILD환경 변수는 flash-attnCUDA 개발 툴킷에 대한 접근 권한이 필요한 소스 코드 빌드를 시도하는 대신, 호환되는 사전 빌드된 휠 파일에서 설치되도록 합니다. CUDA 툴킷을 사용할 수 없는 경우, 환경 변수를 생략할 수 있으며, flash-attn현재 플랫폼, Python 버전 및 PyTorch 버전에 맞는 사전 빌드된 휠 파일이 있으면 해당 파일에서 설치됩니다.

마찬가지로, deep_gemm동일한 패턴을 따릅니다.

```toml
[project]
name = "project"
version = "0.1.0"
description = "..."
readme = "README.md"
requires-python = ">=3.12"
dependencies = ["deep_gemm", "torch"]

[tool.uv.sources]
deep_gemm = { git = "https://github.com/deepseek-ai/DeepGEMM" }

[tool.uv.extra-build-dependencies]
deep_gemm = [{ requirement = "torch", match-runtime = true }]
```

extra-build-dependencies및 의 사용 내역 extra-build-variables은 UV 캐시에 기록되므로 이러한 설정이 변경되면 해당 패키지가 재설치 및 재빌드됩니다. 예를 들어, 의 경우 프로젝트에서 사용되는 flash-attn버전을 업그레이드하면 새 버전의 를 사용하여 가 재빌드됩니다 .torchflash-attntorch

###### 동적 메타데이터

이 기능은 정적 메타데이터를 선언한 match-runtime = true패키지에서만 사용할 수 있습니다 flash-attn. 정적 메타데이터를 사용할 수 없는 경우, 종속성 해결 단계에서 uv를 사용하여 패키지를 빌드해야 합니다. 따라서 uv는 프로젝트 환경에 최종적으로 설치될 빌드 종속성의 버전을 확인할 수 없습니다.

즉, 정적 메타데이터를 선언하지 않으면 uv는 프로젝트 환경에 설치될 flash-attn버전을 확인할 수 없습니다 . 버전을 확인하기 전에 빌드를 먼저 수행해야 하기 때문입니다 .torchflash-attntorch

구체적인 예로, axolotl빌드 종속성을 늘려야 하는 인기 패키지가 있는데, 이 패키지는 torch프로젝트 환경에 설치된 버전에 따라 종속성이 달라지기 때문에 정적 메타데이터를 선언하지 않습니다. 이 경우 사용자는 torch프로젝트에서 사용할 정확한 버전을 지정한 다음, 해당 버전을 빌드 종속성에 추가해야 합니다.

axolotl예를 들어, 에 대해 빌드하려면 torch==2.6.0다음을 포함하세요 pyproject.toml.

```toml
[project]
name = "project"
version = "0.1.0"
description = "..."
readme = "README.md"
requires-python = ">=3.12"
dependencies = ["axolotl[deepspeed, flash-attn]", "torch==2.6.0"]

[tool.uv.extra-build-dependencies]
axolotl = ["torch==2.6.0"]
deepspeed = ["torch==2.6.0"]
flash-attn = ["torch==2.6.0"]
```

마찬가지로, 이전 버전에서는 flash-attn정적 메타데이터를 선언하지 않았기 때문에 match-runtime = true기본적으로 지원하지 않았습니다. axolotl하지만 와는 달리, flash-attn빌드 환경의 동적 속성에 따라 종속성을 변경하지 않았습니다. 따라서 사용자는 설정을 flash-attn통해 메타데이터를 미리 제공하여 dependency-metadata종속성 해결 단계에서 패키지를 빌드할 필요성을 없앨 수 있었습니다. 예를 들어, flash-attn메타데이터를 미리 제공하려면 다음과 같이 합니다.

```toml
[[tool.uv.dependency-metadata]]
name = "flash-attn"
version = "2.6.3"
requires-dist = ["torch", "einops"]
```

> `package`와 같은 패키지의 메타데이터를 확인하려면 해당 Git 저장소로 이동하거나 PyPIflash-attn 에서 패키지를 검색하여 소스 배포판을 다운로드하세요. 패키지 요구 사항은 일반적으로 `.config.js` 또는 `.config.js` 파일에서 찾을 수 있습니다.setup.pysetup.cfg

(패키지에 빌드된 배포판이 포함되어 있는 경우 압축을 풀어 해당 파일을 찾을 수 있습니다 METADATA. 하지만 빌드된 배포판이 있는 경우에는 uv에서 이미 메타데이터를 사용할 수 있으므로 메타데이터를 미리 제공할 필요가 없습니다.)

###### 빌드 격리 비활성화

빌드 격리 없이 패키지를 설치하려면 패키지 자체를 빌드하기 전에 해당 패키지의 빌드 종속성이 프로젝트 환경에 설치되어 있어야 합니다 .

예를 들어, 과거에는 빌드 격리 없이 설치하려면 먼저 프로젝트 환경에 패키지를 설치한 다음, 빌드 격리 없이 설치하기 위한 별도의 명령을 실행 해야 했습니다 cchardet.cythonsetuptoolscchardet

```bash
$ uv venv
$ uv pip install cython setuptools
$ uv pip install cchardet --no-build-isolation
```

no-build-isolation-packageuv는 설정 파일 pyproject.toml과 명령줄 플래그 를 통해 빌드 격리를 해제해야 하는 패키지를 지정할 수 있도록 하여 이 과정을 간소화합니다 --no-build-isolation-package. 또한, 빌드 격리를 해제하도록 표시된 패키지는 2단계 설치를 수행합니다. 먼저 빌드 격리를 지원하는 패키지를 설치한 후, 지원하지 않는 패키지를 설치합니다. 따라서 프로젝트의 빌드 종속성이 프로젝트 종속성으로 포함된 경우, uv는 빌드 격리 해제가 필요한 패키지를 설치하기 전에 해당 종속성을 자동으로 설치합니다.

예를 들어, 빌드 격리 없이 설치하려면 cchardet다음을 포함하세요 pyproject.toml.

```toml
[project]
name = "project"
version = "0.1.0"
description = "..."
readme = "README.md"
requires-python = ">=3.12"
dependencies = ["cchardet", "cython", "setuptools"]

[tool.uv]
no-build-isolation-package = ["cchardet"]
```

uv를 실행하면 uv sync먼저 torch프로젝트 환경에 설치되고, 그 다음 flash-attn(빌드 격리 없이) 설치됩니다. torch는 프로젝트 종속성이자 빌드 종속성이므로 빌드 환경과 런타임 환경 간에 버전이 torch일관되게 유지됩니다.

위 접근 방식의 단점은 빌드 종속성이 프로젝트 환경에 설치되어 있어야 한다는 점입니다. 이는 빌드 시와 런타임 시 모두 flash-attn필요한 경우 에 적합하지만, 빌드 시에만 필요한 경우 에는 적합하지 않습니다.torchcchardetcython

프로젝트 환경에 빌드 종속성이 포함되는 것을 방지하기 위해 uv는 빌드 종속성과 이를 필요로 하는 패키지를 분리할 수 있는 2단계 설치 프로세스를 지원합니다.

예를 들어, 빌드 종속성은 다음과 같이 cchardet선택적 그룹으로 분리할 수 있습니다 .build

```toml
[project]
name = "project"
version = "0.1.0"
description = "..."
readme = "README.md"
requires-python = ">=3.12"
dependencies = ["cchardet"]

[project.optional-dependencies]
build = ["setuptools", "cython"]

[tool.uv]
no-build-isolation-package = ["cchardet"]
```

위 내용을 고려하면, 사용자는 먼저 build선택적 그룹과 동기화한 다음, 빌드 종속성을 제거하기 위해 그룹 없이 동기화해야 합니다.

```bash
$ uv sync --extra build
$ uv sync
```

일부 패키지(예: )는 설치 단계 cchardet에서만 빌드 종속성이 필요합니다 . 반면 다른 패키지는 종속성 해결 단계 에서 프로젝트의 종속성을 해결하기 위해서라도 빌드 종속성이 있어야 합니다 .uv sync

이러한 경우, 하위 수준 API를 사용하여 빌드 종속성을 명령을 uv lock실행 하기 전에 설치할 수 있습니다 . 예를 들어 다음과 같은 경우:uv syncuv pip

```toml
[project]
name = "project"
version = "0.1.0"
description = "..."
readme = "README.md"
requires-python = ">=3.12"
dependencies = ["flash-attn"]

[tool.uv]
no-build-isolation-package = ["flash-attn"]
```

동기화하려면 다음 명령 시퀀스를 실행할 수 있습니다 flash-attn.

```bash
$ uv venv
$ uv pip install torch setuptools
$ uv sync
```

또는 사용자는 설정을 flash-attn통해 메타데이터를 미리 제공하여 dependency-metadata종속성 해결 단계에서 패키지를 빌드할 필요성을 없앨 수도 있습니다. 예를 들어, flash-attn메타데이터를 미리 제공하려면 다음과 같이 합니다.

```toml
[[tool.uv.dependency-metadata]]
name = "flash-attn"
version = "2.6.3"
requires-dist = ["torch", "einops"]
```

### 편집 가능 모드

기본적으로 프로젝트는 편집 가능 모드로 설치되므로 소스 코드 변경 사항이 환경에 즉시 반영됩니다. uv sync및 uv run두 옵션 모두 --no-editable플래그를 지원하며, 이 플래그를 사용하면 uv가 프로젝트를 편집 불가능 모드로 설치합니다. --no-editable는 Docker 컨테이너 빌드와 같이 원본 소스 코드에 대한 의존성 없이 배포 환경에 프로젝트를 포함해야 하는 배포 사용 사례에 적합합니다.

### 상충되는 의존성

uv는 선택적 종속성("extras") 및 종속성 그룹을 포함하여 프로젝트의 모든 종속성을 함께 해결합니다. 한 섹션에 선언된 종속성이 다른 섹션의 종속성과 호환되지 않으면 uv는 오류를 발생시키며 프로젝트 요구 사항을 해결하지 못합니다.

optional-dependencyuv는 충돌하는 종속성 그룹의 명시적 선언을 지원합니다. 예를 들어, 그룹 extra1과 가 호환되지 않음을 선언하려면 다음과 같이 합니다 extra2.

```toml
[tool.uv]
conflicts = [
    [
      { extra = "extra1" },
      { extra = "extra2" },
    ],
]
```

또는 개발 종속성 그룹 group1과 group2비호환성을 선언하려면 다음과 같이 하십시오.

```toml
[tool.uv]
conflicts = [
    [
      { group = "group1" },
      { group = "group2" },
    ],
]
```

자세한 내용은 해결 방법 문서를 참조하십시오(https://docs.astral.sh/uv/concepts/resolution/#conflicting-dependencies)

### 제한된 해상도 환경

프로젝트에서 지원하는 플랫폼이나 Python 버전이 제한적인 경우, environmentsPEP 508 환경 마커 목록을 허용하는 설정을 통해 해결 가능한 플랫폼 범위를 제한할 수 있습니다. 예를 들어, 잠금 파일을 macOS 및 Linux로 제한하고 Windows를 제외하려면 다음과 같이 합니다.

```toml
[tool.uv]
environments = [
    "sys_platform == 'darwin'",
    "sys_platform == 'linux'",
]
```
https://docs.astral.sh/uv/concepts/resolution/#limited-resolution-environments 자세한 내용은 해결 방법 문서를 참조하십시오 .

### 필수 환경

프로젝트에서 특정 플랫폼이나 Python 버전을 지원 해야 하는required-environments 경우, 설정을 통해 해당 플랫폼을 필수로 지정할 수 있습니다. 예를 들어, 프로젝트에서 Intel macOS를 지원하도록 요구하려면 다음과 같이 설정합니다.

```toml
[tool.uv]
required-environments = [
    "sys_platform == 'darwin' and platform_machine == 'x86_64'",
]
```

이 required-environments설정은 소스 코드 배포판을 공개하지 않는 패키지(예: PyTorch)에만 해당됩니다. 이러한 패키지는 해당 패키지에서 공개한 사전 빌드된 바이너리 배포판(휠) 세트에 포함된 환경 에만 설치할 수 있기 때문입니다.

https://docs.astral.sh/uv/concepts/resolution/#required-environments 자세한 내용은 해결 방법 문서를 참조하십시오 .

## Python 과 UV 의 구조적 한계

Python 은 의존성 격리를 제공하지 않으므로, `uv` 는 패키지가 선언된 의존성만 사용하고 다른 것은 사용하지 않도록 보장할 수 없습니다. 특히  워크스페이스의 경우, uv는 패키지가 다른 워크스페이스 구성원이 선언한 의존성을 가져오지 않도록 보장할 수 없습니다.

이 문장은 Python의 구조적 한계와 그 안에서 uv(혹은 다른 패키지 매니저)가 가진 **'보안 및 격리의 한계'**를 설명하고 있습니다.

핵심은 **"Python은 일단 설치된 패키지는 어디서든 다 보인다"**는 점입니다. 이를 이해하기 쉽게 세 부분으로 나누어 설명해 드릴게요.

1. "Python은 의존성 격리를 제공하지 않는다"
Python 실행 환경(Site-packages)에 패키지가 설치되면, 해당 환경에서 실행되는 모든 코드는 설치된 모든 패키지에 접근할 수 있습니다.

비유: 거실(실행 환경)에 있는 책꽂이에 책(패키지)을 꽂아두면, 집에 있는 누구든 그 책을 꺼내 읽을 수 있는 것과 같습니다. 특정 사람(특정 스크립트)만 특정 책을 보게 강제하는 기능이 Python 자체에는 없습니다.

2. "선언된 의존성만 사용하도록 보장할 수 없다"
개발자가 pyproject.toml에 pandas만 쓰겠다고 적어놨더라도, 만약 설치 환경에 누군가 몰래 requests를 깔아뒀다면, 코드에서 import requests를 해도 에러 없이 돌아갑니다.

uv는 내가 선언한 것들을 깔아주기는 하지만, **"선언하지 않은 것은 절대 import 못 하게 막는 벽"**을 세워주지는 못한다는 뜻입니다.

3. "워크스페이스(Workspace)에서의 문제"
이 부분이 가장 까다롭습니다. 보통 규모가 큰 프로젝트는 여러 개의 하위 패키지(워크스페이스)로 나뉩니다.

상황: * 패키지 A: requests를 사용함.

패키지 B: 아무 의존성도 없음.

문제: uv는 효율성을 위해 워크스페이스 내의 모든 패키지를 하나의 가상 환경에 같이 설치하는 경우가 많습니다. 이때, 패키지 B 개발자가 실수로 자기 설정 파일에 적지도 않은 import requests를 써버려도 코드가 작동해 버립니다. 패키지 A 때문에 이미 설치되어 있기 때문입니다.

왜 이게 위험한가요?
나중에 배포할 때 터집니다: 내 컴퓨터(워크스페이스 환경)에서는 잘 돌아가던 패키지 B를 따로 떼어내서 서버에 올리면, 그제서야 requests가 없다며 에러가 발생합니다.

의존성 지옥: 내가 직접 관리하지 않는 "유령 의존성"에 내 코드가 의존하게 되어 유지보수가 힘들어집니다.

요약하자면
"Python 시스템상 한 바구니에 담긴 사과는 누구나 집어 먹을 수 있다. uv가 사과를 바구니에 예쁘게 담아주긴 하지만, 특정 사람이 허락된 사과만 먹도록 감시하는 경찰관 역할까지는 못 한다"는 뜻입니다.

혹시 현재 uv를 사용하면서 워크스페이스 내부에서 import 에러나 의존성 충돌 문제를 겪고 계신가요? 원하신다면 uv에서 이 문제를 최소화할 수 있는 설정법을 알려드릴 수 있습니다.
