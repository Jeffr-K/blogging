## 프로토콜의 다양성: Transporters

NestJS 마이크로서비스 엔진의 추상화 아래에는 실제 데이터를 실어 나르는 **트랜스포터(Transporter)**들이 있다.

TCP는 직접 소켓을 열고, Redis는 Pub/Sub 채널을 사용하며, RabbitMQ는 큐(Queue) 시스템을 이용한다. 겉보기에는 `ClientProxy`를 통해 똑같이 메시지를 보내는 것 같지만, 각 트랜스포터가 내부적으로 **어떻게 패킷을 포맷팅하고 네트워크에 실어 보내는지**는 천차만별이다. 이번 아티클에서는 주요 트랜스포터들의 내부 구현 차이점을 딥다이브해 본다.

---

## 1. TCP Transporter (기본 전송 방식)

TCP 트랜스포터는 가장 성능이 좋고 단순하다. Node.js의 `net` 모듈을 사용하여 직접 소켓을 연다.

### 데이터 프레이밍 (Data Framing)

TCP는 단순한 바이너리 스트림이다. 따라서 메시지의 "시작"과 "끝"을 구분하는 장치가 필요하다.

- **내부 동작**: NestJS TCP 트랜스포터는 메시지 앞에 **길이 정보(Length)**를 붙인 패킷(예: `[Length][JSON Data]`)을 사용한다.
- 수신 측에서는 이 길이를 먼저 읽고, 해당 길이만큼 데이터를 다 받을 때까지 버퍼(Buffer)에 담아 기다린다. 이를 **'프레임워크 레벨의 프레이밍'**이라 한다.

---

## 2. Redis Transporter (Pub/Sub 모델)

Redis 트랜스포터는 Redis의 **`PUBLISH`**와 **`SUBSCRIBE`** 명령어를 기반으로 동작한다.

- **서버**: 지정된 채널 이름(Pattern)을 `SUBSCRIBE` 하여 기다린다.
- **클라이언트**: `PUBLISH` 명령어로 메시지를 보낸다.
- **요청-응답 방식**: 클라이언트는 임시 응답 채널(예: `request_pattern.res`)을 생성하고 이를 구독한 뒤, 서버에 "응답은 이 채널로 줘"라는 정보를 담아 보낸다. 서버가 응답 채널로 결과를 돌려주는 **브로커 기반의 라우팅**이 핵심이다.

---

## 3. RabbitMQ Transporter (AMQP 프로토콜)

RabbitMQ는 가장 강력한 메시지 큐(Message Queue)인 AMQP 프로토콜을 사용한다.

- **큐와 익스체인지(Queue & Exchange)**: NestJS는 내부적으로 비동기 통신을 위해 큐를 생성하고 바인딩(Binding)한다.
- **내구성(Durability)**: 메시지가 안전하게 도착했는지 확인하는 `ack`(Acknowledgement) 메커니즘을 지원한다.
- **내부 동작**: `ClientProxyRabbitMQ` 클래스는 `amqplib` 라이브러리를 사용하여 채널을 열고, 인메모리 맵을 통해 비동기 응답(RabbitMQ의 `replyTo` 기능 활용)을 관리한다.

---

## 4. 트랜스포터 선택 가이드 (내부 관점에서)

- **성능이 최우선인 경우**: TCP (오버헤드가 가장 적음)
- **간단한 알림/이벤트 중심인 경우**: Redis (설정이 간편하고 가벼움)
- **높은 신뢰성과 복잡한 라우팅이 필요한 경우**: RabbitMQ (재시도 로직과 영속성 보장)
- **성능과 순서 보장이 모두 중요한 대용량 스트림**: Kafka (버전 7.x 이상부터 강력 지원)

---

## 요약

모든 트랜스포터는NestJS의 **전송 계층 추상화** 덕분에 외형은 같아 보이지만, **내부의 패킷 전송 전략과 라이브러리 활용 방식**은 확연히 다르다.

- TCP의 직접적인 소켓 제어와 프레이밍 기법
- Redis의 채널 기반 비동기 응답 라우팅
- RabbitMQ의 큐 시스템과 신뢰성 보장 메커니즘

이 내부 구현의 차이를 이해하면, 우리 서비스의 트래픽 특성에 가장 적합한 전송 방식을 선택하고 문제를 해결할 수 있는 혜력이 생긴다.

다음 아티클에서는 이러한 지식을 바탕으로, NestJS가 기본 지원하지 않는 프로토콜을 위한 **커스텀 트랜스포터를 직접 구현**하는 미션에 도전해 본다.
