## 흐름의 과부하: 배압(Backpressure)이란?

서버의 CPU나 메모리보다 훨씬 더 빠른 속도로 데이터 유입이 발생할 때, 시스템은 과부하에 걸린다. 특히 수많은 비동기 요청을 동시에 처리해야 하는 NestJS 백엔드에서, 데이터를 소화하는 속도보다 들어오는 속도가 빠를 때 발생하는 이 불균형을 해결하는 기법이 바로 **배압(Backpressure) 관리**다.

이번 아티클에서는 `RxJS` 오퍼레이터를 사용하여 NestJS 애플리케이션의 안정성을 극대화하는 배압 관리 전략과 정교한 에러 전파 메커니즘을 딥다이브해 본다.

---

## 1. 지능형 샘플링과 전송량 제어

대용량 가동 데이터를 실시간 수집하는 상황을 가정해 보자. 1초에 만 번의 데이터가 들어올 때 이를 모두 DB에 넣으려고 하면 서버는 곧 멈춘다.

- **`sampleTime(1000)`**: 1초마다 가장 최근의 데이터 하나만 골라서 처리한다. 가시적인 모니터링 시스템에서 매우 효율적이다.
- **`throttleTime(1000)`**: 데이터 유입이 시작되면 첫 데이터만 처리하고 1초 동안 다른 유입을 무시한다. (중복 요청 방지)
- **`debounceTime(500)`**: 데이터 유입이 완전히 멈추고 0.5초가 지났을 때 마지막 데이터를 처리한다. (검색어 입력 등)

---

## 2. 딥다이브: 버퍼링(Buffering) 전략

배압을 해결하는 가장 고전적이면서도 강력한 방법은 **'기다렸다가 한꺼번에 처리하는 것'**이다.

- **`bufferCount(100)`**: 데이터가 100개 쌓일 때까지 기다렸다가 배열로 묶어 DB 벌크 연산(Bulk Insert)을 수행한다.
- **`bufferTime(2000)`**: 데이터 양에 관계없이 2초마다 쌓인 데이터를 한 번에 처리한다.

NestJS 마이크로서비스 전송 엔진과 결합하면 네트워크 왕복(Round-trip) 횟수를 획기적으로 줄일 수 있다.

---

## 3. 에러 전파의 차단과 복구 (Resilience)

비동기 스트림에서 **에러는 곧 종료**를 의미한다. 하지만 우리 서비스는 에러가 나도 계속 돌아가야 한다.

- **`catchError()`**: 하위 스트림에서 터진 에러를 포착한다. 여기서 `EMPTY`나 `of(DEFAULT_VALUE)`를 반환하면 스트림은 끊기지 않고 계속 흐른다.
- **`retryWhen()`**: 에러가 났을 때 즉시 재시도하는 것이 아니라, 특정 조건(예: 2초 뒤에 다시 시도)에 맞춰 지능적으로 재구독을 수행한다.

---

## 4. 실전: 윈도잉(Windowing)을 이용한 트래픽 통계

- **`windowTime(60000)`**: 1분 단위의 '새로운 스트림(Window)'을 계속해서 만들어낸다.
- 각 윈도우 스트림을 `count()` 오퍼레이터와 연결하면, 단 몇 줄의 코드만으로 분당 요청 수(RPM) 같은 정밀한 메트릭 수집 엔진을 구축할 수 있다.

---

## 요약

배압 관리는 **"시스템의 한계를 인정하고 흐름을 조율하는 지혜"**다.

- `throttle`과 `debounce`로 불필요한 연산을 원천 차단하자.
- `buffer` 전략을 통해 DB와 네트워크 오버헤드를 줄이자.
- `catchError`와 `retry` 계열 오퍼레이터로 에러에도 죽지 않는 불사조 같은 스트림을 설계하자.

이 지식을 갖추었다면, 이제 대규모 트래픽 앞에서도 당당히 "우리 서버는 안전합니다"라고 말할 수 있는 자격이 생긴다.
