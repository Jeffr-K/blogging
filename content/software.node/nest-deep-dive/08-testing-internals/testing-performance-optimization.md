## 시간은 금이다: 테스트 속도의 함정

프로젝트 규모가 커지면 테스트 케이스는 수천 개로 늘어난다. 만약 `NestFactory.create()`와 유사한 `TestingModule`의 `compile()` 과정을 매 테스트(`.spec.ts`)마다 반복한다면 어떻게 될까? 테스트 실행 속도는 기하급수적으로 느려지고, 개발자의 생산성은 곤두박질친다.

이번 딥다이브의 마지막 아티클에서는 **테스트 실행 성능**을 극적으로 높이기 위해 `TestingModule`을 재사용하거나, 병렬로 실행하고, 리소스 부하를 제어하는 고도의 테스팅 인프라 구축 전략을 파헤쳐 본다.

---

## 1. 딥다이브: TestingModule 재사용 전략

매 `beforeEach`에서 `compile()`을 부르는 것은 가장 안전하지만 가장 느리다.

- **상태 전이(Stateful)**가 없는 서비스라면, `beforeAll`에서 한 번만 `compile()`하고 이를 모든 `it` 테스트에서 공유(Sharing)하는 것이 수 배 이상 빠르다.
- **유의**: 모킹된 정보(`jest.spyOn`)가 다음 테스트에 영향을 주지 않도록 `jest.clearAllMocks()`로 초기화하는 세밀한 관리가 필요하다.

---

## 2. 병렬 실행(Parallelize)과 프로세스 격리

Jest는 기본적으로 파일을 기준으로 별도의 프로세스(Worker)에서 테스트를 실행한다.

- **CPU Core 활용**: `--maxWorkers` 옵션을 주어 프로세서의 모든 코어를 사용하게 하면 테스트 시간을 비약적으로 단축할 수 있다.
- **데이터베이스 충돌 해결**: 병렬 실행 시 모든 테스트가 하나의 DB를 같이 쓰면 에러가 난다. 각 프로세스(Worker)마다 **동적인 데이터베이스 스키마(예: `test_db_1`, `test_db_2`)**를 생성하고 할당하는 지능형 스크립트로 해결해야 한다.

---

## 3. 테스트 리소스 오버헤드: --runInBand와 메모리

테스트가 일정 수준 이상 늘어나면 오히려 병렬 실행이 더 느려지거나 메모리 누수(OOM)가 날 수 있다.

- **원인**: 각 워커 프로세스가 `TestingModule`을 띄울 때마다 독립적인 Node.js 런타임과 NestJS 컨테이너 메모리를 차지하기 때문이다.
- **해결**: 소규모 환경이나 CI(Github Actions) 환경이라면 `--runInBand`를 사용하여 순차적으로 실행하는 것이 전체 시스템 부하 측면에서 더 유리할 수 있다.

---

## 4. 실전: 성능을 좌우하는 SWC 도입

- **`@swc/jest`**: `ts-jest`보다 수 배는 빠른 컴파일 속도를 제공한다.
- **내부 원리**: TypeScript의 타입을 Rust 기반의 초고속 컴파일러인 SWC로 변환하여, 테스트 전처리(Preprocessing) 시간을 획기적으로 단축한다. 대규모 프로젝트의 테스트 부팅 속도를 결정짓는 필살기다.

---

## 요약: 테스팅 딥다이브를 마치며

테스트는 코드의 **안전장치**이기도 하지만, 개발자가 코드를 작성하는 **즐거움(DX)**과도 직결된다.

- `TestingModule`의 수명주기를 조절하여 부팅 시간을 아끼자.
- 하드웨어의 힘을 빌려 병렬로 테스트를 집도하자.
- SWC와 같은 최신 컴파일러를 도입하여 루프 타임을 줄이자.
