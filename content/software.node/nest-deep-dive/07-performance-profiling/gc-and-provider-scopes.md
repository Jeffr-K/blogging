## 메모리의 흔적: 가비지 컬렉션(GC)

Node.js 가비지 컬렉션은 런타임에 사용하지 않는 객체를 자동으로 정리한다. 하지만 우리가 만든 NestJS 프로바이더(Provider)들이 **어떤 수명주기(Scope)**를 가지느냐에 따라 GC가 해야 할 일의 양과 메모리 사용량은 천차만별이 된다.

이번 아티클에서는 `DEFAULT`, `REQUEST`, `TRANSIENT`라는 3가지 프로바이더 스코프가 가비지 컬렉션(특히 V8 엔진의 Scavenge 알고리즘)에 어떤 영향을 미치는지 딥다이브해 본다.

---

## 1. DEFAULT (Singleton) - GC의 효자

NestJS의 기본 스코프인 `Singleton`은 애플리케이션 시작 시 단 한 번 생성되고 종료 전까지 메모리에 머문다.

- **메모리 영향**: 힙 메모리의 'Old Space'로 일찍 이동하여, 빈번한 마이너 GC(Scavenge) 대상에서 제외된다.
- **장점**: 매 요청마다 새로운 객체를 만들고 버리는 비용이 전혀 없다. (가장 권장되는 방식)

---

## 2. 딥다이브: REQUEST 스코프의 위험성

`@Injectable({ scope: Scope.REQUEST })`를 사용하면, 매 HTTP 요청마다 새로운 프로바이더 인스턴스가 생성된다.

- **메모리 폭주**: 1초에 1,000건의 요청이 들어오면 1,000개의 객체가 생성되고 소멸된다. 이는 V8 엔진의 'New Space'를 가득 채우게 되며, **잦은 가비지 컬렉션(Young Generation GC)**을 유발한다.
- **연쇄 인스턴스화**: 특정 서비스가 `REQUEST` 스코프라면, 그 서비스를 주입받는 상위 컨트롤러와 모든 연관 프로바이더 또한 강제로 `REQUEST` 스코프가 된다. (이것이 진정한 성능 저하의 주범이다.)

---

## 3. TRANSIENT 스코프: 새로운 인스턴스마다

주입되는 곳마다 새로운 인스턴스를 만드는 방식이다.

- **용도**: 로거(Logger)처럼 각 클래스마다 독립적인 상태가 필요한 경우 유용하다.
-**GC 영향**: `REQUEST` 스코프보다는 덜하지만, 여전히 객체가 자주 생성되고 버려지므로 메모리 단편화(Fragmentation)에 주의해야 한다.

---

## 4. 실전 최적화: REQUEST 스코프 줄이기

- **Context 캐싱**: `REQUEST` 스코프가 필요한 유일한 이유는 현재 요청한 유저(`req.user`) 정보를 알고 싶을 때가 많다.
- **대안**: `@createParamDecorator`를 사용하거나, `AsyncLocalStorage`를 도입하여 싱글톤 서비스 내에서 현재 요청의 컨텍스트를 읽어오도록 설계하면, 성능과 가비지 컬렉션 효율을 극대화할 수 있다.

---

## 요약

프로바이더의 스코프 선택은 단순히 디자인 패턴의 문제가 아니라, **런타임 메모리 관리 수준**의 결정이다.

- 가능하면 모든 프로바이더를 `DEFAULT(Singleton)`로 유지하자.
- `REQUEST` 스코프를 쓸 때는 연쇄적인 오버헤드와 GC 부하를 반드시 고려하자.
- `AsyncLocalStorage`를 활용하여 싱글톤으로도 요청 컨텍스트를 처리하는 지능형 아키텍처를 구축하자.

이 지식을 바탕으로 대규모 트래픽 앞에서도 메모리 누수 없이 안정적으로 동작하는 강력한 고성능 서버를 설계할 수 있게 된다.
