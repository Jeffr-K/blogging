## 추상화의 대가: 성능과 가독성 사이

우리가 NestJS를 찬양하는 이유는 데코레이터(`@`)와 의존성 주입(DI)이 주는 강력한 추상화 때문이다. 하지만 모든 추상화에는 비용(Cost)이 따른다.

클래스에 데코레이터를 붙일 때마다 메타데이터가 생성되고, 객체를 생성할 때마다 DI 컨테이너가 맵을 뒤지고 그래프를 그린다. 과연 이 기능들이 우리 애플리케이션의 런타임 성능에 어떤 영향을 미칠까? 이번 아티클에서는 NestJS의 핵심 기능들이 실제 CPU와 메모리에 어떤 오버헤드를 주는지 **성능 벤치마킹** 관점에서 딥다이브해 본다.

---

## 1. 부트스트래핑 타임 분석 (Bootstrapping Time)

프로젝트 규모가 커질수록 `NestFactory.create()`의 실행 시간은 길어진다.

- **원인**: 수백 개의 모듈과 수천 개의 프로바이더를 스캔하고 인스턴스화하는 과정이 순수 자바스크립트 객체 생성보다 훨씬 복합적이기 때문이다.
- **측정**: `console.time`을 사용하여 부트스트래핑 단계를 모니터링해 보면, 프로바이더 수가 늘어날 때마다 선형적으로 시작 시간이 증가하는 것을 볼 수 있다. (하지만 이는 런타임 성능과는 무관한 단 한 번의 비용이다.)

---

## 2. 딥다이브: 데코레이터의 런타임 오버헤드

데코레이터는 사실상 **'함수 호출'**이다. 클래스가 매번 인스턴스화될 때마다(특히 `REQUEST` 스코프일 경우), 상속 구조가 복잡할수록 데코레이터 함수들의 실행 횟수가 늘어난다.

- **성능 차이**: 순수 자바스크립트 클래스 생성 vs NestJS의 `@Injectable` 클래스 생성. 벤치마킹 도구(Benchmark.js)로 돌려보면, 수백만 번 반복 시 미세한 나노초(ns) 단위의 차이가 발생하지만 일반적인 API 요청 수준에서는 무시할 수 있는 수준이다.

---

## 3. 의존성 주입(DI)의 조회 비용

`InstanceLoader`가 미리 인스턴스를 하나씩 만들어두는(Singleton) 정책은 런타임 성능에 아주 유리하다.

- **내부 동작**: 요청이 올 때마다 `Map`에서 이미 만들어진 객체를 가져오는 행위는 `O(1)`의 시간 복잡도를 가진다. 따라서 주입 계층이 10단위로 깊어져도 검색 비용은 거의 증가하지 않는다.

---

## 4. 실전 성능 최적화: 정적 분석과 트리 쉐이킹

- **트리 쉐이킹(Tree Shaking)**: 사용하지 않는 모듈이나 프로바이더가 컨테이너에 등록되지 않도록 하는 것이 메모리 절감의 핵심이다.
- **컴파일 타임 최적화**: `ts-loader` 대신 `swc-loader` 등을 사용하여 데코레이터 메타데이터 생성 속도를 높이는 것이 빌드 성능 최적화의 첫 단추다.

---

## 요약

이 모든 추상화가 주는 편리함에 비해 **성능 비용은 의외로 매우 낮다.**

- 부트스트래핑(시작 시간)은 모듈 수에 비례하여 늘어난다.
- 싱글톤 스코프를 유지한다면 DI 조회 비용은 무시할 수 있는 수준이다.
- 데코레이터 오버헤드보다 데이터베이스나 네트워크 I/O 지연이 훨씬 더 큰 병목 지점이다.

이 지식을 바탕으로 성능에 대한 막연한 두려움을 버리고, 안심하고 NestJS의 강력한 추상화 기능을 활용하자. (단, 과도한 `REQUEST` 스코프 남용은 금물이다.)

다음 아티클에서는 이러한 성능 비용의 또 다른 한 축인 **가비지 컬렉션(GC)과 프로바이더 스코프 관리 전략**을 딥다이브해 본다.
