## E2E 테스트 데이터 독립성과 시더(Seeder) 활용 전략

E2E 테스팅이 실패하는 가장 큰 원인은 '코드 버그'가 아니라 **'데이터 오염'**입니다. 첫 번째 테스트가 생성한 데이터가 두 번째 테스트의 결과에 영향을 미치는 순간, 우리의 테스트는 신뢰를 잃고 '가끔 깨지는(Flaky)' 골칫덩이가 됩니다. 모든 E2E 테스트가 깨끗한 도화지 위에서 그려질 수 있도록 돕는 데이터 관리 전략을 알아봅니다.

---

### 1. 테스트 데이터 팩토리 (Factory Pattern)

테스트마다 매번 고정된 JSON을 하드코딩하는 것은 유지보수의 재앙입니다. 엔터티의 기본 구조를 갖춘 **팩토리**를 사용하여 동적으로 데이터를 생성하십시오.

```typescript
// test/factories/user.factory.ts
import * as f from 'faker'; // 또는 @faker-js/faker

export const userFactory = (overrides?: Partial<User>) => ({
  email: f.internet.email(),
  password: 'password123',
  nickname: f.name.findName(),
  ...overrides, // 특정 값만 덮어쓰기 가능
});
```

### 2. 데이터 시더 (Seeder)와 사전 준비

테스트가 시작되기 전, 베이스가 되는 데이터(카테고리 목록, 기본 관리자 계정 등)를 DB에 밀어 넣는 과정입니다.

- **Global Seeder**: 전체 테스트 스위트가 시작되기 전 딱 한 번 실행. (마스터 데이터용)
- **Local Seeder**: 특정 `describe`나 `it` 시작 전 실행. (해당 테스트 케이스 전용 유저 등)

### 3. 데이터베이스 리셋 전략: "깨끗하게 맑게 자신 있게"

E2E 테스트 후에는 반드시 흔적을 지워야 합니다.

1. **DB 재구축**: 매 테스트마다 `Drop table` 후 `Create table`. (가장 안전하지만 가장 느림)
2. **TRUNCATE**: 모든 테이블의 데이터만 삭제. (추천하는 방식)
3. **랜덤 식별자 활용**: 데이터를 지우지 않는 대신, 모든 전용 데이터에 고유한 Prefix(예: `test_user_...`)를 붙여 서로 겹치지 않게 관리.

### 4. 시니어의 조언: "실제 상용 데이터(Production Dump)를 쓰지 마라"

많은 팀이 귀찮다는 이유로 상용 DB를 덤프 떠서 E2E 테스트 환경에 넣습니다.

- **위험성 1**: 개인정보 유출 리소스가 매우 큽니다. 
- **위험성 2**: 데이터 양이 너무 많아져 테스트 실행 속도가 처참해집니다. 
- **해결책**: 오직 테스트에 필요한 **'최소한의 유의미한 데이터'**만을 코드로 정의하고 생성하십시오. 테스트 데이터 자체가 시스템의 요구사항을 설명하는 또 다른 명세서가 되어야 합니다.

---

### 전문가의 한마디: "데이터 고립은 신뢰의 근간이다"

테스트가 실패했을 때 로그를 보며 "이 데이터가 어디서 왔지?"라고 고민하는 시간을 없애십시오. 

각 테스트 케이스가 자신의 데이터를 직접 생성하고 직접 청소하는 **'완결성'**을 가질 때, 여러분의 E2E 테스트는 어떤 배포 환경에서도 당당하게 "Green"을 띄울 수 있을 것입니다.
