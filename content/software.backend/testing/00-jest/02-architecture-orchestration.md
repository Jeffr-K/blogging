## Jest 아키텍처: 병렬 실행과 워커 스레드 오케스트레이션

Jest가 다른 테스팅 도구보다 압도적으로 빠른 이유는 단순히 코드가 효율적이기 때문만이 아닙니다. 그 밑바닥에는 정교하게 설계된 **'병렬 실행 엔진'**이 자리 잡고 있습니다. Jest가 우리의 CPU 자원을 어떻게 활용하고, 테스트 파일 간의 고립을 어떻게 보장하는지 그 내부 아키텍처를 파헤쳐 봅시다.

---

### 1. 워커 스레드 (Worker Threads) 시스템

Jest는 기본적으로 **'파일 단위의 병렬성'**을 채택합니다.

- **Orchestrator**: 메인 프로세스는 테스트 파일들의 목록을 만들고 작업을 배분하는 지휘자 역할을 합니다.
- **Worker**: 개별 테스트 파일은 독립된 자식 프로세스(또는 워커 스레드)에서 실행됩니다.
- **이점**: 하나의 파일에서 `Infinity Loop`가 발생하거나 메모리 누수가 생겨도 다른 테스트 파일의 실행에는 영향을 주지 않습니다.

### 2. 가상 환경의 마법: Sandbox

각 워커에서 실행되는 테스트는 완전히 고립된 전역 상태를 가집니다.

- **독립성**: 테스트 파일 A에서 `global.foo = 'bar'`라고 설정해도 테스트 파일 B에는 아무런 영향을 주지 않습니다.
- **원리**: Jest는 각 테스트 파일마다 새로운 가상 환경(JSDOM 기반 혹은 Node 환경)을 생성하고 그 안에서 코드를 실행합니다. 이는 테스트 간의 오염(Pollution)을 원천 차단하는 강력한 무기입니다.

### 3. 지능형 캐싱 (Intelligent Caching)

Jest는 파일의 소스 코드를 변환(Transform) 한 결과를 디스크에 캐싱합니다.

- **빠른 재시작**: Babel이나 TypeScript로 컴파일된 결과물이 이미 캐시에 있다면, 테스트 실행 시 컴파일 단계를 건너뛰고 즉시 코드를 실행합니다.
- **의존성 그래프**: 어떤 파일이 수정되었을 때 그 파일을 참조하는 테스트 파일만 골라서 다시 실행할 수 있는 비결도 바로 이 의존성 캐시 덕분입니다.

---

### 결론: 아키텍처가 성능을 만든다

우리가 무심코 `npm test`를 누를 때, 내부에서는 수십 개의 멀티스레드가 동시에 깨어나 의존성 그래프를 분석하고 캐시를 대조하며 병렬로 작업을 수행합니다.

이 정교한 오케스트레이션 덕분에 우리는 수천 개의 테스트 케이스 앞에서도 기다림 없이 쾌적한 개발 경험을 누릴 수 있는 것입니다. 시스템의 속도는 도구가 우리 대신 얼마나 지능적으로 자원을 관리하느냐에 달려 있습니다.
