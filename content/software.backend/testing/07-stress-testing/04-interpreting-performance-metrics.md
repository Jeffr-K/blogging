## 성능 리포트 해석 가이드: P99 지표와 병목 지점(Bottleneck) 분석

부하 테스트를 마친 뒤 K6 리포트를 받아 들었을 때, 대부분의 초급자는 "그래, 서버는 안 터졌고 평균 속도는 200ms네. 합격!"이라고 생각합니다. 하지만 고수들은 그 숫자들 이면에 가려진 **'위험의 전조'**를 읽어냅니다. 숫자 뒤에 숨은 진실을 밝히는 성능 데이터 해석 법을 제안합니다.

---

### 1. 평균(Average)의 함정: "우리 유저의 1%는 고통받고 있다"

평균값은 시스템의 전체적인 상태를 보여주지만, 개별 사용자의 불쾌한 경험을 교묘하게 가립니다.

- **평균 200ms**: 서비스가 매우 쾌적해 보입니다.
- **P99 5000ms**: 전체 사용자 중 상위 1%는 요청 하나에 5초를 기다리고 있습니다. 만약 동시 접속자가 1만 명이라면, 100명이 탈퇴를 고민하고 있다는 뜻입니다.

**결론**: 시스템의 안정성을 판단하는 기준은 평균이 아니라 항상 **P95** 혹은 **P99**여야 합니다. 꼬리 지연 시간(Tail Latency)이 길어지는 원인을 찾는 것이 최우선 과제입니다.

### 2. RPS와 Latency의 상관관계: 병목의 시작점 찾기

- **RPS (Request Per Second)**: 초당 처리량.
- **Latency**: 응답 시간.

부하가 늘어남에 따라 RPS가 정체되고 Latency가 급격히 우상향(Hockey Stick) 한다면, 시스템이 포화 상태(Saturation)에 도달한 것입니다.

- **Latency만 늘어남**: 네트워크 대역폭 부족이나 외부 API의 지연 의심.
- **RPS가 떨어지며 에러 발생**: DB Connection Pool 부족이나 Thread Pool 고갈 의심.

### 3. 주요 병목 지점(Bottleneck) 3인방

1. **CPU Bound**: 복잡한 비즈니스 계산, JSON 직렬화/역직렬화 과다. (Node.js의 경우 이벤트 루프 지연으로 직결됨)
2. **I/O Bound**: 느린 쿼리, 인덱스 누락, 외부 API 응답 대기. (가장 흔한 병목)
3. **Memory Bound**: 가비지 컬렉션(GC)의 잦은 동작으로 인한 시스템 멈춤(Stop-the-world).

### 전문가의 조언: "숫자는 거짓말을 하지 않되, 질문하지 않으면 답하지 않는다"

리포트의 숫자만 보고 안심하지 마십시오.

- "부하가 올라가도 P99가 일정하게 유지되는가?"
- "에러율이 0%인데 왜 응답 속도가 점점 느려지는가?"

이런 질문들을 끊임없이 던지며 리포트를 파고드십시오. K6가 뽑아낸 데이터는 여러분의 시스템이 **'어느 지점에서 무너질 기미를 보이는지'** 미리 알려주는 예언서입니다. 지표를 다스리는 자가 시스템의 운명을 결정합니다.
