## 실전 사례: 대규모 이벤트 오픈 시의 트래픽 폭주 대응 및 튜닝

"운영 서버가 뻗었습니다." 이 한마디는 모든 엔지니어의 악몽입니다. 특히 마케팅 부서에서 수만 명의 유저에게 '선착순 타임 세일' 푸시 알림을 발송한 직후라면 더욱 그렇죠. 이번 사례에서는 K6를 통해 이러한 극한의 상황을 미리 재현하고, 발견된 **DB 커넥션 병목**을 어떻게 해결했는지 그 기술적 대응 과정을 공유합니다.

---

### 1. 테스트 시나리오: 블랙 프라이데이 타임 세일

- **상황**: 낮 12시 정각에 선착순 100명에게 상품을 100원에 판매.
- **예상 트래픽**: 평소의 20배 수준인 초당 5,000건(RPS)의 요청이 1초 이내에 몰림.
- **K6 시나리오**: `Spike Testing` 전략을 사용하여 10초 만에 VU를 1,000명까지 수직 상승시킴.

### 2. 발견된 문제: 'Connection Timeout'의 연쇄 폭발

테스트 결과, P99 응답 시간이 10초를 넘어가며 서버가 `504 Gateway Timeout`을 내뱉기 시작했습니다.

- **분석 결과**: CPU와 메모리는 여유로웠지만, DB의 **`Wait Queue`**가 가득 찼습니다.
- **원인**:
    1. 상품 정보를 가져올 때 `is_selling` 컬럼에 인덱스가 없어 풀 스캔 발생.
    2. 느려진 쿼리가 DB 커넥션을 오래 붙잡고 있음.
    3. NestJS 앱의 TypeORM 커넥션 풀(Default 10)이 순식간에 고갈되어, 뒤따라오는 유저들이 커넥션을 얻지 못해 대기하다 타임아웃 발생.

### 3. 대응 및 튜닝 과정

우리는 두 가지 처방을 즉시 내리고 K6를 다시 돌렸습니다.

1. **DB 튜닝**: 자주 조회되는 조건절 컬럼에 `Index`를 생성하여 쿼리 속도를 500ms에서 5ms로 단축.
2. **커넥션 풀 확장**: NestJS 설정에서 `poolSize`를 50으로 조절하고, 유휴 커넥션을 미리 생성해두는 설정을 추가.

```typescript
// src/database/database.config.ts
TypeOrmModule.forRoot({
  // ...
  extra: {
    max: 50, // 커넥션 풀 확장
    min: 20, // 유휴 커넥션 유지
    connectionTimeoutMillis: 2000, // 대기 시간 단축
  },
})
```

### 4. 사후 분석: 튜닝 후의 평화

재테스트 결과, 동일한 부하에서 P99 지연 시간은 **200ms**로 안정화되었고, 에러율은 **0%**를 기록했습니다. 이로써 마케팅 이벤트 당일 실제 시스템이 무너지지 않을 것이라는 기술적 확신(Guarantee)을 얻었습니다.

---

### 전문가의 총평: "훈련은 피를 덜 흘리게 한다"

성능 테스트는 배포 전의 예방 접종입니다.

실제 트래픽이 닥치기 전에 K6를 통해 시스템을 고의로 망가뜨려 보십시오. 그 과정에서 발견되는 병목 지점이 바로 여러분의 시스템이 성장해야 할 방향입니다. 숫자로 증명되지 않은 성능은 희망 고문에 불과합니다. K6를 통해 **'숫자로 증명된 안정성'**을 확보하십시오.
