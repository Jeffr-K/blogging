## 단위 테스트의 한계와 속성 기반 테스팅의 보완성

많은 개발자가 "단위 테스트(Unit Test)를 꼼꼼히 짰는데 왜 상용 환경에서 예외가 발생하죠?"라고 묻습니다. 그 답은 간단합니다. 단위 테스트는 우리가 **'아는 위험'**만 테스트하기 때문입니다. 속성 기반 테스팅(Property-based Testing)은 우리가 **'모르는 위험(Unknown Unknowns)'**을 찾아내는 가장 강력한 보완재입니다.

---

### 1. 인간의 편향: "우리는 성공할 예제만 생각한다"

단위 테스트를 짤 때 우리는 무의식적으로 '정상적인 범위'를 먼저 생각합니다.

- 이름 입력 필드 테스트: `"홍길동"`, `"John"`
- 수량 입력 필드 테스트: `1`, `10`, `100`

이러한 **'성공 사례 위주의 예제'**들은 코드 커버리지를 100%로 만들 수는 있지만, `Unicode 이모지`가 섞인 이름이나 `천문학적인 큰 수`가 입력되었을 때의 잠재적 크래시는 잡아내지 못합니다. 속성 기반 테스팅은 인간의 편향을 배제하고 기계적으로 모든 경계값(Edge Case)을 타격합니다.

### 2. 단위 테스트 vs 속성 기반 테스팅 비교

| 구분 | 예시 기반 단위 테스트 (Unit Test) | 속성 기반 테스팅 (PBT) |
| :--- | :--- | :--- |
| **데이터 결정** | 사람이 직접 정의 (`1, 2, "test"`) | 도구가 무작위 생성 (`-999, "", 🦄`) |
| **검증 방식** | 기대값과 결과값의 일치 (`toBe(3)`) | 결과값이 속성을 만족하는지 (`isTrue()`) |
| **주요 목적** | 의도한 기능의 정상 동작 확인 | 예외 케이스 및 불변성(Invariant) 증명 |
| **장점** | 비즈니스 시나리오 가독성이 좋음 | 인간이 상상 못한 버그 발견 가능 |

### 3. 상호보완적 관계: 하나만으로는 부족하다

속성 기반 테스팅이 만능은 아닙니다.

- **단위 테스트**는 비즈니스 기획서의 내용을 가장 잘 대변합니다. "사용자가 A를 누르면 B가 되어야 한다"는 명확한 스토리텔링은 단위 테스트의 몫입니다.
- **속성 기반 테스팅**은 그 비즈니스 로직의 '근간'을 지탱합니다. "어떤 상황에서도 시스템의 데이터 정합성은 깨지지 않는다"는 바닥을 다지는 일이죠.

따라서 시니어 레벨의 엔지니어는 핵심 도메인 로직에 대해 **'전형적인 시나리오는 단위 테스트'**로, **'강력한 신뢰가 필요한 계산/변환 로직은 속성 기반 테스팅'**으로 병행하여 구축합니다.

---

### 4. 실전 임팩트: "버그 발견의 고속도로"

속성 기반 테스팅을 도입하면, 작성 단계에서부터 자신의 설계적 오류를 발견하게 됩니다.

"모든 양수에 대해 이 함수가 동작해야 한다"고 선언하고 돌리는 순간, 소수점 입력이나 0 입력에서 시스템이 터지는 것을 목격하게 되죠. 이것은 테스팅을 넘어 **'방어적 프로그래밍(Defensive Programming)'**을 강제하는 강력한 훈련 도구가 됩니다.

기계의 끈질김을 이용하여 여러분의 코드에서 '운 좋게 숨어있던 버그'를 영원히 추방하십시오.
