## 적용 가능한 도메인과 효율적인 트레이드오프 전략

속성 기반 테스팅(Property-based Testing)은 마치 전차와 같습니다. 강력한 방어력을 제공하지만, 좁은 골목길(단순한 CRUD)에 투입하기에는 너무 무겁고 느릴 수 있습니다. 테스팅의 전문가가 되기 위해서는 이 강력한 무기를 **'어디에 투입하고 어디서 멈출지'** 결정하는 선구안이 필요합니다.

---

### 1. 투입 결정: 어떤 로직에 적합한가?

속성 기반 테스팅이 가장 빛나는 곳은 **'입력은 무한하지만 결과의 규칙은 명확한 곳'**입니다.

- **순수 계산/변환 로직 (Pure Logic)**: 환율 계산기, 세금 산출 엔진, JSON 파서, 암호화 알고리즘 등
- **정렬 및 검색 알고리즘**: 복잡한 비즈니스 조건이 들어간 커스텀 정렬 로직
- **인프라 어댑터**: 파일 시스템 경로 처리기, URL 파서와 같이 다양한 엣지 케이스가 존재하는 유틸리티
- **동시성 및 상태 머신**: 여러 이벤트가 무작위 순서로 발생해도 최종 상태가 정합성을 유지해야 하는 경우 (`fast-check`의 Model-based testing 활용)

### 2. 기피 대상: 언제 피해야 하는가?

반대로 다음과 같은 경우에는 예제 기반 단위 테스트만으로 충분하거나, 오히려 속성 기반 테스팅이 해로울 수 있습니다.

- **단순 CRUD**: 유저를 저장하고 그대로 조회하는 로직은 "내가 넣은 값이 그대로 나온다"는 속성 외에는 검증할 것이 적으며, DB Mocking 설정 비용이 더 큽니다.
- **UI/UX 테스팅**: "버튼이 파란색이어야 한다"는 속성은 무작위 데이터로 검증할 성질의 것이 아닙니다.
- **지나치게 느린 로직**: 하나의 테스트가 1초 이상 걸린다면, 1,000번의 무작위 시도를 수행하는 속성 기반 테스팅은 전체 테스트 스위트를 멈추게 할 것입니다.

---

### 3. 트레이드오프 전략: 가성비 챙기기

속성 기반 테스팅을 현명하게 운영하는 전략적 조언입니다.

1. **테스트 횟수 조절**: 개발 단계에서는 `100회` 정도로 빠르게 돌리고, 배포 전 CI 환경에서는 `1,000회~10,000회`로 늘려 깊이 있게 검증하십시오.
2. **복잡한 Arbitrary 피하기**: 데이터 생성기(Arbitrary) 자체가 너무 복잡해져서 **'테스트 데이터를 만드는 코드의 버그'**를 걱정해야 할 정도라면, 설계를 단순화해야 한다는 신호입니다.
3. **가역성(Round-trip) 속성 활용**: `serialize(deserialize(data)) === data`와 같은 **라운드 트립 테스트**는 속성 기반 테스팅을 적용하기 가장 쉽고 가성비 좋은 지점입니다.

---

### 시니어의 결론: "모든 곳에 쓸 필요는 없다"

여러분의 코드 중 **'버그가 발생했을 때 손실이 막대한 핵심 알고리즘'** 10%에만 속성 기반 테스팅을 투입하십시오.

나머지 90%의 평범한 로직은 기존의 단위 테스트와 통합 테스트로 관리하는 것이 엔지니어링 리소스 측면에서 훨씬 효율적입니다. 전략적인 선택과 집중이 여러분의 시스템을 가장 경제적이면서도 단단하게 만들어 줄 것입니다.
