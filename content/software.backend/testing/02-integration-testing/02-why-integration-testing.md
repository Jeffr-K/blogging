## 단위 테스트의 한계를 메우는 통합 테스팅의 필요성

"단위 테스트 커버리지가 100%인데, 왜 실제 DB를 연결하면 서버가 터질까요?" 이 질문은 모든 백엔드 엔지니어의 숙명과도 같습니다. 단위 테스트는 개별 모듈의 논리는 증명하지만, 모듈들이 서로 맞물렸을 때 발생하는 **'상호작용의 복잡성'**까지는 해결하지 못합니다.

---

### 1. 단위 테스트의 사각지대 (Blind Spots)

단위 테스트가 잡아내지 못하는 전형적인 버그들이 있습니다.

- **구성(Configuration) 오류**: 잘못된 환경 변수, DB 접속 정보 오류, 빈(Bean) 등록 누락.
- **SQL 문법 및 DBMS 제약**: 모킹된 리포지토리는 SQL을 검증해주지 않습니다. 실제 DB에서만 발생하는 `Index 중복`, `FK 제약 조건 위반`, `Type 불일치` 등은 단위 테스트의 영역이 아닙니다.
- **통신 시퀀스 오류**: 메서드 호출 순서는 맞을지 몰라도, 실제 TCP 연결이 끊기거나 타사 API가 예상치 못한 403 에러를 뱉는 상황은 실제 통신이 일어나야만 알 수 있습니다.

### 2. 통합 테스팅이 주는 심리적 안정감

- **데이터 무결성 확인**: "서비스 계층에서 저장한 객체가 정말로 DB에 동일한 구조로 들어갔는가?"를 직접 확인함으로써 ORM 설정의 무결성을 증명합니다.
- **실전 같은 예행연습**: 실제 환경과 유사한 Docker 컨테이너(Testcontainers) 등을 띄워 테스트함으로써 배포 직전의 리스크를 획기적으로 낮춥니다.

### 3. 트레이드오프: 비용과 속도

물론 통합 테스트는 단위 테스트보다 비쌉니다.

- **속도**: DB를 초기화하고 연결하는 시간 때문에 단위 테스트보다 수십 배 느립니다.
- **복잡도**: 테스트 환경을 구축하는 설정(DockerCompose, YAML 등)이 복잡해집니다.

하지만 이 모든 '비용'은 **'상용 장애로 인한 손실'**에 비추어 볼 때 매우 저렴한 보험료입니다.

---

### 전문가의 한마디: "부품이 좋다고 자동차가 굴러가지는 않는다"

단위 테스트가 완벽한 엔진, 타이어, 핸들을 보증한다면, 통합 테스트는 이들을 조립하여 핸들을 돌렸을 때 타이어가 올바른 방향으로 움직이는지를 확인하는 작업입니다.

단위 테스트의 고속 피드백에 안주하지 마십시오. 시스템이 외부 세계인 인프라와 만나는 **'가장 뜨거운 경계면'**을 통합 테스트로 수호하십시오. 그것이 진정한 엔드 투 엔드 품질의 시작입니다.
 Jennifer 정 (Senior QA Architect)
