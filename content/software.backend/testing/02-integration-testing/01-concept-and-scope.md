## 통합 테스트의 정의와 검증 범위: 경계선을 넘어라

단위 테스트가 고립된 방 안에서 홀로 춤을 추는 것이라면, **통합 테스트(Integration Testing)**는 파트너와 손을 잡고 춤을 추는 것과 같습니다. 아무리 정교하게 설계된 부품이라도 서로 연결될 때 어긋날 수 있습니다. 통합 테스트는 모듈과 모듈, 혹은 시스템과 인프라 사이의 **'인터페이스 정합성'**을 증명하는 강력한 수단입니다.

---

### 1. 통합 테스팅의 본질: '협력'의 증명

통합 테스트의 주인공은 개별 함수가 아니라, **'메시지의 흐름'**입니다.

- **모듈 간 통합**: Service A가 도메인 엔진 B를 호출할 때 데이터 형식이 일치하는가?
- **인프라 통합**: 애플리케이션이 생성한 SQL 쿼리가 실제 DBMS에서 문법 오류 없이 실행되는가?
- **외부 연동**: 결제 모듈이 보낸 요청을 외부 PG사 어댑터가 정확히 이해하고 가공하는가?

### 2. 검증 범위: 어디까지가 통합 테스트인가?

통합 테스트는 보통 **'프로세스 내부(In-process)'**와 **'프로세스 외부(Out-of-process)'**의 경계에서 일어납니다.

1. **내부 모듈 통합**: 여러 서비스와 리포지토리를 한목에 띄워 비즈니스 흐름을 검증합니다.
2. **저장소 통합 (Persistence)**: 실제 DB(또는 테스트용 DB)를 사용하여 데이터가 영속되는 과정을 검증합니다.
3. **인프라 어댑터 통합**: 메시지 큐(RabbitMQ, Kafka)나 Redis와의 통신 규약을 검증합니다.

### 3. 단위 테스트와의 명확한 경계선

시니어 레벨에서는 **'공유 의존성(Shared Dependency)'**의 사용 여부로 구분합니다.

- **단위 테스트**: 네트워크나 DB 서버 없이 메모리 내에서만 작동. (Side Effect 없음)
- **통합 테스트**: 실제 네트워크 서비스, 데이터베이스, 파일 시스템 등을 활용. (Side Effect 발생)

---

### 결론: 통합 테스트는 시스템의 지도를 그리는 작업이다

많은 개발자가 통합 테스트를 단순히 "여러 기능을 한꺼번에 돌려보는 것"으로 오해합니다. 하지만 진정한 통합 테스트의 가치는 **"애플리케이션이 외부 세계와 맺고 있는 계약(Contract)이 여전히 유효한가?"**를 확인하는 데 있습니다.

내부 로직이 아무리 완벽해도 외부 인프라와의 통신 한 번이 실패하면 시스템은 멈춥니다. 통합 테스트는 여러분의 코드가 세상과 소통하는 **'신뢰의 가교'**가 되어 줄 것입니다.
 Jennifer 정 (Senior System Architect)
