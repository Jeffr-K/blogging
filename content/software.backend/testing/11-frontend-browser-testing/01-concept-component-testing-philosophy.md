## 컴포넌트 테스팅의 본질: 구현이 아닌 '사용자의 행위'를 테스트하라

"제가 컴포넌트 내부의 `state`가 `true`인지 확인하는 테스트를 짰는데, 코드를 조금만 고쳐도 테스트가 다 깨져요." 프론트엔드 주니어 개발자들이 가장 많이 토로하는 고충입니다. 이는 테스팅의 목적을 **'코드의 작동'**이 아닌 **'결과의 검증'**으로 착각했기 때문입니다. 프론트엔드 테스팅의 본질은 사용자가 무엇을 보고 무엇을 느끼는가에 있습니다.

---

### 1. 구현 세부 사항(Implementation Details)의 함정

- **잘못된 테스트**: "버튼을 클릭했을 때 `isDisabled` 상태값이 `true`로 변하는가?"
- **문제점**: 나중에 `isDisabled`라는 변수명을 `isPending`으로 바꾸면, 실제 기능은 똑같아도 테스트는 깨집니다.

이것을 **'취약한 테스트(Brittle Test)'**라고 부르며, 개발 효율을 깎아먹는 주범이 됩니다.

### 2. 사용자 중심의 블랙박스 테스팅

사용자는 컴포넌트 내부의 `state`가 어떻게 되어있는지 관심이 없습니다. 오직 **"버튼을 눌렀더니 로딩 스피너가 보이고 버튼이 클릭되지 않네?"**라는 현상만 봅니다.

- **올바른 테스트**: "사용자가 로그인 버튼을 클릭했을 때, 화면에 '로그인 중...'이라는 문구가 보이는가?"

이렇게 테스트를 짜면 내부 코드를 `useState`에서 `useReducer`로 바꾸든, 상태 변수명을 무엇으로 고치든 테스트는 깨지지 않고 우리를 지켜줍니다.

### 3. 리팩토링의 파수꾼

프론트엔드 개발은 UI 트렌드와 라이브러리 교체가 매우 빈번합니다. 사용자의 행위에 기반한 테스트는 우리가 대규모 리팩토링을 감행할 때 "인터페이스는 바뀌지 않았으니 사용자는 예전과 똑같이 서비스를 이용할 수 있어"라는 확신을 주는 가장 강력한 도구가 됩니다.

---

### 결론: 화면 뒤가 아닌 화면 앞을 테스트하라

여러분의 테스트 코드가 컴포넌트의 프롭스(Props)나 상태(State)를 직접 건드리고 있다면 즉시 멈추십시오.

사용자의 눈으로 컴포넌트를 바라보십시오. 사용자가 무엇을 클릭하고, 무엇이 화면에 나타나기를 기대하는지 그 **'행위의 흐름'**을 기술하십시오. 그것이 바로 10년이 지나도 깨지지 않는 견고한 프론트엔드 테스트를 만드는 유일한 비결입니다.
 Jennifer 정 (Senior Frontend Architect)
