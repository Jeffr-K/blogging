## 캐시가 왜 필요한가

핵심 이유는 하나입니다. **빠른 저장소와 느린 저장소 사이의 속도 차이(Speed Gap)** 때문입니다.

```
레지스터       ~0.3 ns
L1 캐시        ~1 ns
L2 캐시        ~4 ns
L3 캐시        ~10 ns
DRAM           ~100 ns    ← CPU 대비 300배 느림
SSD            ~100 μs    ← CPU 대비 300,000배 느림
HDD            ~10 ms     ← CPU 대비 30,000,000배 느림
네트워크 (DB)  ~1~10 ms
```

CPU가 아무리 빨라져도, 데이터를 가져오는 시간이 병목이면 의미가 없습니다. 캐시는 이 병목을 해소하기 위해 **자주 쓰는 데이터를 더 빠른 저장소에 미리 올려두는 것**입니다.

백엔드 관점에서는 DB가 느리고, 애플리케이션 메모리나 Redis가 빠릅니다. 캐시는 이 둘 사이에 놓이는 중간 계층입니다.

## 지역성의 원리 (Principle of Locality)

캐시가 효과적인 이유는 **프로그램의 데이터 접근 패턴이 균등하지 않기 때문**입니다.

### 시간 지역성 (Temporal Locality)

> 최근에 접근한 데이터는 가까운 미래에 또 접근할 가능성이 높다.

```
- 방금 조회한 상품 상세 페이지 → 뒤로가기 → 다시 같은 페이지
- 오늘 많이 팔리는 상품 → 계속 조회됨
- 로그인한 유저의 세션 → 요청마다 반복 조회
```

### 공간 지역성 (Spatial Locality)

> 특정 데이터에 접근하면, 그 근처의 데이터도 곧 접근할 가능성이 높다.

```
- 게시글 목록 조회 → 첫 페이지 → 두 번째 페이지 (순서대로)
- 배열의 첫 번째 원소 접근 → 두 번째, 세 번째 원소도 곧 접근
- CPU 캐시가 캐시라인(64바이트) 단위로 올리는 이유
```

### 실무 함의

지역성이 없는 데이터는 캐싱해도 효과가 없습니다.

```
효과 있음: 인기 상품 목록, 유저 프로필, 설정 정보
효과 없음: 랜덤 유저 ID 조회, 매번 다른 복잡한 쿼리 결과
```

## 캐시의 정의

```
캐시 = 원본 데이터 소스보다 빠른 저장소에
       자주 접근하는 데이터를 복사해두는 것
```

중요한 건 **복사본**이라는 점입니다. 원본은 DB에 있고, 캐시는 그 복사본입니다. 이게 바로 **Cache Invalidation이 어려운 근본 이유**입니다. 원본이 바뀌면 복사본도 바꿔야 하니까요.

---

## 캐시의 기본 동작 흐름

```
클라이언트 요청
    ↓
캐시 확인 (Cache Lookup)
    ├── HIT: 캐시에서 바로 반환 ✓
    └── MISS: DB 조회 → 캐시에 저장 → 반환
```

```python
def get_user(user_id: str):
    # 1. 캐시 먼저 확인
    cached = redis.get(f"user:{user_id}")
    if cached:
        return deserialize(cached)  # Cache HIT

    # 2. 미스면 DB 조회
    user = db.query("SELECT * FROM users WHERE id = ?", user_id)

    # 3. 캐시에 저장 (TTL 5분)
    redis.set(f"user:{user_id}", serialize(user), ex=300)

    return user  # Cache MISS
```

## 캐시의 트레이드오프

캐시는 공짜가 아닙니다.

| 얻는 것 | 잃는 것 |
|--------|--------|
| 응답 속도 향상 | 데이터 일관성 (원본과 복사본 불일치 가능) |
| DB 부하 감소 | 추가 메모리 비용 |
| 처리량 증가 | 운영 복잡도 증가 |

> 캐시를 도입하는 순간, **"이 데이터가 최신임을 어떻게 보장할 것인가"** 라는 질문이 따라옵니다. 이게 Cache Invalidation 문제이고, 캐싱에서 가장 어려운 부분입니다.

---

## 핵심 요약

- 캐시는 Speed Gap을 해소하기 위해 존재한다
- 지역성(시간/공간)이 있는 데이터에 캐시가 효과적이다
- 캐시는 복사본이므로 원본 변경 시 동기화 문제가 발생한다
- 성능 vs 일관성 트레이드오프를 항상 인식해야 한다
