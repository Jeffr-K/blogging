## CAP 이론

분산 시스템에서 다음 세 가지를 동시에 모두 보장할 수 없습니다:

```
C (Consistency):    모든 노드가 같은 시각에 같은 데이터 반환
A (Availability):   모든 요청이 응답을 받음 (오류 없음)
P (Partition Tolerance): 네트워크 파티션(단절)이 발생해도 동작
```

**실제로는 P를 포기할 수 없습니다** (네트워크는 항상 실패 가능). 따라서 실질적인 선택은 **CP vs AP**입니다.

---

## CP 시스템 (일관성 우선)

네트워크 파티션 시 응답을 거부합니다.

```
Redis Cluster: 과반수 노드 없으면 쓰기 거부
ZooKeeper: 리더 없으면 읽기/쓰기 거부

동작:
  파티션 발생 → 과반수 없는 쪽: 오류 반환
  파티션 해소 → 정상 서비스

사용 사례: 분산 락, 설정 관리, 리더 선출
```

---

## AP 시스템 (가용성 우선)

네트워크 파티션 시 구버전 데이터를 반환합니다.

```
DNS 캐시, CDN, Redis Sentinel(기본 설정):
  파티션 발생 → 구버전 데이터 계속 서빙
  파티션 해소 → Eventually Consistent

사용 사례: 콘텐츠 캐시, 사용자 프로필, 설정 캐시
```

---

## 캐시는 어디에?

```
Redis 단일 노드: AP (노드가 응답하면 항상 반환)

Redis Cluster: 기본 AP (읽기는 구버전 반환 가능)
               CP로 설정 가능 (replica-read 제한)

Redis Sentinel: AP (Failover 중 구버전 반환)

캐시 레이어 전체: AP 특성
  → 캐시가 구버전 데이터를 반환할 수 있음
  → DB는 CP (트랜잭션, 잠금)
```

---

## PACELC 이론 (CAP 확장)

파티션이 없을 때도 **지연시간(L) vs 일관성(C)** 트레이드오프가 있습니다:

```
파티션 있을 때: PA/PC 선택
파티션 없을 때: EL(Else Latency) / EC(Else Consistency) 선택

예시:
  캐시 읽기:  P→A, E→L  (가용성 + 낮은 지연시간 우선)
  캐시 쓰기:  P→A, E→L  (빠른 쓰기, 불일치 허용)
  분산 락:    P→C, E→C  (일관성 우선, 지연시간 허용)
```

---

## 캐시 설계에 CAP 적용

```
1. 재고 (강한 일관성 필요)
   → CP: 캐시 없이 DB에서 직접
   또는 → 분산 락 + 캐시 (CP 동작)

2. 사용자 프로필 (최종 일관성 허용)
   → AP: Redis 캐시, TTL로 최종 수렴
   일시적 구버전 반환 OK

3. 세션 (가용성 중요, 일관성 보통)
   → AP: Redis, Sentinel로 Failover
   세션 인증: 만료 기반으로 처리

4. 분산 락 (강한 일관성 필수)
   → CP: Redlock (5노드 과반수) 또는 ZooKeeper
```

## 실무 결론

```
캐시를 사용하는 순간 이미 AP 시스템:
  → 일관성을 일부 포기한 것
  → 얼마나 포기할지는 비즈니스 요구사항

허용 불일치 시간:
  "잔액 틀리면 안 됨" → 캐시 없이 DB 직접
  "프로필 1분 구버전 OK" → TTL=60s 캐시
  "조회수 5분 오차 OK" → TTL=300s 캐시
```

---

## 핵심 요약

- CAP: 분산 시스템에서 C/A/P 동시 보장 불가, 실질적 선택은 CP vs AP
- 캐시는 AP: 구버전 데이터 반환 가능, 대신 빠름
- PACELC: 파티션 없을 때도 지연시간 vs 일관성 선택
- 강한 일관성 필요 → 캐시 제외 또는 분산 락 + 동기 업데이트
- 비즈니스가 허용하는 불일치 시간 = TTL 설계의 출발점
