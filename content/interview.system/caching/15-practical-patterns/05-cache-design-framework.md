## 캐시 설계의 7단계

면접이나 실무에서 캐시를 설계할 때 아래 순서로 접근합니다.

---

### 1단계: 무엇을 캐시할 것인가

```
판단 기준:
  □ 반복 조회되는가? (같은 쿼리가 초당 N번 이상)
  □ 계산 비용이 큰가? (쿼리 > 50ms, 복잡한 집계)
  □ 변경 빈도가 낮은가? (TTL 내에 변경 안 됨)
  □ 공유 가능한가? (사용자별로 같은 값인가)

예시:
  좋음: 상품 정보, 랭킹, 설정값, 카테고리 목록
  나쁨: 실시간 잔액, 재고 1개 남은 한정판, 개인화 피드
```

---

### 2단계: 어디에 캐시할 것인가

```
로컬 캐시 (Caffeine):
  → 읽기 전용, 변경 드문 데이터
  → 초저지연 필요, Hot Key 완화

Redis (분산 캐시):
  → 서버 간 공유 필요
  → 대용량 데이터

Two-Level (Local + Redis):
  → Hot Key + Redis 부하 분산

HTTP 캐시 (CDN/브라우저):
  → 공개 정적 콘텐츠
  → API 응답 (사용자 독립적)
```

---

### 3단계: 어떤 TTL을 설정할 것인가

```
데이터 특성별 TTL 가이드:
  설정/코드표:        24시간~7일
  카테고리/메뉴:      1~24시간
  상품 정보:         5분~1시간
  사용자 프로필:      1분~1시간
  랭킹/집계:         30초~5분
  실시간 재고:        5~30초 (또는 캐시 안 함)
  세션:              30분~24시간 (Sliding TTL)

Jitter 반드시 포함:
  ttl = base_ttl * (0.9 + random() * 0.2)  # ±10%
```

---

### 4단계: 어떻게 무효화할 것인가

```
TTL 만료:         변경이 드물고 구버전 허용 시
이벤트 기반:      변경 즉시 무효화 필요 시
버전 기반:        그룹 무효화 필요 시
CDC/Debezium:    코드 없이 인프라로 처리 시
```

---

### 5단계: 장애 패턴 대비

```
Stampede:  mutex / probabilistic refresh / jitter
Avalanche: jitter + circuit breaker + 다단계 캐시
Penetration: null caching + bloom filter
Hot Key:   local cache + key sharding
```

---

### 6단계: 일관성 수준 결정

```
허용 불일치 시간 = TTL 상한

"이 데이터가 N초 구버전이어도 괜찮은가?"
  → Y: TTL = N, 캐시 적용
  → N: 캐시 없이 DB 직접, 또는 분산 락 + 동기 업데이트
```

---

### 7단계: 모니터링 설정

```
필수 지표:
  - 히트율 (목표 > 80%)
  - 메모리 사용률 (경고 > 85%)
  - 응답 시간 p99 (경고 > 50ms)
  - 제거 수 (증가 추세면 메모리 부족)

알람:
  - 히트율 < 60%: 즉시 확인
  - 메모리 > 95%: 즉시 대응
  - 응답 시간 급증: Stampede/Avalanche 의심
```

---

## 빠른 설계 체크리스트

```
캐시 설계 시 반드시 답해야 하는 질문:

1. 히트율 예상? (30% 미만이면 도입 가치 낮음)
2. 허용 불일치 시간? (TTL 결정)
3. 무효화 트리거? (언제 삭제?)
4. Stampede 대책? (Jitter or Mutex)
5. 장애 시 동작? (Redis 다운 시 DB Fallback?)
6. 민감 데이터 없음? (개인정보, 비밀번호 절대 금지)
7. 모니터링 있음? (히트율, 메모리 알람)
```

## 면접 답변 예시

Q: "대규모 커머스에서 상품 페이지 캐싱을 어떻게 하시겠습니까?"

```
1. 캐시 대상: 상품 기본 정보(TTL 1시간), 가격(5분), 재고(캐시 안 함)

2. 전략: Cache-Aside + Write-Through(가격)
   상품 업데이트 시 캐시 삭제 이벤트

3. 무효화: @CacheEvict or CDC(Debezium)로 상품 변경 시 자동

4. 장애 대비:
   - Jitter로 동시 만료 방지
   - Bloom Filter로 없는 상품 ID 조기 차단
   - Two-Level Cache (Caffeine + Redis)로 Hot Key 완화

5. 일관성: 가격/재고는 구버전 절대 불가 → 캐시 없이 DB 직접
   상품 설명은 1시간 구버전 OK → TTL 기반

6. 모니터링: 히트율 >85% 목표, 메모리 알람, 제거율 모니터링
```

---

## 핵심 요약

캐시 설계 7단계:
1. 무엇을 → 반복 조회, 계산 비용, 변경 빈도
2. 어디에 → 로컬/Redis/CDN
3. TTL → 데이터 특성 + Jitter
4. 무효화 → TTL/이벤트/CDC
5. 장애 패턴 → Stampede/Avalanche/Penetration 대비
6. 일관성 → 허용 불일치 시간 결정
7. 모니터링 → 히트율/메모리/응답시간
