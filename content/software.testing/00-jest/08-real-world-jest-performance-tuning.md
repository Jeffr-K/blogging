## 실전 사례: 대규모 프로젝트에서 Jest 실행 속도 2배 끌어올리기

프로젝트가 성장하여 테스트 케이스가 수천 개를 넘어서면, 어느 순간 "테스트 돌리는 게 너무 느려서 배포를 못 하겠어요"라는 불만이 터져 나옵니다. 로컬 PC에선 괜찮던 Jest가 왜 CI 서버만 가면 거북이가 되는 걸까요? 20분 걸리던 테스트 전체 실행 시간을 5분 이내로 단축시킨 실전 성능 최적화 전략을 공유합니다.

---

### 1. CI 서버의 비명: CPU Core와 maxWorkers의 비밀

Jest는 스마트하지만 CI 서버의 환경(제한된 리소스)을 완벽히 이해하진 못합니다.

- **원인**: CI 서버는 보통 2~4 코어의 낮은 사양입니다. Jest가 기본값으로 모든 코어를 다 쓰려고 시도하면, 오히려 컨텍스트 스위칭 비용 때문에 속도가 처참하게 느려지거나 OOM(Out of Memory)이 발생합니다.
- **해결책**: CI 환경에서는 `--maxWorkers=50%` 또는 명시적으로 `--maxWorkers=2` 정도로 제한하십시오. 적은 수의 워커가 집중해서 일하는 것이 훨씬 빠릅니다.

### 2. 분할 정복: Jest Sharding (샤딩)

Jest 28 버전부터 도입된 **Sharding**은 테스트 스위트를 여러 개의 덩어리로 나누어 각각 다른 CI 머신에서 실행하게 해줍니다.

```bash
# 전체 테스트를 4개의 머신으로 나누어서 실행 (첫 번째 머신 예시)
npx jest --shard=1/4
```

이렇게 하면 4대의 CI 서버가 동시에 테스트를 분담하므로, 이론적으로 실행 속도를 1/4로 줄일 수 있습니다.

### 3. 메모리 누수(Memory Leak) 범인 검거

의존성이 복잡한 NestJS 테스트는 종종 메모리 누수를 일으킵니다.

- **증상**: 테스트가 진행될수록 한 파일당 실행 시간이 점점 늘어납니다.
- **해결**: `--logHeapUsage` 옵션을 켜서 어떤 테스트 파일이 메모리를 먹고 있는지 확인하십시오. 주로 전역 객체(Global)에 싱글톤 인스턴스를 테스트마다 계속 생성하여 쌓아두는 코드가 범인입니다. (`afterEach`에서 명시적으로 큰 객체를 `null` 처리하거나 앱 인스턴스를 닫으십시오.)

---

### 4. 사후 분석: 튜닝이 가져온 개발 문화의 변화

- **결과**: 전체 테스팅 시간 **65% 단축**.
- **변화**: 배포 전 테스트를 돌리는 것이 '준비 운동'처럼 가벼워졌고, "테스트가 느려서 생략하고 배포할게요"라는 위험한 변명이 사라졌습니다.

---

### 전문가의 총평: "성능은 도구가 아니라 운영이 결정한다"

Jest는 최고의 엔진이지만, 그 엔진을 CI라는 척박한 도로 위에서 어떻게 굴릴지는 엔지니어의 몫입니다.

리소스를 분석하고, 병렬성을 제어하며, 메모리 흐름을 관찰하십시오. 여러분의 테스트 자동화 환경이 쾌적해질수록, 팀 전체의 개발 속도와 신뢰도는 정비례하여 상승할 것입니다.
