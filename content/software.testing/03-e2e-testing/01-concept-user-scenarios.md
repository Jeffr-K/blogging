## E2E 테스트의 정의와 사용자 시나리오 기반 설계

**E2E 테스팅 (End-to-End Testing)**은 실제 사용자의 관점에서 시스템의 한쪽 끝(입력)에서 다른 쪽 끝(결과)까지 전체 흐름을 검증하는 기법입니다. 소스 코드가 어떻게 생겼는지, 어떤 데이터베이스를 쓰는지 모른 채 오직 **'비즈니스 결과물'**에만 집중하는 가장 포괄적인 테스팅 전략입니다.

---

### 1. 블랙박스 테스팅 (Black-box Testing)

E2E 테스트의 핵심 철학은 **"내부를 들여다보지 않는다"**는 것입니다. 

- **단위/통합 테스트**: 내부 클래스, 메서드, SQL 등을 직접 타격 (White-box).
- **E2E 테스트**: HTTP API, UI 요소 등 외부 노출 인터페이스만 타격 (Black-box).

이러한 특성 덕분에 내부 코드를 아무리 대규모로 리팩토링하더라도, 사용자 기능이 동일하다면 E2E 테스트는 깨지지 않고 우리를 지켜줍니다.

### 2. 사용자 시나리오 (User Scenario) 설계

E2E 테스트는 모든 기능을 테스트하는 것이 아닙니다. 사용자가 우리 앱에서 수행하는 **'가장 가치 있는 경로(Golden Path)'**를 시나리오로 만듭니다.

- **나쁜 시나리오**: 로그인이 되는가? -> 닉네임 변경이 되는가? (파편화됨)
- **좋은 시나리오**: 사용자가 회원가입을 하고, 로그인을 한 뒤, 상품을 검색하여 장바구니에 담고, 결제까지 성공하는가? (연속된 흐름)

### 3. 검증의 범위: 모든 시스템의 결합

E2E 테스트는 단순히 API 응답 코드만 보는 것을 넘어 다음과 같은 전체 인프라의 협력을 검증합니다.

1. **인증/인가**: JWT 혹은 세션이 모든 요청에서 정확히 유지되는가?
2. **비동기 처리**: 주문 요청 후 백엔드 워커가 메시지 큐를 통해 알림 메일을 성공적으로 발송했는가?
3. **네트워크 인프라**: 로드 밸런서, 방화벽 설정을 뚫고 외부 API와 정상적으로 통신하는가?

---

### 결론: E2E 테스트는 비즈니스의 최종 합격 통지서다

단위 테스트가 수천 개 있더라도 사용자가 주문을 마무리하지 못한다면 그 시스템은 실패한 것입니다. 

E2E 테스팅은 시스템의 부품이 아닌 **'목적'**을 검증합니다. 비즈니스의 핵심 성공 경로를 시나리오로 설계하십시오. 그 시나리오가 통과될 때마다 여러분은 "우리 서비스는 오늘도 안전하게 돈을 벌 준비가 되었다"는 확신을 가질 수 있게 될 것입니다.
