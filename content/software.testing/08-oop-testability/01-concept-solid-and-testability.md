## SOLID 원칙: 테스트 가능한 객체 설계의 5가지 이정표

많은 개발자가 SOLID 원칙을 '클린 코드를 위한 지침'으로만 알고 있지만, 사실 SOLID는 **'테스트 코드를 짜기 위한 최소 조건'**에 가깝습니다. SOLID를 어긴 코드는 반드시 테스트 코드 상에서 **'고통'**을 유발합니다. 각 원칙이 테스트 가능성과 어떻게 직결되는지 파헤쳐 봅시다.

---

### 1. SRP: 한 놈만 팬다 (Single Responsibility Principle)

- **테스트 관점**: 클래스가 여러 책임을 가지면 테스트의 설정(Setup)이 거대해집니다. `A` 기능을 테스트하고 싶은데 `B`, `C`에 필요한 의존성까지 다 모킹해야 하죠.
- **결과**: SRP를 지킨 클래스는 테스트 케이스가 명확해지고, 테스트 코드의 길이가 획기적으로 줄어듭니다.

### 2. OCP: 확장은 열고 수정은 닫고 (Open-Closed Principle)

- **테스트 관점**: 새로운 기능이 추가될 때마다 기존 테스트 코드를 고쳐야 한다면 OCP 위반입니다.
- **결과**: 인터페이스나 추상 클래스를 통해 디자인된 코드는 기존 테스트를 건드리지 않고도 새로운 시나리오(신규 구현체 테스트)를 추가할 수 있게 해줍니다.

### 3. LSP: 바꿔 끼워도 무방함 (Liskov Substitution Principle)

- **테스트 관점**: 우리가 만드는 **Mock 객체**는 상위 타입의 계약을 완벽히 준수해야 합니다.
- **결과**: LSP를 지키면 테스트 코드에서 실제 객체 대신 가짜 객체를 넣었을 때 시스템이 이상 동작을 하지 않을 것이라는 강력한 보증을 얻습니다.

### 4. ISP: 쓸데없는 일 시키지 마라 (Interface Segregation Principle)

- **테스트 관점**: "단 하나의 메서드만 쓰는데 10개의 메서드가 정의된 인터페이스를 구현해야 한다면?" 테스트 코드는 무의미한 9개의 모킹으로 가득 차게 됩니다.
- **결과**: ISP를 통해 인터페이스를 찢어놓으면, 테스트에 필요한 최소한의 인터페이스만 구현(Stub)하여 테스트의 밀도를 높일 수 있습니다.

### 5. DIP: 추상화에 의존하라 (Dependency Inversion Principle)

- **테스트 관점**: 구체 클래스(예: MySQLRepository)에 직접 의존하면 테스트는 DB 없이는 돌아갈 수 없습니다.
- **결과**: DIP를 통해 추상화(인터페이스)에 의존하면, 테스트 타임에 이 인터페이스를 구현한 가짜(InMemoryRepository)를 마음대로 갈아 끼울 수 있습니다.

---

### 결론: 테스트가 어렵다면 SOLID를 보라

테스트 코드를 짜다가 화가 난다면 멈추고 클래스의 구조를 보십시오. 분명 SOLID 중 하나 이상을 위반하고 있을 것입니다.

SOLID는 단순히 예쁜 코드를 만드는 도구가 아니라, **"이 객체를 고립시켜서 완벽하게 검증할 수 있는가?"**라는 질문에 답을 주는 아키텍처적 초석입니다. 설계를 고치십시오. 그러면 테스트는 선물처럼 따라올 것입니다.
 Jennifer 정 (Senior Design Architect)
